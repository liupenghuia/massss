## 冲突项

### C-1 操作日志 / 审计留痕是否属于本期本 feature

- 各方主张：
  - admin 主张 **高严重度，应做成 F-001 的最小内置能力**——「状态变更本身就是本 feature 的核心动作，不属于价格或回收站范畴，**没有地方能顺带补上这个日志**」
  - api 主张 **低严重度，不阻塞上线**——「建议至少记录 `updatedBy`/`updatedAt`」
  - qa 主张 **中严重度**——「即便本期不做，也建议显式写入『明确不做』清单，避免验收阶段产生分歧」
  - domain 未提及；miniapp 未提及
- 分歧根因：对 principles.md「后台账号越权」零容忍项是否需要日志作为落地抓手，判断不同。admin 认为「越权发生了也无法追溯、无法举证，等于零容忍条款没有落地抓手」；api 认为只是「后续排查缺乏依据」。
- 选项 A：本期内置完整操作日志（操作人、时间、变更前后状态/字段），并决定是否在后台可查 — 代价：评审中未给出工作量说明；admin 另提出「日志要不要在管理后台里可查看，还是只落库不展示」仍未定
- 选项 B：本期只记 `updatedBy`/`updatedAt` — 代价：api 自述为「建议」，未说明是否满足 admin 提出的追溯诉求
- 选项 C：本期不做，写入「明确不做」清单 — 代价：qa 指出否则验收阶段会产生分歧；admin 指出之后没有其他 feature 能承接

### C-2 是否为 F-005（回收站）预留软删除 / 已删除状态的扩展空间

- 各方主张：
  - api 主张 **不预留**——「本期不在 `vehicles` 表里预置 `is_deleted`/`deleted_at`，遵循 YAGNI，留给 F-005 时再做迁移」（自述为倾向、非定论，需用户确认迁移成本）
  - qa 主张 **应预留**——「F-001 设计状态枚举时应为未来的『已删除/回收站中』状态预留扩展空间，避免 F-005 落地时需要对已有状态字段做破坏性变更」
  - domain、admin、miniapp 未表态
- 分歧根因：YAGNI（api）与「避免破坏性变更」（qa）两条原则在同一处取舍相反。
- 选项 A：不预留字段 — 代价：api 自述「F-005 上线时大概率需要给 `vehicles` 表新增字段并对现有编辑/查询/状态流转接口做兼容改造」
- 选项 B：预留软删除字段 / 状态扩展位 — 代价：api 自述「违反 YAGNI」

### C-3 并发编辑（乐观锁）与创建幂等的优先级

- 各方主张：
  - api 主张 **高严重度，必须做**——编辑接口用乐观锁（`version` 或 `updatedAt` 比对），冲突返回 409；创建接口要求前端传 `Idempotency-Key`
  - qa 主张 **低严重度**——「车辆数量级『一百台以内』、无硬期限，短期风险不高，但建议在 open-questions 里记录以免遗漏」
  - admin、domain、miniapp 未提及并发场景
- 分歧根因：api 从「静默覆盖 + 用户不会感知丢失了什么」的数据损失后果定级；qa 从数据量级与并发概率定级。
- 选项 A：本期实现乐观锁 + Idempotency-Key — 代价：需要前端配合（传 version / Idempotency-Key、处理 409 提示），而管理后台评审（admin）通篇未提及这两项
- 选项 B：本期不做，记入 open-questions — 代价：api 描述的「后提交者静默覆盖前者修改」风险保留

### C-4 上下架动作对「非法/重复调用」的返回语义

- 各方主张：
  - api 主张 **幂等**——「对已处于目标状态的车辆重复调用 publish/unpublish 返回 200 且无副作用，而不是报错，避免管理员误触或网络重试导致状态抖动或产生多余的操作记录」
  - qa 主张 **非法路径应有明确错误**——「草稿状态下能否被『下架』（应报错还是无操作）？非法状态转换（如对草稿执行『重新上架』）应返回什么结果？这些非法路径不测会成为线上事故来源」，并要求先补齐「状态转换矩阵」
  - api 自己也把「草稿态车辆能否直接下架」列为中严重度未定义项
  - domain、admin、miniapp 未就返回语义表态
- 分歧根因：api 以「避免状态抖动 / 多余操作记录」为目标；qa 以「非法路径可测、可断言」为目标。
- 选项 A：重复/非法调用返回 200 无副作用 — 代价：qa 指出无法为非法路径写断言用例
- 选项 B：非法转换返回明确错误码 — 代价：api 指出误触或网络重试会导致状态抖动或产生多余操作记录

### C-5 交付载体是否为微信小程序（全项目技术选型未定）

- 各方主张：
  - miniapp 主张 **高严重度，前提未经确认**——「全项目**目前没有任何一处文档明确提出『微信小程序』这个载体**」；倾向前台走 H5、管理后台不做小程序，自述「一旦确认不采用，本评审中标注为『若小程序』的条目可全部作废」
  - api / admin / domain / qa 均**默认 Web**（api 用 `/public/*`、`/admin/*` 路由；admin 称「管理后台前端」「导出 Excel」；miniapp 之外无人对载体表态）
- 分歧根因：其余四方把 Web 当作既定前提直接展开设计，miniapp 指出该前提从未被确认。
- 选项 A：确认走 Web（H5 前台 + 桌面网页后台） — 代价：miniapp 评审的大部分风险条目作废
- 选项 B：确认（部分）走小程序 — 代价：miniapp 列出的类目审核资质、openid 与管理员账号绑定、分包、合法域名备案等条目成为「真实阻塞项，需要在启动开发前定论，避免返工」
- 附：miniapp 单方提出的高严重度条目——二手车/车辆信息类目在小程序审核中可能被归为限制类目，需企业资质，「否则可能审核不通过导致整个前台无法上线」，其余四方均未评估此风险

### C-6 车辆卡片本身是否包含价格字段

- 各方主张：
  - domain 主张 **不含**——「『车辆卡片』在 F-001 范围内只承载状态与『核心字段』本身，价格、图片、报告是挂在同一车辆实体上、但由其他 feature 独立管理的关联数据」
  - api 主张 **倾向不含但需确认**——「需要确认：车辆卡片本身是否包含任何价格占位字段（哪怕为空）……这个边界如果不清楚，两个 feature 的 contracts 会互相踩脚」
  - qa 主张 **需明确读写权归属，并给出两种可能**——「F-001 只读展示、F-004 独占写入？还是 F-001 在创建时写入首次价格、后续变更走 F-004？这个边界不清，F-004 的『价格历史』起点就无法定义（第一条历史记录从哪来）」
  - admin 未就字段归属表态，只问「发布上架时是否要求价格已录入」
- 分歧根因：domain 从聚合边界出发，qa 从 F-004 价格历史「第一条记录来源」出发，两者对同一字段的必要性判断不同。
- 选项 A：F-001 完全不含价格列 — 代价：qa 指出 F-004 的价格历史起点无法定义
- 选项 B：F-001 含价格占位/首次价格字段 — 代价：api 指出两个 feature 的 contracts 可能互相踩脚，需先划清读写权

### C-7 跨 feature 关联锚点用技术主键还是业务唯一标识

- 各方主张：
  - api 主张 **技术主键**——「`vehicleId` 作为稳定主键（自增或 UUID 均可，倾向自增），作为 F-003/F-004 挂载的外键锚点」
  - domain 主张 **引入业务侧唯一标识**——「建议为车辆引入一个业务侧唯一标识（如车架号/VIN 或内部编号），作为跨 feature（价格记录、图片、回收站）关联和运营查重的锚点」
  - qa 未选边，但要求「车辆的唯一标识（ID）生成规则和稳定性要求是什么？编辑过程中是否可能变化」
  - admin 提出「没有说明车辆用什么字段判重/查找（车架号 VIN？内部编号？）」
- 分歧根因：api 以外键稳定性为目标，domain 以「跨 feature 关联 + 运营查重」双重目标为出发点。
- 选项 A：技术主键做关联，业务标识只作查重字段 — 代价：评审中未给出
- 选项 B：业务唯一标识兼作关联锚点 — 代价：评审中未给出；与 A-5「主键创建后不可变更」的关系未有任何一方说明

### C-8 管理后台列表页（筛选/搜索）是否属于 F-001 范围

- 各方主张：
  - admin 主张 **属于本 feature 隐含最小可用范围**——「即使 brief 没提，我倾向于把它当作本 feature 的隐含最小可用范围，而不是留到后续迭代——否则车辆一多（哪怕上限 100 台）列表页就没法用」，并因 F-001 不做删除、数据只增不减而认为这是「高优先级缺口，而不是可以推给未来迭代的东西」（风险表中自评为中严重度）
  - api 未定义任何列表 / 查询端点（端点清单仅含 POST 创建、PUT/PATCH 编辑、publish、unpublish），仅提到「为 `status`、更新时间等常用筛选字段建普通索引」
  - domain、qa、miniapp 未提及列表页
- 分歧根因：admin 从运营日常最高频操作路径出发主动扩范围；其余角色按 brief 字面范围展开。
- 选项 A：纳入 F-001（列表 + 状态筛选 + 关键字搜索） — 代价：admin 自述这是「本评审提出的隐含需求，不是 brief 里写的」，即扩大 brief 范围
- 选项 B：不纳入 — 代价：admin 描述「运营会在几十上百条已下架车辆里迷失」

### C-9 「已下架」能否退回「草稿」

- 各方主张：
  - domain 主张 **当前状态机不支持，但需提前确认**（低严重度）——「草稿只是单向起点……若运营上有『下架后想大改再重新走草稿流程』的诉求，现状态机无法支持」
  - api 的端点设计中 publish 覆盖「草稿或已下架 → 已发布」，无回退草稿的端点
  - admin、qa、miniapp 未提及
- 分歧根因：无正面对立主张，属 domain 单方提出、其余方默认不支持。
- 选项 A：状态机固定为 草稿 → 已上架 ⇄ 已下架 — 代价：domain 指出无法支持「下架后大改再走草稿流程」
- 选项 B：允许已下架 → 草稿 — 代价：评审中未给出
