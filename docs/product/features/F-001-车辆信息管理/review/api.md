## 我理解的需求

管理员在管理后台对车辆卡片做增、改、发布/下架，服务端统一提供 `/admin/*`（需鉴权）与 `/public/*`（无需鉴权）接口。核心是一套三态状态机（草稿/已上架/已下架），编辑与状态转换解耦，全程无审核。价格、图片/报告、删除恢复分别归 F-004/F-003/F-005，本 feature 只管车辆基础信息与状态。

## 我的方案倾向

- 车辆以系统自动生成的技术主键（如自增 ID 或 UUID）作为跨 feature 关联锚点，VIN 不做唯一性约束、不作为主键。
- 编辑接口用乐观锁（版本号字段）防止后台并发编辑覆盖写；创建接口要求客户端传幂等键，防止网络重试导致重复建卡。
- 状态转换接口（发布/下架/重新上架）按"目标状态"设计，对已处于目标状态的重复调用直接返回成功（幂等），对非法转换（如草稿直接下架）返回明确错误，二者用不同的响应区分，不能混为一谈。
- `/public/*` 列表与详情接口直接按 status='published' 过滤，不引入独立的发布快照表或缓存层，保证下架立即生效；100 台量级下全表扫描/简单索引足够，不需要提前做读写分离。
- 发布前置校验（图片≥4张、价格非空）需要跨 feature 读 F-003/F-004 的数据，这个校验应放在 F-001 的发布接口内做同步调用/联表查询，不应要求 F-003/F-004 反向推送状态到 F-001，避免维护额外的冗余标志位。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 中 | 发布前置条件依赖 F-003/F-004 数据的一致性 | 发布时同步查图片数与价格是否非空，若 F-003/F-004 的写入接口和 F-001 的发布接口分属不同事务，存在"查询时满足、真正发布时又不满足"的极小窗口（如同时编辑价格清空），建议发布校验与状态落库在同一事务/短时间窗口内完成，不做长时间的两阶段流程 |
| 中 | 乐观锁版本号未在 spec 中明确暴露给前端的字段名与冲突提示格式 | contracts 中已有 VEHICLE_VERSION_CONFLICT，但需确认冲突时是否返回最新数据供前端合并展示，还是仅报错要求用户刷新重试 |
| 低 | 车辆规模"按可增长设计"缺少具体量级预期 | ADR-007 已提及，但列表接口的分页/搜索字段（按关键字搜索命中哪些字段：品牌/车型/VIN后六位?）未列出，影响是否需要建组合索引，此项应在 spec 或 contracts 补充而非留空 |
| 低 | 操作日志"只落库不做查看页面"缺少保留期与清理策略 | 无上限持续写入的操作日志表长期会膨胀，建议明确是否需要定期归档/删除，非阻塞项，可后续小改 |

## 对其他端的隐含要求

**管理后台**：发布/下架/重新上架失败时，需要能展示服务端返回的"缺失项提示"（如缺图片/缺价格）具体内容，而不是只显示通用错误码；编辑保存前应做好版本冲突提示与重新拉取最新数据的交互。

**F-003/F-004**：图片上传、价格录入接口需保证写入后立即可被 F-001 发布校验读到（不做异步落库或队列延迟），否则会出现"刚上传4张图却提示不足4张"的体验问题。

## 我需要别人回答的问题

- 管理后台列表页"按关键字搜索"具体命中哪些字段（品牌/车型/颜色/VIN后六位），需要明确以确定索引设计。
