## 我理解的需求

F-001 是管理后台对车辆卡片（核心字段）的录入、编辑、上架/下架状态流转，不含图片、评估报告、价格、回收站（分别归 F-003/F-004/F-005），也不含前台展示逻辑（归 F-002）。本 feature 唯一会被人在手机/微信内置浏览器打开的场景，是管理员在手机上操作管理后台（新建、编辑车辆、发布/下架）。前台访客侧不在本 feature 范围内，故本次不评前台微信打开体验。

## 我的方案倾向

管理后台按 ADR-001/principles 走响应式 Web，不做小程序、不做微信专属能力，微信内置浏览器当普通手机浏览器测即可，不需要额外的小程序化改造或 JS-SDK 接入。管理后台表单（品牌/车型/年份/里程/颜色/车况描述/能源类型联动字段/VIN）应保证手机竖屏下可完整填写与提交，登录态用标准 session/JWT，不依赖微信身份体系。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 中 | 微信内置浏览器（X5 内核）的 session/cookie/localStorage 行为与普通浏览器有差异（如多标签共享登录态、被清理更激进） | spec 未提及管理后台登录态在微信内置浏览器下的持久化策略，若管理员通过微信分享链接打开后台处理上下架，登录态异常会直接影响"全程不需要他人审核，保存后可自行直接发布"这条成功标准的可用性 |
| 中 | 车辆表单字段较多且含能源类型联动的选填字段（排量/电耗/电池度数），手机竖屏一屏难以容纳 | spec 未定义移动端表单的分组/折叠策略，若照抄桌面双栏布局在手机上会违反 principles 的"简单"与"375px 不破版"硬规则 |
| 低 | VIN（车架号）为后台专用字段，展示只露后六位，但录入是全号 | 手机端长字符串输入框易被 iOS 键盘放大或遮挡，spec 未提及录入交互，需按 principles 的 16px 字号规则处理 |
| 低 | 发布前置条件（图片≥4张、价格已填）校验失败时的提示 | spec 只说"返回明确的缺失项提示"，未强调手机端展示方式；需避免用状态码兜底（principles 已定义为缺陷），实现时需留意 |

## 对其他端的隐含要求

**服务端**：登录态建议用可跨浏览器环境正常工作的标准 session/JWT 机制，不假设桌面浏览器行为，避免微信内置浏览器下登录频繁失效。

**管理后台**：车辆表单在手机竖屏下需明确字段分组/折叠方案，不能直接压缩桌面双栏布局；发布前置条件的缺失项提示需在小屏幕上逐条可读。

**前台（F-002）**：本 feature 不涉及前台展示，微信内 H5 相关风险留给 F-002 评审处理，此处不重复评。
