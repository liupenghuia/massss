## 我理解的需求

F-001 是**管理后台**侧的能力：管理员录入/编辑车辆卡片核心字段，控制车辆的
草稿、上架、下架状态，全程无需他人审核、保存后可自行发布。
不含价格记录（F-004）、删除/回收站（F-005）、图片与评估报告上传（F-003）、
访客展示（F-002）。

根据 `docs/product/overview.md`：管理后台"桌面优先"、需登录；前台"移动优先"、
无需登录，且 SEO 不重要（"纯客户端渲染即可"）。全项目**目前没有任何一处文档
明确提出"微信小程序"这个载体**——技术栈仅写"稳定可靠，具体帮我定下来就行"。

因此我对这次评审的定位是：F-001 本身不描述任何端的技术形态，我需要先确认
本项目的前台/管理后台是否会以微信小程序形式交付，再判断微信侧的风险是否成立。
下面的风险与问题均基于"可能采用小程序"这一未决前提展开，一旦确认不采用，
本评审中标注为"若小程序"的条目可全部作废。

## 我的方案倾向

在拿到明确的技术选型前，我的倾向是：

1. **前台优先考虑 H5，而非微信小程序。** `principles.md` 明确写"只是发链接给
   客户看→纯客户端渲染即可，简单得多"。"发链接"是网页的天然能力，小程序分享
   出去打开的是卡片/小程序页面而非普通 URL，链接语义与"发链接给客户看"的诉求
   不完全匹配。若产品确认后续仍要走小程序，需要另行评估分享链路（短链/小程序码/
   URL Scheme）如何满足这个诉求。
2. **管理后台不建议做成小程序主战场。** overview.md 明确"桌面优先"，且涉及
   多字段表单录入、图片排序（后续 F-003）等复杂交互，小程序表单能力和文件
   操作能力弱于 Web 后台，做小程序会明显增加开发成本且体验更差。
3. **如果确有"管理员在手机上快速上/下架"的场景**，倾向于用响应式 Web 后台
   （管理后台移动端浏览器直接打开）覆盖，而不是专门再做一个小程序端。
   多一个端意味着多一套登录态、多一次小程序审核、多一份包体积预算，
   在"一百台以内车辆、无硬期限"的规模下投入产出比不高。
4. 若产品坚持要做小程序（无论前台还是管理端），我倾向于：
   - 登录态与业务账号解耦，微信 openid 只做"设备/身份识别层"，
     不作为管理员账号体系的唯一凭证（管理后台需要账号密码或至少双因素，
     不能仅凭微信授权就获得管理权限）；
   - 车辆列表、详情、图片、评估报告等按体积分包，首屏只加载列表骨架和
     首屏必要字段，图片走 CDN + 懒加载，不在主包内堆资源；
   - 评估报告（PDF 等）优先用 `wx.openDocument`/`wx.previewImage` 之类
     的原生能力预览，不引入重型 PDF 渲染组件占用包体积。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 全项目技术选型尚未定型，"是否做小程序"未经产品确认，本评审建立在假设之上 | brief.md、overview.md、principles.md 均未指定小程序作为交付载体；若最终确认不做小程序，本次评审的大部分风险条目不成立，但若确认要做，以下条目会成为真实阻塞项，需要在启动开发前定论，避免返工 |
| 高 | 二手车/车辆信息类目在微信小程序审核中可能被归为限制类目 | 若前台以小程序形式向访客展示车辆信息（尤其带价格、评估报告），微信可能将其归入"二手车交易"或"汽车服务"相关类目，要求提交企业资质（如二手车经营许可、汽车销售相关资质）。本项目明确不做交易/支付/下单，但"展示 + 价格"仍可能触发类目审核从严，需要提前确认主体资质，否则可能审核不通过导致整个前台无法上线 |
| 中 | 若管理后台做小程序，登录态与"无需他人审核、保存即可发布"的诉求存在天然张力 | 微信小程序的登录态（`wx.login` 换 openid/session_key）本身只解决"这是谁"，不解决"这个人有没有管理员权限"。需要明确：管理员账号体系是否独立于微信身份存在？如果管理员离职/换手机，openid 与账号如何解绑？这类问题如果留到开发中才发现，会返工登录模块 |
| 中 | 图片与评估报告是主要成本项，若小程序端参与图片管理（编辑上传者拖拽排序、图片说明），涉及相册权限、文件系统权限等隐私接口的多次授权弹窗，体验和审核都有额外成本 | `open-questions.md`（overview 待确认清单）提到"图片顺序……编辑上传者可以拖拽进行排序"，这类交互在小程序里比 Web 更难做（`movable-view` 实现拖拽排序体验有限），且批量选图/上传涉及 `chooseMedia` 权限弹窗，若管理员高频操作会造成明显打断感 |
| 低 | "移动端优先"可能被误读为"应该做成小程序" | `principles.md` 的"移动端优先"是针对手机竖屏浏览体验的设计取向，不等于必须选择小程序这个技术载体，H5 同样可以移动优先。评审时需要把"移动优先"（设计目标）和"是否小程序"（技术载体）分开讨论，避免团队内部因为这句话默认走上小程序技术路线 |

## 对其他端的隐含要求

- **服务端**：若前台或管理后台任一方采用小程序，服务端需要新增专门的
  微信侧接口（`code2Session` 换取 openid/unionid、可能的手机号一键登录
  `getPhoneNumber` 解密接口），且这套凭证体系要与现有"管理后台需登录、
  前台无需登录"的两级权限模型对齐——不能让 openid 直接等同于管理员权限，
  必须在服务端维护一张"openid → 管理员账号"的绑定表，且绑定/解绑动作
  只能由超级管理员或已登录的管理后台账号发起，不能由小程序端自助完成，
  否则会违反 `principles.md` 中"后台账号越权"的零容忍底线。
- **管理后台（若走小程序）**：F-006 后台账号管理目前是空白 brief，
  账号体系尚未定义。如果管理后台要接入小程序登录，F-006 必须先明确
  账号密码体系与微信身份的绑定关系、账号停用后 openid 侧如何同步失效，
  否则 F-001 里"管理员编辑/上下架"这类操作可能在账号被停用后仍可通过
  微信身份继续执行，形成权限漏洞。
- **前台（若走小程序）**：F-002 目前也是空白 brief。一旦确认前台走小程序，
  需要补充：分包策略（车辆列表/详情/图片/报告分包，避免主包超 2MB 限制）、
  图片列表的首屏加载策略（"每车最少 4 张、数量无上限"意味着列表页不能
  一次性加载全部图片，需要服务端配合返回缩略图字段）、是否需要小程序码
  分享单个车辆详情页给客户（涉及 `wx.getShareInfo`/`onShareAppMessage`
  及对应的服务端参数化路由支持）。这些都需要服务端在设计车辆详情接口时
  提前预留字段，否则后续补加会变成"前端加逻辑"，违背 `principles.md`
  "前端是哑终端"的取向。
- **图片与评估报告（F-003）**：如果上传环节（管理后台）或预览环节（前台）
  任一侧是小程序，都要提前确认文件格式支持范围——微信小程序对文件预览
  组件的格式支持有限（如 `wx.openDocument` 支持的格式列表是固定的），
  overview.md 待确认清单里"评估报告是 PDF、PNG、jpeg 文件直接展示"这条
  一旦坐实为小程序端展示，需要逐格式验证小程序原生能力是否覆盖，
  不能假设"网页能展示的小程序也能展示"。
- **对象存储/CDN**：`principles.md` 强调"图片是主要成本项，优先对象存储
  + CDN"。若小程序参与，域名需要在小程序后台配置 `downloadFile`/`request`
  合法域名白名单，涉及备案与 HTTPS 强制要求，需要在选型对象存储服务商时
  一并确认域名可备案、可加入小程序合法域名列表，否则上线前会被小程序
  域名校验卡住。

## 我需要别人回答的问题

1. 本项目的前台、管理后台，是否有任何一方计划以**微信小程序**形式交付？
   还是目前默认走 Web（H5 + 桌面网页）？这个决定会改变本次评审里所有
   风险条目是否成立，需要产品/技术负责人先给出结论。
2. 若前台走小程序：车辆展示是否会涉及价格公开展示（overview 待确认清单
   第 3 条"价格记录给访客看"）？这会影响是否触发微信"二手车交易"相关
   类目审核及资质要求，需要明确经营主体是否已具备可申请该类目的资质。
3. 若管理后台走小程序（或只是想要一个"手机上快速上下架"的轻量入口）：
   这个入口的账号体系打算独立于微信身份，还是允许管理员直接用企业微信/
   微信身份登录？F-006 后台账号管理的 brief 目前是空的，需要先补上再谈
   小程序登录方案。
4. 评估报告文件的格式范围是否已经定死为"PDF、PNG、jpeg"？如果后续要支持
   更多格式（如 Word、Excel），需要提前告知，因为这直接决定小程序端
   （如果有）能否用原生组件直接预览，还是要额外做文件转换服务。
5. "发链接给客户看"这个诉求里的"链接"，是否要求客户点开后**无需安装/
   打开微信**也能看（即纯 Web 链接）？如果是，前台基本可以排除小程序路线；
   如果客户本身就是通过微信触达（比如客服在微信里发链接），小程序路线
   仍然可行，但需要额外确认"分享出去的车辆详情页"这个跳转链路要怎么做。
