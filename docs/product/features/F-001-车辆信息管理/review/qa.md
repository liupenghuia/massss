## 我理解的需求

管理员在管理后台对车辆卡片做增删改与状态流转：新建（草稿/直接发布）、编辑、上架/下架/重新上架，全程无需审核。价格、图片评估报告、删除回收站、前台展示逻辑均不在本 feature 范围内，但状态机与发布动作会与它们产生依赖（发布前置校验依赖 F-003 图片数、F-004 价格）。

## 我的方案倾向

以状态机（草稿/已上架/已下架）为核心测试骨架，覆盖：三态间的合法转换、非法转换、幂等重复调用；发布前置条件的边界值（图片数=3/4、价格空/"面谈"/具体值）；编辑与状态转换解耦后的并发写（乐观锁）；创建接口的幂等键重复提交。

## 反对/风险
| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 发布前置条件的跨 feature 数据依赖难以独立测试 | 图片数量、价格是否已填依赖 F-003/F-004 的数据状态，F-001 的验收用例若不能 mock/伪造这两类依赖数据，发布校验将无法在 F-001 单独验收，需明确测试环境下如何构造前置数据 |
| 高 | 能源类型联动字段的校验规则未定义 | spec 只列了"选填、与能源类型联动"，未说明：选纯电时排量是否必须为空/禁止填写？后台是否强校验字段组合，还是仅前端隐藏？这是可测性缺口，不同实现会导致验收标准完全不同 |
| 中 | 编辑接口的乐观锁冲突（VEHICLE_VERSION_CONFLICT）触发条件和返回体格式未在 spec 描述，需要契约明确才能写自动化用例 |  |
| 中 | 必填字段的格式/范围校验未定义 | 里程、上牌年份、过户次数是否有上下界（如年份不能晚于当前年、里程非负、过户次数非负整数）？车况描述是否有长度上限？无这些边界会导致校验用例无法设计 |
| 中 | VIN 展示"只露后六位"但"不要求全局唯一"，两台车录入相同 VIN 是否允许保存，无报错提示要求，需明确是否需要给出提示（非阻断） |  |
| 低 | 草稿保存时哪些字段可以为空未明确（必填字段是否在"保存草稿"时也强制校验，还是只在发布时校验） | 若草稿阶段也强制必填字段非空，则"暂不发布"的价值会打折，需要确认 |

## 对其他端的隐含要求
- 服务端：需提供可在测试环境下直接设置/伪造 F-003 图片数量、F-004 价格状态的手段（测试夹具或接口），否则发布前置校验无法独立验收。
- 服务端：乐观锁冲突与幂等键重复提交需返回可断言的稳定错误码/字段，供自动化用例识别。
- 管理后台：非法状态转换、发布前置条件缺失时的错误提示需可被 UI 自动化测试定位（如稳定的 data-testid 或错误信息结构化）。

## 我需要别人回答的问题
1. 能源类型与排量/电耗/电池度数的联动，是否要求服务端强校验字段组合（如纯电禁止填排量），还是仅作前端展示提示？
2. 里程、上牌年份、过户次数（手数）是否有取值范围或格式限制（如年份区间、里程非负）？
3. 草稿保存时，"必填"字段（品牌/车型/年份等）是否也强制非空，还是仅发布时才校验？
4. 测试/联调环境下，F-001 的发布前置校验用例如何独立构造 F-003 图片数量与 F-004 价格数据（是否提供测试夹具或允许直接写库）？
