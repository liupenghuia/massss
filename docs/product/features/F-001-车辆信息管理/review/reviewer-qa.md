## 我理解的需求

管理员在管理后台维护「车辆卡片」的基础信息：
- 新建车辆：可保存为「草稿」（不对前台可见），也可直接「发布/上架」
- 编辑已有车辆的基础信息
- 对已上架车辆执行「下架」，对已下架车辆执行「重新上架」
- 整个过程无需他人审核，管理员一人可完成创建到发布的全流程

明确排除：价格与价格历史（F-004）、删除/回收站/恢复（F-005）、图片与评估报告（F-003）、前台展示逻辑（F-002）。

本需求目前只给出了状态动作（草稿/发布/下架/重新上架）和成功标准，**没有给出车辆卡片的具体字段清单、字段校验规则、状态之间的转换矩阵、以及管理员权限模型**，这些是本次评审的主要缺口，直接影响验收标准能否落地为自动化用例。

## 我的方案倾向

- 在需求细化阶段，先补齐「状态转换矩阵」（草稿/已上架/已下架三态之间，哪些动作合法、哪些非法，例如"草稿能否直接下架"这种非法操作应返回什么错误）——这是自动化用例设计的前提，不补齐无法开始写测试。
- 字段校验规则建议以「服务端强校验、前端仅做体验层校验」的方式落地，与 principles.md「内容准确 > 功能丰富、有疑问时砍功能不砍校验」的取向一致；测试重点放在服务端边界值与非法输入上，而非前端交互细节。
- 建议 F-001 的验收标准最终以"状态 + 字段"两张表的形式呈现（状态转换合法性表 + 字段校验规则表），这样才能一一映射为测试用例，而不是停留在当前"能新建/能编辑/能上下架"这种流程性描述。
- 权限模型（如果存在"低权限管理员"）应作为本 feature 的显式验收项，而不是留到实现阶段临时决定，因为这直接对应 principles.md 的零容忍项。

## 反对/风险
| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 车辆卡片字段清单缺失 | brief 只说"车辆基础信息（车辆卡片核心字段）"，未列出具体字段（如品牌、车型、年份、里程、车架号/VIN、车牌等）及其类型、是否必填、格式校验、是否唯一。没有字段清单就无法写字段级校验用例，也无法判断哪些是边界条件（如里程为负数、年份超出合理范围、必填字段为空）。 |
| 高 | 状态转换矩阵未定义 | 只列出"草稿→发布""已上架→已下架""已下架→重新上架"，但没说明：编辑已上架车辆是否需要重新走一次发布确认？编辑会不会导致车辆被隐式下架？草稿状态下能否被"下架"（应报错还是无操作）？这些非法路径不测会成为线上事故来源。 |
| 高 | 发布前置条件未定义 | F-003（图片/评估报告）明确排除在本 feature 之外，但发布动作是否要求"至少有 N 张图片"作为前置条件未说明。若允许无图车辆发布上架，与 principles.md「内容准确 > 功能丰富」的取向可能冲突，需要业务明确。 |
| 高 | 权限模型与 principles.md 冲突信号 | brief 说"全程不需要他人审核"，暗示单一角色即可完成全流程；但 principles.md 把"后台账号越权（低权限账号能改不该改的东西）"列为零容忍质量底线，暗示可能存在多角色/多权限管理员。两处信息不一致，需澄清本 feature 内是否存在权限分级，否则"越权"这条零容忍在 F-001 无法测试。 |
| 中 | 价格字段归属不清 | 价格调整/价格记录归 F-004，但车辆卡片本身（F-001）是否含有一个初始价格字段未说明。如果 F-001 完全不含价格字段，会出现"车辆已发布上架但没有价格"的业务场景，是否允许需要确认，否则无法判断这是正常流程还是缺陷。 |
| 中 | 草稿态没有清除/纠错手段 | 删除功能归属 F-005（未上线），若管理员误建草稿或想放弃某条草稿数据，当前流程没有出口（只能靠 F-005 上线后处理）。这是否是有意为之的中间态设计，需要业务确认，否则测试时会把"无法删除草稿"误判为缺陷。 |
| 中 | 缺少操作留痕（创建人/编辑人/时间）要求 | brief 未提及是否需要记录谁在何时创建/编辑/上下架，若后续要追责或做审计，属于遗漏；即便本期不做，也建议显式写入"明确不做"清单，避免验收阶段产生分歧。 |
| 低 | 并发编辑无约束 | 未说明多个管理员是否可能同时编辑同一车辆、是否需要乐观锁/版本号防止覆盖写。车辆数量级"一百台以内"、无硬期限，短期风险不高，但建议在 open-questions 里记录以免遗漏。 |

## 对其他端的隐含要求

- **对 F-002（前台展示）**：前台是"哑终端"（principles.md），只能展示后台数据决定的内容，因此 F-001 必须在 contracts/ 中明确暴露一个「车辆状态」字段（如 published/unpublished/draft），且该字段的取值与语义必须与前台"只展示已上架车辆"的过滤逻辑完全对齐。F-001 的"下架"动作生效后，前台何时能感知（实时查询 vs 有缓存/CDN 延迟）需要在契约里写清楚，否则"已下架车辆仍在前台可见"会直接踩中 principles.md 的零容忍红线，但这条红线的责任边界（F-001 保证状态落库 vs F-002 保证及时拉取）目前没有划分。
- **对 F-003（图片与评估报告）**：F-003 需要关联到一个稳定的车辆标识（车辆 ID/主键），因此 F-001 必须先于或至少同步给出车辆记录的唯一标识，且该标识在编辑过程中不能变化（否则图片关联会错位，触碰 principles.md"图片与车辆错配"这条零容忍项）。此外，若发布动作要校验图片数量前置条件（见风险表），F-001 与 F-003 之间存在校验时序依赖，需要双方在契约里明确谁做这个校验。
- **对 F-004（价格记录）**：需要明确车辆卡片是否含"当前价格"字段、该字段的读写权归属谁（F-001 只读展示、F-004 独占写入？还是 F-001 在创建时写入首次价格、后续变更走 F-004？）。这个边界不清，F-004 的"价格历史"起点就无法定义（第一条历史记录从哪来）。
- **对 F-005（回收站）**：F-001 设计状态枚举（草稿/已上架/已下架）时应为未来的"已删除/回收站中"状态预留扩展空间，避免 F-005 落地时需要对已有状态字段做破坏性变更（如枚举值语义冲突、状态机需要重新设计）。
- **对 contracts/（接口契约）**：车辆状态枚举、车辆唯一标识、字段清单一旦确定即成为跨 F-002/F-003/F-004/F-005 的共享事实来源，建议本 feature 的裁决结果直接落到 contracts/，而不是散落在各 feature 的 brief 里，减少后续多端口径不一致的风险。

## 我需要别人回答的问题

1. 车辆卡片的具体字段清单是什么？每个字段是否必填、类型、格式校验规则（例如车架号/VIN 是否要求全局唯一）？
2. 状态转换矩阵：草稿能否被"下架"？已上架车辆编辑后是否自动变为草稿或保持上架？非法状态转换（如对草稿执行"重新上架"）应返回什么结果？
3. 发布（上架）动作是否有前置条件，例如是否要求至少已有 N 张图片才允许发布？还是允许"裸车卡"先上架、图片后补？
4. 车辆卡片本身是否包含价格字段？如果有，创建时填写的价格与 F-004 的价格历史是什么关系（是否算作第一条历史记录）？
5. "全程不需要他人审核"是否意味着 F-001 范围内所有管理员权限完全相同（无角色分级）？principles.md 提到"低权限账号越权"的零容忍项在本 feature 是否适用，还是该项只针对其他 feature？
6. 草稿数据在 F-005（回收站/删除）上线之前，管理员是否有任何手段清除/作废误建的草稿？如果没有，这是否是本期可接受的已知限制？
7. 是否需要记录车辆记录的创建人/编辑人/操作时间？如果本期不做，是否需要显式写入 brief 的"明确不做"清单？
8. 车辆的唯一标识（ID）生成规则和稳定性要求是什么？编辑过程中是否可能变化（直接影响 F-003 图片关联的正确性）？
9. "下架"后车辆在前台不可见这一约束，生效延迟允许多大（实时 vs 有缓存），由 F-001 服务端保证还是由 F-002 前台拉取策略保证？
10. 是否存在多个管理员同时编辑同一辆车的并发场景？如果存在，是否需要版本号/乐观锁防止覆盖写？
