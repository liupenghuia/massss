## 我理解的需求

管理员通过管理后台对车辆卡片（车辆基础信息，不含价格、图片、评估报告，这些分别归 F-004、F-003）进行全生命周期的录入与状态维护：

- 新建车辆：可保存为草稿（不发布），也可直接发布上架，二选一，无审核环节。
- 编辑已有车辆：草稿态、已上架、已下架的车辆均可编辑（brief 未明确区分，按字面理解为都能编辑）。
- 状态流转：管理员可对已上架车辆执行下架，对已下架车辆执行重新上架。
- 全程单人操作即可完成，无需二级审核（即没有"提交待审 → 他人审核通过"的流程）。
- 明确排除：价格、删除/回收站、图片与评估报告、前台展示逻辑，均由其他 feature 承接。

brief 目前只描述了"单个车辆的增删改状态动作"，完全没有描述**管理后台列表页**（筛选、搜索、排序、批量操作、导出）以及**谁能做这些操作（权限/角色）**、**操作留痕（审计日志）**，这三块是我作为管理后台评审最关心、也是当前信息缺口最大的部分。

## 我的方案倾向

- 状态机采用三态：`草稿(draft)` → `已上架(published)` ⇄ `已下架(unpanel published)`，新建时二选一入口（存草稿 / 直接发布），草稿可编辑后发布，已上架/已下架均可编辑（编辑不改变状态，除非管理员显式点击上/下架按钮）。
- 车辆列表页至少支持按状态（草稿/已上架/已下架）筛选 + 关键字搜索（建议按车辆唯一编号或车型名称），这是运营日常找车的最基本操作，即使 brief 没提，我倾向于把它当作本 feature 的隐含最小可用范围，而不是留到后续迭代——否则车辆一多（哪怕上限 100 台）列表页就没法用。
- 权限先按"单一管理员角色，全权限"实现，不做多级角色区分，因为 brief 通篇只提到"管理员"一个角色，且强调"全程不需要他人审核"。但这个假设必须让用户显式确认，因为一旦以后要加"运营只能编辑不能发布"这类角色，数据模型和接口鉴权层最好一开始就留好角色字段，不然是破坏性改造。
- 操作日志（谁在什么时间对哪辆车做了什么状态变更）建议做成本 feature 的最小内置能力，而不是等 F-004/F-005 之类的 feature 来补——因为状态变更（尤其是下架/重新上架）本身就是本 feature 的核心动作，不属于价格或回收站范畴，没有地方能"顺带"补上这个日志。
- 批量操作（批量上架/下架）在车辆数量级只有 100 台以内的前提下，优先级不高，倾向于第一版不做，留到有实际运营痛点再加，避免过度设计。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 状态变更无审计日志 | brief 完全没提操作记录。principles.md 把"后台账号越权"列为零容忍项，但如果连"谁下架了这辆车、什么时候上架的"都查不到，越权发生了也无法追溯、无法举证，等于零容忍条款没有落地抓手。 |
| 高 | 权限模型未定义 | brief 全程只提"管理员"一个角色，没说是否所有登录管理后台的账号权限完全相同，还是有更细的角色划分（比如只读、只能编辑不能发布）。这个不定下来，鉴权代码没法写，且后续加角色是破坏性变更。 |
| 中 | 列表页筛选/搜索完全未定义 | 没有列表页规格，运营无法在后台批量浏览、按状态找车、按编号找车。100 台以内规模下靠"一页翻到底"勉强能用，但用户体验会很差，且这是管理后台最高频的操作路径，比新建/编辑还高频。 |
| 中 | 车辆"核心字段"未列出 | brief 只说"车辆基础信息（车辆卡片核心字段）"，没有列出具体字段清单（车架号/VIN、车型、年份、里程、颜色等）。表单校验规则、必填项、发布前置条件都依赖这份清单，目前完全空白。 |
| 中 | 草稿/已上架/已下架之间的编辑规则不清楚 | 编辑已上架车辆是立即生效，还是需要重新走一次"发布"确认？编辑已下架车辆会不会附带把状态改回上架？这类细节决定表单交互和后端状态机实现，需要明确。 |
| 低 | 无导出能力 | principles.md 明确"不做数据看板/统计报表"，但导出车辆清单（给运营做 Excel 台账）和"报表"不是一回事，需要确认是否需要导出，否则运营可能会临时找开发要数据。 |
| 低 | 唯一标识字段未定 | 没有说明车辆用什么字段判重/查找（车架号 VIN？内部编号？），影响新建时是否要校验重复。 |

## 对其他端的隐含要求

- **对前台（F-002）**：管理后台的"下架"操作必须让前台立即不可见，不能有缓存延迟或异步同步窗口——这属于 principles.md 零容忍条款"已删除车辆仍在前端可见"的近亲风险（下架车辆理应享受同等严格度）。这要求服务端提供的公开查询接口必须严格按 `status = published` 过滤，且后台状态变更要同步生效，不能走定时任务批量刷新这种有延迟的方案。
- **对服务端**：车辆表需要一个 `status` 字段（draft/published/unpublished）供前台过滤和后台管理共用，前台接口与后台接口对同一份数据做不同视图裁剪，这与 principles.md"服务端合一、用路由前缀区分 `/public/*` 与 `/admin/*`"的技术偏好一致，但需要明确后台列表接口要支持按 status 筛选查询（这是本评审提出的隐含需求，不是 brief 里写的）。
- **对 F-003（图片与评估报告）**：车辆"发布上架"这个动作，是否要求已经上传了图片（principles.md 强调"每车最少 4 张"图片）？如果发布时没有图片校验，前台会展示一辆没有图的车，这属于内容不准确的范畴（principles.md："内容准确 > 功能丰富"）。这个校验逻辑该放在 F-001 的发布动作里，还是放在 F-003，需要两个 feature 提前对齐，否则容易出现互相以为对方做了校验的缺口。
- **对 F-004（价格记录）**：新建车辆发布上架时，是否要求价格已经录入？如果 F-001 允许"没有价格也能发布"，前台会展示一辆无价车，同样触及 principles.md 的"内容准确"红线。需要 F-001 与 F-004 明确谁负责这道校验，或者在 F-001 的发布逻辑里显式检查价格是否存在。
- **对 F-005（回收站）**：F-001 明确"不做删除"，意味着下架车辆会一直留在管理后台列表里（不会被物理或逻辑删除），列表数据只增不减。这要求管理后台列表页必须有筛选能力才能保持可用，否则运营会在几十上百条已下架车辆里迷失——这进一步印证了本评审"反对/风险"里提到的"列表页筛选缺失"是高优先级缺口，而不是可以推给未来迭代的东西。

## 我需要别人回答的问题

1. 管理后台账号是否只有一种角色（全权限管理员），还是存在不同权限层级（例如只读账号、只能编辑不能发布的账号）？这决定鉴权模型要不要一开始就设计角色字段。
2. 状态变更（新建、编辑、上架、下架、重新上架）是否需要记录操作日志（操作人、操作时间、变更前后的状态/字段）？如果需要，日志要不要在管理后台里可查看，还是只落库不展示？
3. 车辆卡片的"核心字段"具体包含哪些？请给出字段清单（哪些必填、哪些选填），这直接决定表单和校验规则。
4. 车辆是否有唯一标识字段（如车架号/VIN、内部编号）？新建时是否要校验查重？
5. 编辑已上架车辆的信息，是立即生效展示到前台，还是需要重新确认/重新发布？编辑已下架车辆，是否会连带把状态改回上架，还是状态与内容编辑完全独立？
6. 管理后台列表页是否需要按状态、关键字（车型/编号）筛选和搜索？这是否属于 F-001 范围，还是打算放到别的 feature？
7. 是否需要导出车辆清单（如 Excel）？如果需要，导出哪些字段、是否受权限/筛选条件限制？
8. 发布上架时，是否要求车辆已经有图片（F-003）和价格（F-004）？这道校验放在 F-001 的"发布"动作里，还是由 F-003/F-004 各自负责？
9. 车辆数量级"一百台以内"是当前规模还是长期上限？如果未来会突破，列表页分页/批量操作的优先级需要重新评估。
