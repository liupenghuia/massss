## 我理解的需求

管理员在管理后台维护「车辆」这一核心实体：新建（存草稿或直接发布）、编辑、上架/下架。
车辆卡片是核心字段集合（品牌、车型、里程、颜色、能源类型等 + VIN），价格、图片、评估报告、删除/回收站均由其他 feature（F-003/F-004/F-005）承载，
本 feature 只负责车辆基础信息本体与三态状态机（草稿/已上架/已下架）。当前 spec.md（v1.4, agreed）已就实体主键、状态机、发布前置条件、乐观锁给出明确裁决，本评审在此基础上核对是否有遗漏的领域风险。

## 我的方案倾向

- 车辆以系统自动生成的技术主键为跨 feature 关联锚点（已在 spec 中裁决），VIN 仅作展示/后台录入字段、不做唯一性约束，这个选择是对的——避免把外部标识符当聚合根标识符，符合"内容准确优先"但不为难以验证的外部数据强加唯一性。
- 状态机三态、单向转换（无 已下架→草稿）、编辑与状态转换解耦，这个设计自洽，没有死状态：草稿可发布，已上架/已下架互转，非法转换报错、同态重复调用幂等，覆盖完整。
- 发布前置条件（图片≥4、价格非空）依赖 F-003/F-004 的数据，属于跨聚合的一致性校验，建议在校验失败时明确指出"缺失项来自哪个模块"，避免管理员误以为是本模块的字段问题。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 中 | 已上架车辆的"发布前置条件"仅在发布/重新上架动作时校验一次，之后若通过 F-003/F-004 把图片删到 4 张以下或清空价格，已上架状态不会被联动降级或校验 | spec 明确"编辑操作与状态转换解耦"，这本身合理，但需要确认：已上架车辆的图片/价格被其他 feature 改到不满足前置条件时，是维持已上架不动（当前隐含选择），还是需要某种兜底提示。若维持不动，属于已知的最终一致性缺口，建议在 spec 里补一句明确这是有意选择，而不是遗漏 |
| 中 | "车况描述"（F-001 必填字段）与 overview.md 术语表中的"车辆描述"（挂在整台车上的详细说明）是否为同一字段未在 spec 明确 | 若是两个不同字段，spec 核心字段清单里应同时出现两者并区分用途；若是同一字段的两种叫法，需要统一命名，防止实现时长出两个语义重叠的字段 |
| 低 | "过户次数（手数）"未定义计数起点（新车=0手还是1手） | 属于字段级枚举/取值口径问题，不影响状态机与聚合边界，建议随字段实现时以一行 ADR 或 spec 备注确认，不必升级为跨端评审 |

## 对其他端的隐含要求

**服务端**：发布前置校验需要跨模块读取 F-003 图片计数和 F-004 当前价格，这是一次跨聚合读，若图片/价格所在表与车辆表分离，需保证读到的是同一事务快照内的最新值，避免校验通过后瞬间又被并发改动破坏前置条件。

**F-003（图片）**：图片删除到低于4张时，不需要（也不应该）反向调用 F-001 把已上架车辆自动下架，这属于本 feature 已确认的最终一致性缺口，F-003 侧不用为此做额外联动。

**F-004（价格）**：价格清空/置空操作不需要触发车辆状态变更，F-001 的发布前置条件只在发布动作那一刻校验，F-004 侧无需感知车辆当前状态。
