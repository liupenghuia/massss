## 我理解的需求

管理后台是车辆数据唯一入口：新建/编辑车辆卡片（品牌、车型、年份、里程、颜色、车况描述、能源类型、手数等必填字段，及排量/电耗/电池度数联动选填字段，VIN 后台专用字段），管理草稿/已上架/已下架三态流转（发布、下架、重新上架），列表页按状态筛选、按关键字搜索，不做导出、不含价格字段（归 F-004）。发布时校验图片≥4张与价格非空（依赖 F-003/F-004 数据）。只有一种管理员角色（无只读/审核账号），无需审批。操作日志只落库不做查看页面。

## 我的方案倾向

- 列表页：状态筛选（草稿/已上架/已下架）+ 关键字搜索（品牌/车型/VIN 后六位）放在同一信息层级，符合 overview 里"列表搜索+筛选同一信息层级"的手机端约束。
- 编辑页：能源类型切换时联动显隐排量/电耗/电池度数字段，不做成三套独立表单，减少维护成本。
- 发布/下架/重新上架做成列表行内操作 + 详情页顶部操作按钮两处入口，就近原则；非法状态转换按钮直接禁用（而非点击后报错），减少无效请求。
- 发布前置条件不满足时，错误提示需列出具体缺失项（"图片不足4张"/"价格未填写"），不能只提示"发布失败"。
- 乐观锁冲突（VEHICLE_VERSION_CONFLICT）在编辑保存时用明确提示引导用户刷新重取最新数据，不做静默覆盖。

## 反对/风险
| 严重度 | 问题 | 说明 |
|---|---|---|
| 中 | 操作日志无查看页面 | spec 明确"只落库不做查看页面"，管理后台无处排查"谁在什么时候改了这辆车"，出问题只能查库。当前定位为已知限制，不算缺陷，但要在本文档记录，避免后续被当作遗漏。 |
| 中 | 草稿堆积无清理入口 | spec 已知限制：F-005 上线前草稿无法清除/作废。管理后台列表如果不做默认过滤，草稿会一直混在列表里，运营体感变差。需要列表默认视图或排序上做一点缓解（见问题1）。 |
| 低 | VIN 展示后六位口径 | spec 写"车架号仅后台展示后六位"，需要确认这是列表页也如此还是仅详情页如此，列表页如果要支持按 VIN 搜索，搜索框输入完整还是后六位需明确（见问题2）。 |
| 低 | 单一管理员角色下的误操作风险 | 无审核、无只读账号，任何登录账号可直接发布/下架/编辑任何车辆，符合已确认设计，但意味着管理后台在关键操作（下架、发布）上应有二次确认弹窗防误触，这是可带上线范围内的体验优化，非必须裁决项，此处仅记录不列入待裁决。 |

## 对其他端的隐含要求

**服务端**：列表接口需支持 status 筛选与关键字搜索（品牌/车型/VIN），返回值需包含足够字段供列表展示与筛选，无需额外接口约定。
**前台**：无隐含要求，管理后台改动不影响前台展示逻辑。

## 我需要别人回答的问题

1. 草稿在管理后台列表里默认是否要与已上架/已下架分开展示（如默认筛选到"全部"还是默认排除草稿），还是完全交给筛选器由用户自行选择？
2. 车辆列表页的关键字搜索框，对 VIN 是按完整车架号匹配还是按展示的后六位匹配？
