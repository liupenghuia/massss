## 我理解的需求

两级扁平账号体系（`admin` / `super_admin`），无审批流、无自定义权限矩阵。核心实体是
`Account`（登录名、密码、角色、启用状态）与其派生的 `Session`（服务端会话，可吊销）。
账号生命周期只有「启用 ⇄ 停用」两态转移，不做物理删除；登录名永久唯一占用。业务能力
（车辆/价格/图片/回收站）两级角色完全相同，权限差仅体现在"能否管账号"。操作日志与价格
记录的"操作人"要落库为账号稳定 ID，与账号本身生命周期解耦。

当前 spec.md（v1.2）与已 Accepted 的 RFC 已经把大部分状态机与边界细节实体化（含
`mustChangePassword` 标志、末位超管保护、会话吊销时机），本评审基于 brief 的建模意图，
核对现有状态机是否自洽、有无遗留死角。

## 我的方案倾向

- 保持 `role`、`enabled` 两个正交维度是对的，但建议把 `mustChangePassword` 也作为账号的
  第三个显式状态位写进 spec 的"状态机"章节（目前只在"各端职责"散落描述），否则后续改动
  （如新增找回密码方式）容易漏掉它的转移规则。
- 账号的唯一性约束（登录名永久占用、不可删除）本质上是把"账号"建模成仅追加
  （append-only）的资源，这与操作日志/价格记录要引用稳定 ID 的诉求一致，不需要改。

## 反对/风险
| 严重度 | 问题 | 说明 |
|---|---|---|
| 中 | `mustChangePassword` 未进入状态机表格 | spec.md「状态机」一节只列 role/enabled 两个维度，`mustChangePassword` 只在"各端职责"和 RFC 里出现，导致停用/启用/重置密码对这个标志的转移关系没有集中定义的地方，后续改动容易遗漏（例如"启用一个之前被停用的账号"是否要重新置位）。 |
| 中 | 重新启用（disabled→active）后 `mustChangePassword` 取值未定义 | spec 只定义了"新建"和"重置密码"会置 `mustChangePassword=true`，没说"停用中的账号被重新启用"要不要强制改密。若账号停用期间密码疑似泄露，仅"重新启用"不强制改密，等于绕开了强制改密这道口子。 |
| 低 | 自我降级路径未在权限矩阵中显式排除 | 矩阵写明"不能停用自己"，但未写"能否把自己从 super_admin 降级为 admin"。若允许且当前不是最后一个超管，操作后该账号立即失去管账号能力，属于自证降权，逻辑上不违反不变量，但矩阵没写清楚会被当成遗漏来回问。 |

## 对其他端的隐含要求

**服务端**：需要把"停用→启用"这条转移是否重置 `mustChangePassword` 的规则明确写进账号状态转移逻辑，不能只靠"新建/重置密码"两个入口兜底。

**管理后台**：账号列表的状态标签应能反映 `mustChangePassword` 悬而未决的账号（例如"待完成首次改密"），否则超管无法从列表判断某账号是否仍卡在强制改密页面。

**前台**：无隐含要求，前台不接触账号体系。

## 我需要别人回答的问题

1. 账号从 `disabled` 重新 `active` 后，`mustChangePassword` 是否也要强制置为 `true`（等同一次密码重置）？
2. 超级管理员是否允许把自己降级为 `admin`（在非最后一个超管的前提下），还是应和"停用自己"一样禁止？
