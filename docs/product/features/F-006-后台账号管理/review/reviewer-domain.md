## 我理解的需求

本 feature 只收口**管理后台账号生命周期与两级角色**，不引入字段级分权、审批流、前台用户。

核心实体是**后台账号（AdminAccount）**。每个账号有且仅有一个角色：`管理员` 或 `超级管理员`。两级角色在车辆/图片/价格/回收站上的业务能力相同；权限差只在「能否生成、分配、停用管理员账号」。

账号至少有业务状态：`可用`（可登录、可改数据）、`停用`（立即不可登录、不可再改数据）。brief 未给出启用/删除/改密等其它终态。

一致性边界：鉴权是服务端对 `/admin/*` 的强制门禁。停用必须让后续写操作失败，不能只挡登录页。登录成功后的身份是 F-001/F-003/F-004 操作日志与价格记录「操作人」的稳定标识。

## 我的方案倾向

把账号作为独立聚合根：身份（稳定 ID）、角色、凭证、状态。角色用枚举两值。停用是状态转移，不是物理删除，以便历史「操作人」仍能指向同一账号。会话/令牌必须随停用失效。操作人落库用账号稳定 ID。

## 反对/风险
| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 「生成」与「分配」未建模 | brief 并列两个动作，未说明是一次创建还是两步。边界不清会导致谁拥有凭证、何时可登录出现歧义。 |
| 高 | 停用后无出口，可能成死状态 | 只写停用，未写能否重新启用、能否物理删除。 |
| 高 | 「立即不能再改数据」的一致性未定义 | 已持有登录态的请求、进行中的写事务、多标签页，是否全部在停用提交成功后立刻失败，未规定。 |
| 中 | 超级管理员自身生命周期空白 | 超级管理员如何产生、能否有多个、能否停用彼此/自己、最后一个被停用后系统是否锁死，均未写。 |
| 中 | 操作人标识不稳定风险 | 若用登录名而非稳定 ID，改名/再分配后历史日志与价格记录会串人。 |
| 中 | 管理员自操作未覆盖 | 能否改自己的凭证、能否停用自己、列表能否看见其他账号，未定义。 |

## 对其他端的隐含要求

- **服务端**：所有 `/admin/*` 必须校验登录态 + 账号未停用；账号管理类接口必须再校验超级管理员角色。
- **管理后台**：未登录不得进入后台页；角色只展示服务端返回的能力。停用成功后，被停用者已打开的后台必须在下一次请求失败时退出。
- **前台**：零账号、零登录；不得复用后台会话。
- **F-001 / F-003 / F-004**：写操作必须带当前登录账号身份；停用账号不得再产生新变更；历史记录保留原操作人。
- **路由**：账号生命周期接口只能挂在 `/admin/*` 且仅超级管理员可写账号。

## 我需要别人回答的问题

1. 「生成」和「分配」是两个独立动作还是一次创建？凭证如何交给对方？
2. 停用后能否重新启用？账号能否删除？删除后历史操作人如何显示？
3. 超级管理员如何初始化？是否允许多个？超级管理员能否被停用（含自己）？只剩一个时如何约束？
4. 「立即」停用是否包含作废已有会话、打断进行中的写请求？允许的最大失效窗口是多少？
5. 「操作人」落库字段是账号稳定 ID、登录名，还是 ID + 当时显示名快照？登录名能否变更？
6. 管理员能否查看账号列表、修改自己的密码？超级管理员能否重置管理员密码？
7. 登录凭证形态是什么？失败锁定、过期、强制改密是否本期范围？
8. 角色能否升降级，还是创建后不可变？
