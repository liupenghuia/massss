## 我理解的需求

管理后台采用两级账号（管理员/超级管理员），业务权限完全相同，权限差只在账号生命周期管理
（建号/停用/启用/改角色/重置密码）。会话服务端存储、可吊销，8 小时滑动过期，未登录 401、
权限不足或已停用 403。密码策略、登录失败锁定、最后一个超管保护、登录名永久占用不可复用、
操作人字段落库稳定 ID 均已在 spec 中明确。本次评审对象是 brief 描述的成功标准与边界，spec
已比 brief 细化（含状态机、错误码），以 spec 现状为准核对可测性。

## 我的方案倾向

按 spec 已定义的错误码（FORBIDDEN/MUST_CHANGE_PASSWORD/INVALID_CREDENTIALS/ACCOUNT_DISABLED/
ACCOUNT_LOCKED/ACCOUNT_LOGIN_NAME_TAKEN/CANNOT_DISABLE_SELF/LAST_SUPER_ADMIN）逐一设计正例+
反例用例；状态机测试覆盖"角色×启用状态"四种组合下各操作的准入结果；会话失效相关用例需覆盖
"停用后已发出的会话立即失效"这一强时效要求，用自动化验证而非人工观察。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | "停用/改密后作废该账号全部现有会话"的时效未量化 | spec 说"立即"，但会话是否轮询校验、多实例部署下失效延迟多久没写，验收标准无法定具体阈值（如"停用后 N 秒内失效"），影响自动化用例的等待/超时设置 |
| 高 | 锁定窗口与限流的交互未定义 | 连续 5 次失败锁 15 分钟，同时登录接口有 IP 级限流，两者触发顺序/优先级未说明（先返回 ACCOUNT_LOCKED 还是限流错误），影响用例断言哪个错误码 |
| 中 | 建号/重置密码"不支持幂等重放"的边界未覆盖 | spec 说网络超时靠"再次调用重置补救"，但再次调用是否会使前一个未过期的初始口令失效（导致同事之前收到的口令作废却不自知）没写清，需要明确以设计可测用例 |
| 中 | 密码策略只给下限（8 位含字母数字），未给上限与允许字符集 | 边界用例（如 100 位密码、含空格/特殊符号、含 emoji）无规则可依，可能导致注入或截断类问题未被覆盖 |
| 中 | "最后一个 active 超管不能停用/降级"未覆盖并发场景 | 两个超管同时对彼此发起停用/降级请求时，谁先到谁后到决定是否触发保护，是否有事务锁未说明，可能出现两个都成功导致 0 个超管 |
| 中 | 首次强制改密"改密前无法使用其他功能"未定义改密页本身以外的可达路径 | 是否允许在改密前登出、切换账号、查看只读信息（如自己的登录名）没写，验收用例无法穷举"其他功能"边界 |
| 低 | 登录失败锁定 15 分钟是否可被超管手动解锁未说明 | spec 只说停用/启用是显式操作，锁定是否等价于自动 disabled 或独立状态未定义，影响"锁定中能否被停用"这类交叉用例 |

## 对其他端的隐含要求

- 服务端：需提供确定性的"会话失效生效时间"行为（如每次请求强校验 DB 状态，不做本地缓存），否则该端的自动化用例无法稳定断言"立即失效"。
- 管理后台：新建账号/重置密码的"口令展示一次"页面需保证刷新或路由跳转后不可再取，否则安全用例无法验证口令不留痕。
- 管理后台：错误码到文案的映射需与 spec 列出的 8 个错误码一一对应，不能笼统展示"操作失败"，否则黑盒用例无法按错误码断言界面表现。

## 我需要别人回答的问题

- 停用/改密后会话失效的最大允许延迟是多少（用于定自动化用例的断言超时）？
- 登录锁定（15 分钟）与登录接口 IP 限流同时触发时，返回哪个错误码，是否有优先级？
- 建号/重置密码超时后再次调用，是否会使前一次生成的口令立即失效？
