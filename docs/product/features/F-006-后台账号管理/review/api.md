## 我理解的需求

管理后台需要一套双角色（admin / super_admin）的账号与会话体系：会话存服务端可吊销、8 小时滑动过期；
账号仅"启用/停用"两态，不做物理删除、不做字段级分权；账号生命周期写操作（建号/停用/启用/重置密码/
改角色）仅超级管理员可做，且系统禁止最后一个启用的超管被停用或降级；登录失败计数锁定 15 分钟；
建号/重置密码返回一次性明文口令，不支持幂等重放。spec v1.2 已定稿并落地契约（RFC Accepted），
本次评审确认落地方案在并发/幂等/数据量/迁移维度是否有遗留风险。

## 我的方案倾向

- 会话表：`session_id`(主键) / `account_id` / `expires_at` / `revoked_at`，按 `account_id` 建索引以支持
  "停用/改密时批量吊销该账号全部会话"；每次 `/admin/*` 请求按 `session_id` 单行查询，账号量级下（个位数到
  几十个后台账号）此设计无性能问题，不需要额外缓存层。
- "最后一个启用超管"的校验（禁止停用/降级）与登录失败计数器，都必须落在同一事务里做"先加锁读、再判断、
  再写"，不能读时判断、写时才发现冲突，否则存在并发窗口。
- 登录失败次数与锁定判断建议用数据库原子操作（`UPDATE ... SET fail_count = fail_count + 1 WHERE ...`
  配合唯一账号行锁），不要"读出计数、内存 +1、再写回"，避免并发登录失败时计数丢失导致锁定失效。
- 重置密码/建号返回的一次性口令展示一次即不再可查，属于已知的不可幂等操作（spec 已写明），实现上仍需
  保证：即使前端展示失败（网络抖动），后端也已完整落库新口令的 hash，不能出现"生成了口令但只有一半写入
  成功"的中间态——这类写操作必须整体在一个事务内完成（生成口令 hash + 强制改密标记 + 会话作废）。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 「最后一个启用超管」校验存在竞态 | 若两个超管几乎同时分别停用/降级另外两个不同的超管账号，且当前只剩两个启用超管，两次请求各自读到"还有 ≥2 个启用超管"从而都通过校验，结果导致启用超管数变为 0。必须用行级锁或数据库唯一约束/触发器兜底，不能仅在应用层用"先查询计数再写"的方式判断。 |
| 中 | 登录失败计数与解锁窗口无显式清理策略 | spec 未说明失败计数/锁定记录的过期清理方式（TTL 字段？定时任务？），账号量小可以不做也不会有数据量问题，但需在实现时明确"计数器复位靠成功登录清零"是唯一复位路径，避免遗留脏计数长期占位。 |
| 中 | 会话吊销的实时性依赖"每请求查库" | spec 已选择服务端会话（非 JWT），每次 `/admin/*` 请求都要查会话表判断是否 revoked/过期，属于正确选型（保证停用立即生效），但要注意别在会话校验中间层加本地内存缓存/短 TTL 缓存，否则会破坏"停用后下一次请求立即失败"的验收标准。 |
| 低 | 建号/重置密码接口不支持幂等重放，客户端超时后需人工判断是否已生效 | spec 已作为已知限制写明（靠再次调用重置补救），架构上补充：这两个接口应记审计日志（已要求落库），便于超管在"不确定口令是否生成成功"时通过审计记录核实，而不是盲目重复点击生成多个口令造成困惑。此项已被 spec 的"落库审计"覆盖，不再需要额外机制。 |

## 对其他端的隐含要求

**管理后台**：需对 `403`（`FORBIDDEN`/`CANNOT_DISABLE_SELF`/`LAST_SUPER_ADMIN`）与 `401` 做不同的 UI 处理
（前者提示权限不足并留在当前页，后者强制跳转登录）；一次性口令展示页需明确提示"仅展示一次、请立即
转达"，不可支持刷新后再查看。

**前台**：无隐含要求（`/public/*` 与后台会话完全隔离，本 feature 不涉及前台改动）。
