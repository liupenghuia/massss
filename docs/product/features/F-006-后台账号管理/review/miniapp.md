## 我理解的需求

管理后台是纯 Web（ADR-001 已确认不做小程序），账号仅两级（管理员/超级管理员），登录基于服务端会话
Cookie（`HttpOnly; Secure; SameSite=Strict; Path=/admin`），首次登录/重置密码强制改密，8 小时滑动过期。
管理后台仅面向内部人员，前台无用户体系、与管理后台不同域部署。我的评审范围是：管理员如果在微信
内置浏览器（企业微信/微信聊天里点开链接）打开管理后台做登录、改密、建号等操作时的体验与风险。

## 我的方案倾向

按 principles 已定的口径处理：微信内置浏览器当普通手机浏览器测，不做任何微信专属能力（不接
JS-SDK、不做微信授权登录、不判断 UA 做特殊分支）。管理后台本身不是拉新/分享场景，正常预期管理员
是收藏链接或直接输入域名访问，而不是靠微信内分享链接进入，因此本视角风险面本身就窄，不需要因为
"可能被微信打开"而新增设计。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 中 | 微信安全域名拦截 | 若管理后台域名被误判/未在微信平台侧处理过，通过微信聊天/企业微信分享的链接可能被"已停止访问该网页"拦截，管理员当场无法进入登录页。属于管理后台域名的外部依赖，不属于代码缺陷，但会造成"链接能用/不能用"不可控。 |
| 低 | Cookie 生存周期 | 微信 iOS 内置浏览器在系统内存紧张时可能回收 WebView 进程，`SameSite=Strict` Cookie 本身没问题，但用户体感上可能出现"切到微信聊天再切回来发现要重新登录"，属于可带上线的体验瑕疵，不是账号机制缺陷。 |
| 低 | 初始口令展示页的复制/截图 | "创建成功页展示一次"若在微信内打开，长按复制在部分微信版本受限，管理员可能改用截图保存口令，产生口令留存在聊天记录/相册的次生风险；这是操作习惯问题，不是本 feature 要解决的范围，仅提醒。 |

## 对其他端的隐含要求

- 服务端：登录/改密相关接口不得依赖任何仅浏览器原生环境才有的能力（如 WebAuthn、系统级密码管理器自动填充触发），保持账号名+密码的最低公分母方案，微信内置浏览器与普通浏览器一致可用。
- 管理后台：登录页与改密表单的输入框字号需按 principles 已定规则（≥16px 防 iOS 自动放大），这一条对所有手机浏览器（含微信内置）通用，不需要为微信单独加代码。
- 前台：与本 feature 无关，`/public/*` 不读取/校验后台会话，微信内打开前台页面不在本次评审范围内。

## 我需要别人回答的问题

（无。管理后台不依赖微信身份体系，微信内置浏览器仅作为"又一个手机浏览器"对待，已被 principles 与
spec 的通用手机端规则覆盖，未发现需要新增裁决的问题。）
