## 我理解的需求

管理后台需要一套登录/会话体系，两级角色（管理员、超级管理员）业务权限完全相同，权限差只体现在「账号管理」入口的可见性与可操作性上。超级管理员能建号、停用/启用、改角色、重置密码；首次登录/密码重置后强制改密才能用其他功能。账号列表默认展示全部（含停用），带状态标签。无审计查看页，无自定义权限矩阵，无物理删除。

## 我的方案倾向

- 登录页做成独立路由，不挂在 `/admin/*` 布局下，避免登录页被全局权限守卫拦截；登录成功后跳转回原目标页（带 redirect 参数），提升可用性但非强制。
- 前端用一个全局的「当前账号」上下文（角色、登录名、账号 ID）在应用启动时拉取一次，驱动「新建管理员」「停用/启用」「重置密码」「改角色」等入口的可见性；不在各页面各自判断角色字符串，避免散落的权限判断逻辑不一致。
- 401/403/`MUST_CHANGE_PASSWORD` 等错误码在请求层统一拦截处理：401 强制跳登录页，`MUST_CHANGE_PASSWORD` 强制跳改密页并锁定其余路由，403 就地给出「权限不足」提示而不是跳转，避免和 401 混淆。
- 强制改密页面做成路由守卫级别的拦截（类似支付宝强制实名那种全屏遮挡），不能通过前进后退或直接改 URL 绕过。
- 新建账号成功页的初始口令，只展示一次即离开就不可再查看，需要有明显的"请立即复制/告知，关闭后不可再查看"提示，并禁止该页面被浏览器返回缓存复现明文口令（history 或前端状态里不留存）。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 初始口令/重置口令仅展示一次，前端状态管理不当会导致泄露或误丢 | 若把口令存进全局 store 或路由 state 且未及时清理，用户切换页面后回退可能重新看到明文；离开该页面后必须主动清空内存中的口令值。 |
| 中 | 停用自己/最后一个超管等错误码（`CANNOT_DISABLE_SELF`/`LAST_SUPER_ADMIN`）需要在操作前置校验，避免用户点击后才收到后端拒绝 | 列表页对「停用」按钮、「降级」按钮要结合当前登录账号 ID 和统计的启用超管数（若可知）做前端预判提示，减少无效请求和困惑；但最终仍以后端错误码为准，不能只靠前端拦截。 |
| 中 | 登录名永久占用、不可改，创建表单需要一次性把这条规则讲清楚 | 若创建输入框旁无提示，运营容易输错登录名后才发现无法改名、也无法回收，只能弃用该名再建新号，造成"僵尸登录名"堆积且无处查看（无审计页）。 |
| 中 | 会话 8 小时滑动过期，管理后台长任务（如批量上传图片/报告）过程中会话过期会导致操作失败但用户无感知 | 需要前端在长任务过程中遇到 401 时给出明确提示并保留未提交的表单数据，而不是静默失败或清空用户输入。 |
| 低 | 账号列表默认展示全部含停用账号，量级不明确时未做分页/筛选说明 | brief/spec 未给出账号规模上限，按管理员/超级管理员开设频率通常个位数到几十，暂不视为风险，但列表页仍应支持按状态/角色筛选以方便运营核对。 |

## 对其他端的隐含要求

- 服务端：401 与 403 必须严格区分（未登录 vs 已登录但权限不足/已停用），前端依赖这个区分做不同的 UI 分支（跳登录 vs 提示无权限）。
- 服务端：`MUST_CHANGE_PASSWORD` 需要在登录响应和后续所有 `/admin/*` 请求中都能被前端识别为一种"半登录态"，不能只在登录接口返回一次。
- 服务端：账号列表接口需要能返回角色、启用状态、（若可能）当前是否为最后一个启用超管的判断依据，供前端做操作前置提示；若接口不返回该信息，前端只能等后端拒绝后二次提示，体验会打折扣，需要接口方确认是否提供。
