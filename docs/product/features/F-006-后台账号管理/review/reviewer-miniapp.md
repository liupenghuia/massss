## 我理解的需求

管理后台必须登录后才能进页面、才能调 `/admin/*`。账号只有两级：管理员（车辆录入/编辑/上下架/改价/进回收站）和超级管理员（上述全部 + 生成、分配、停用管理员）。没有只读、没有审核流、没有字段级分权。前台无用户体系。登录态要能落到 F-001/F-003/F-004 的操作人。被停用账号须立刻不能登录、不能改数据。

对照 `docs/principles.md` 与 brief 中的 ADR-001：**前台与管理后台均采用 Web，明确不做微信小程序、不做微信/企微身份登录、不做小程序登录。** 因此本 feature 不进入小程序技术栈，也不存在小程序登录态、openid/unionid、隐私授权或审核类目问题。

## 我的方案倾向

- **不实现小程序端。** 不为账号管理、后台登录、openid 绑定做任何小程序页面、分包或 `wx.login`。
- 前台保持无用户体系：不在任何访客端收集 openid/unionid；操作人标识只来自管理后台账号。
- 若产品日后推翻 ADR-001 要做小程序，账号管理仍应只在 Web 管理后台完成。
- 包体积/分包/首屏：本需求对小程序无增量。

## 反对/风险
| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 用小程序做管理后台会直接违背原则与 brief | 微信审核对内部管理系统、登录与用户信息收集极严；brief 已写明不做小程序登录。任何把 `/admin/*` 接到小程序的方案都应拒绝。 |
| 中 | 停用账号「立即」在小程序场景无法定义 | 本需求不该有小程序会话；若用微信会话缓存管理员身份，停用后客户端仍可能持有旧 token。应坚持仅 Web + 服务端鉴权。 |
| 低 | 误把「操作人」做成微信昵称/openid | 操作人必须是后台账号，不能用微信身份凑标识。 |

## 对其他端的隐含要求

- **服务端：** `/admin/*` 一律校验后台登录态；不要提供「code 换 openid 再当管理员」的接口。停用必须使已签发的后台 token/session 立即失效。权限差只在「管账号」接口。操作日志、价格记录的操作人写后台账号 id，不要写 openid。
- **管理后台（Web）：** 未登录不能进页；超级管理员才能生成/分配/停用管理员。登录入口不要做成微信一键登录。
- **前台：** 零登录、零账号、不展示管理员信息。
- **小程序：** 无页面、无登录、无隐私协议。不要为 F-006 申请企业管理类目。
- **F-001/F-003/F-004：** 操作人依赖后台账号，契约不要出现 openid 作为操作人。

## 我需要别人回答的问题

- 是否 100% 维持 ADR-001（全程无小程序）？
- 「分配」管理员账号的具体形态（口令、一次性链接、仅超管代设密码）由谁定？不要出现「扫小程序码领账号」。
- 停用「立即」的服务端语义（踢掉已有 session 的时限、是否允许多端同时登录 Web）需服务端确认。
