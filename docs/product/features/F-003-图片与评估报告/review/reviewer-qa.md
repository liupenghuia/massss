## 我理解的需求

管理员在管理后台为每辆车（以 F-001 技术主键关联，ADR-005 已定）上传图片（≥4 张、无上限）、
调整图片顺序、给单张图片加说明文案（区别于车辆描述）、上传第三方评估报告文件
（PDF/PNG/jpeg），全部存对象存储 + CDN，不落应用服务器本地磁盘。访客在前台只读查看
车辆的全部图片、图片说明、评估报告。发布时是否要求已有图片，由 F-001 的发布动作校验
（ADR-003 已裁定：发布前置校验图片数量 ≥ 4 张），不在本 feature 内实现，但本 feature
需要为该校验提供可靠的数据来源。明确不做在线编辑、视频、审核流程。车辆下架时图片是否
联动处理，brief 显式标记为"留待本 feature 评审裁决"，目前尚无结论。

## 我的方案倾向

- 验收标准应按「图片」「图片说明」「评估报告」「排序」四条数据线分别设计用例，
  每条都要覆盖"下限/上限边界 + 格式非法 + 关联车辆错误"三类用例，而不是只测正常路径。
- 凡是 brief 里出现"无上限"的地方，测试阶段都需要一个可执行的实际上限值（哪怕只是
  压测基准，例如"验证 200 张不报错、验证单张 20MB 以内"），否则无法写自动化断言，
  也无法验证是否触及 principles.md 的月度成本上限。
- 图片与车辆的关联正确性（不能 A 车挂 B 车的图）属于 principles.md 零容忍项，建议把
  "切换车辆后上传是否仍精确落在原车辆"设计为专门的回归用例，而不是随手测一下。
- 涉及 F-001 联调的部分（发布前校验图片数量）不应等 F-001/F-003 两边契约都写完才测，
  建议先以 mock 数据把这条校验逻辑的边界（3 张拒绝、4 张放行）单独验证。

## 反对/风险
| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 图片删除/替换操作未定义 | brief 全文只提"上传、排序、说明、展示"，没有一处提到删除或替换已上传图片。若确实不支持删除，管理员误传图片后没有补救手段，这类"操作无出口"的缺口在 F-001 评审中已经出现过一次（草稿清除出口），本 feature 不应重蹈。 |
| 高 | 车辆下架时图片/报告是否联动处理，brief 自己标记待裁决但未给出方案 | 关系到 principles.md「已删除车辆仍在前端可见」的零容忍红线：如果图片/评估报告走对象存储 + CDN 公开直链，即便车辆状态在服务端被过滤为不可见，文件本身的 URL 如果不失效，仍可能被外部直接访问到。这不是"能不能测"的问题，是"测哪个层面"的问题——页面不可见 ≠ 资源不可访问，需要先有裁决结论才能设计验收用例。 |
| 高 | 图片与车辆错配的防护机制未描述 | principles.md 零容忍项，但 brief 没有说明上传接口如何强绑定目标车辆（例如管理员开多个标签页操作不同车辆时如何防止误提交到错误 vehicleId）。没有机制描述就无法设计针对性的边界/并发用例。 |
| 中 | "无上限"没有可测试边界 | 图片总数、单张文件大小、评估报告文件大小均未设上限，无法转化为自动化边界用例；同时与 principles.md「月度云支出上限 500」存在潜在冲突（无限制的图片数量 + CDN 流量是长期成本大头，brief 自己也这么说）。 |
| 中 | 评估报告"直接展示"缺具体交互定义 | PDF 在移动端浏览器的内嵌预览兼容性未评估，与 principles.md「移动端优先」的取向存在风险；不确定是"页面内嵌预览"还是"新开/下载"，两种验收路径完全不同。 |
| 中 | "条数无上限"表述有歧义 | 原文："给单张图片添加说明文案……条数无上限"。无法判断是指"每张图片可加多条独立说明"，还是重复强调"图片总数无上限"。两种理解对应的数据模型和验收用例完全不同。 |
| 中 | 排序结果的保存时机未定义 | "排序后保存或发布"是否意味着存在一个独立于发布动作的"仅保存排序"接口？如果排序必须随编辑/发布动作一并提交，会和 F-001 的编辑接口耦合，目前没有描述这个边界。 |
| 中 | 评估报告文件数量与可替换性未定义 | 每辆车允许几份评估报告（一份还是多份，来自不同检测机构）？已上传的报告能否替换/删除？未说明。 |
| 低 | 图片格式范围未明确 | 只提到"图片"，未列出允许的具体格式（jpg/png/webp/gif 是否都算），评估报告已明确 PDF/PNG/jpeg 但图片本身没有。 |
| 低 | 上传失败/超时/大文件重试策略未提 | 评估报告 PDF 体积可能较大，上传中断后是否支持续传或需要整体重传，未说明，属于可带上线但建议记录。 |

## 对其他端的隐含要求

- **对 F-001（服务端/发布逻辑）**：ADR-003 已裁定发布前校验"图片数量 ≥ 4 张"由 F-001
  在发布动作里主动反查 F-003 的图片数据。这意味着 F-003 必须对外提供一条稳定、可在
  F-001 发布流程内同步查询的数据通路（无论是服务间调用还是共享库读取），且这条通路的
  contracts 需要先于或同步于 F-001 的发布端点定稿，否则会重现 ADR-003 里已经指出的
  "F-001 发布逻辑在 F-003 契约定稿前无法完整实现和测试"的问题。
- **对 F-001（权限模型）**：图片上传/删除/排序、评估报告上传这些写操作是否受管理后台
  权限分级约束，取决于 F-006（后台账号管理）的裁决结果，该问题目前仍未裁决。F-003 的
  验收标准里"谁能操作"这一维度暂时无法写死。
- **对 F-002（前台展示，目前无 brief）**：访客查看图片/说明/评估报告依赖 F-003 提供
  `/public/*` 只读接口，但 F-002 尚不存在 brief。F-003 对外契约（返回哪些字段、图片顺序
  如何体现、评估报告 URL 格式）需要先明确，否则 F-002 后续开工时容易反复要求 F-003 改接口。
- **对服务端/存储选型**：图片与评估报告的对象存储访问策略（公开直链 vs 签名 URL）
  直接决定前台能否用普通 `<img src>` 展示、也决定"下架车辆资源是否仍可被外部直接
  访问"这条红线怎么落地。这个决定权不在 F-003 内部就能定，需要和整体存储技术选型
  一起裁决。
- **对管理后台前端**：拖拽排序需要一个支持批量提交顺序（如 index/order 字段数组）的
  接口设计，不是逐张图片单独 PUT；前端具体交互方式（保存按钮 vs 拖拽即时提交）会
  反过来约束后端接口的幂等性设计，需要双方对齐后才能定验收标准。
- **对 F-001 状态机（ADR-004）**：ADR-004 规定"编辑不改变车辆状态"，但图片/评估报告
  的增删改是否算作"编辑"动作、是否会立即反映到已上架车辆的前台展示（无需重新点击
  发布），brief 未提及，需要与 F-001 的编辑语义对齐，否则会出现"改图片要不要重新发布"
  的行为歧义。

## 我需要别人回答的问题

1. 已上传的图片是否支持删除或替换？如果不支持，管理员上传错误图片后有什么补救手段？
2. 车辆下架时，F-003 挂载的图片和评估报告是否需要联动处理？具体是指：CDN 直链在车辆
   下架后是否仍可被外部直接访问到文件本身？这是 brief 自己标注"留待本 feature 评审
   裁决"的问题（对应 F-001 conflicts.md 问题 24），需要一个明确结论才能设计验收用例。
3. "给单张图片添加说明文案……条数无上限"具体指什么：是每张图片可以添加多条独立说明
   文案，还是仅重复表达"图片总数无上限"？
4. 图片总数、单张图片文件大小、评估报告单份文件大小，是否需要设一个实际上限（哪怕只是
   用于测试和成本控制的软上限）？允许的图片格式范围是什么（是否等同评估报告的
   PDF/PNG/jpeg，还是另有一套）？
5. 每辆车允许上传的评估报告份数是多少？已上传的评估报告是否支持替换或删除？
6. 评估报告"直接展示"具体是什么交互——页面内嵌预览，还是点击后新开/下载？PDF 在移动端
   浏览器的内嵌预览是否有兼容性要求（principles.md 要求移动端优先）？
7. 图片和评估报告的对象存储访问策略是公开直链还是需要签名 URL/鉴权？这直接决定问题 2
   的答案能否落地。
8. 排序调整后的保存是一个独立动作（如"保存排序"按钮直接调用接口生效），还是必须和
   车辆的编辑/发布动作一起提交？
9. 图片、评估报告的上传/删除/排序操作是否受管理后台权限分级约束？这依赖 F-006 的
   裁决结果，目前该问题尚未裁决。
10. F-003 向 F-001 暴露"某车辆当前图片数量"这一数据的具体方式是什么（服务间接口调用、
    共享数据库直接查询，还是别的形式）？两个 feature 的 contracts 定稿顺序如何协调，
    以免出现 ADR-003 已提示过的"F-001 发布逻辑联调受阻"？
