## 我理解的需求

围绕车辆（F-001 技术主键）挂两类子资产：车辆图片（≥4 张、无上限，支持排序、单图 1:1 说明文案）与第三方评估报告（可多份、按上传时间倒序）。
两者都没有独立状态机，可见性完全继承车辆的发布状态；增删改都是即时生效的"编辑"动作，不存在"已保存未发布"的中间态。存储走对象存储直传 + 预签名 URL，服务端只做元数据确认落库。

## 我的方案倾向

- 图片、报告建模为车辆的两个独立子实体集合（一对多），而非合并成一个"附件"实体：两者字段差异大（图片有 order/caption，报告没有），业务规则也不同（图片有数量下限、报告没有），拆开更清晰。
- 图片的"顺序"用整型 rank 字段维护，不做乐观锁/版本号（已知不做并发冲突检测），但重新排序需整批覆写 rank 而非增量插入，避免出现两张图 rank 相同导致排序不确定。
- 预签名直传的"确认"步骤是唯一的一致性关卡：必须在服务端确认时校验对象 key 与目标 vehicleId 强绑定，否则"图片/报告与车辆错配"和"评估报告串号"这两个零容忍项无法真正兜住。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 预签名直传的错配防护未在需求里显式描述 | "图片与车辆错配""评估报告串号"是零容忍项，但客户端直传+服务端确认落库的两步流程本身存在"确认时传错 vehicleId 也能落库"的风险面，需求里没有写确认步骤要校验对象 key 归属，这个校验不是"实现细节"而是领域完整性约束，遗漏会导致零容忍项失守。 |
| 中 | "已删除车辆"与"已下架车辆"在图片可见性上的边界未分清 | 现状 spec 只写明"/public/* 接口不返回已下架数据"，零容忍项是"已删除车辆仍在前端可见"。若车辆存在回收站/软删除状态（非单纯 unpublished），需要明确图片/报告的公开接口是否也覆盖这一状态，否则"已下架"与"已删除"两个状态的图片可见性口径不一致会直接踩零容忍红线。 |
| 中 | 报告实体缺少可区分多份报告的领域属性 | 一辆车可挂多份评估报告，仅按上传时间倒序展示，没有"评估机构/报告类型"之类的标识字段。管理员上传多份后无法在列表里区分谁是谁，只能靠打开文件确认，属于领域信息不完整（不是纯 UI 问题，是实体缺字段）。 |
| 低 | 图片说明文案无长度上限 | "条数无上限"指图片数量，但单条说明文案是否有长度约束未提及，长文案可能影响展示排版，建议定一个工程默认上限而非完全不限。 |

## 对其他端的隐含要求

- **server**：预签名确认接口必须校验上传对象所属 vehicleId 与请求参数一致，拒绝跨车辆确认；批量重排序需整批覆写 rank，避免部分失败导致顺序错乱。
- **admin-web**：多份评估报告的列表展示需要能让管理员快速区分不同报告（哪怕只是显示文件名/上传时间，也要在设计里体现，不能靠打开文件才能分辨）。
- **public-web**：图片与报告的公开可见性判断必须同时覆盖"未发布"和"已删除/回收站"两种车辆状态，不能只按 published 布尔值单一判断。

## 我需要别人回答的问题

1. 车辆是否存在"回收站/软删除"状态（区别于 unpublished）？若存在，`/public/*` 接口是否已确认同时过滤该状态下的车辆图片/报告？
2. 评估报告是否需要"评估机构名称"或"报告类型"字段用于区分同一车辆下的多份报告，还是仅靠文件名即可满足现状？
