## 我理解的需求

管理员为每辆车（用 F-001 技术主键关联）上传图片（≥4 张、无上限）和评估报告文件（PDF/PNG/jpeg），
可拖拽排序、给单张图片加说明文案；图片/报告走客户端直传对象存储 + 预签名 URL，服务端只做元数据落库；
访客在前台查看全部图片、说明与报告（报告新标签页打开原文件）。无独立状态机，增删改即时生效，
可见性完全由车辆 published/unpublished 状态决定；已上架车辆删除图片使数量 <4 时服务端拒绝该次删除；
下架不做图片联动清理；本期不做并发排序冲突检测、不做打包下载、不做已删除车辆的存储文件清理。

## 我的方案倾向

以「零容忍项」为核心组织测试：优先覆盖图片/报告与车辆的绑定正确性（防串号）、
已上架车辆的 4 张下限拒绝逻辑、以及 `/public/*` 接口对下架/已删除车辆的过滤。
其余（排序、说明文案、批量上传进度、文件类型/大小限制）按边界值 + 异常路径补充用例，
直传+预签名的失败/中断路径（孤儿对象、confirm 未调用）单独列为高风险场景重点验证。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 图片/报告与车辆错配的测试覆盖依赖预签名 URL 的车辆 ID 绑定实现，spec 未说明预签名 URL 或 confirm 接口如何校验"该文件确实是为这台车申请的"，需明确防串号机制（如 URL 内嵌车辆 ID 签名、confirm 时校验），否则零容忍项无法写自动化断言 |
| 高 | 客户端直传成功但从未调用 confirm（用户中途关闭页面/网络中断）会在 OSS 留下孤儿文件，且不会出现在元数据里；spec 未定义此场景的处理或清理责任，测试需要能确定性复现并验证系统行为（至少不影响图片计数/展示） |
| 中 | `adminReorderVehicleImages` 未说明当传入的图片 ID 列表与该车实际图片集合不一致（缺失某些 ID、包含其他车的 ID、重复 ID）时的服务端行为，是拒绝整个请求还是部分生效，需明确才能写边界用例 |
| 中 | 图片说明文案（caption）未定义最大长度/是否允许空字符串，无法确定校验边界用例的上下限 |
| 中 | 批量拖拽上传"部分失败不影响其余"未定义前端如何区分展示成功/失败文件及是否支持单个重试，验收标准无法转成 UI 自动化用例（这属于跨端隐含要求，见下） |
| 低 | "单车图片数超 100 张只告警不阻断"的告警渠道未定义（日志/后台提示/运维通知），若无法观测则该条无法自动化验证，只能靠日志检查 |
| 低 | 已上架车辆删除图片被拒绝时的错误提示文案/错误码未在 spec 中给出示例，需要契约明确才能断言前端展示与后端返回一致 |

## 对其他端的隐含要求

**server：** 预签名/confirm 接口需能校验文件确属申请时绑定的车辆 ID，防止跨车串号；4 张下限校验需在删除接口做原子判断，避免并发删除绕过下限；`/public/*` 列表接口需在车辆下架/删除后立即停止返回其图片与报告元数据。

**admin-web：** 批量上传需展示每个文件的独立进度与失败状态（含可定位的错误原因），不能整体失败/成功笼统提示；删除图片/报告需二次确认弹窗，且拒绝态（如低于 4 张）需有明确文案而非静默失败；拖拽排序需在保存前后都有加载态反馈。

**public-web：** 图片画廊需按后台返回顺序渲染，不做前端重排；评估报告链接需新标签页打开且需处理文件加载失败/404 的占位态；下架车辆的图片/报告不应通过任何前台入口可达，即使直链未失效。

## 我需要别人回答的问题

1. 预签名 URL / confirm 接口如何校验文件所属车辆，防止串号（这是零容忍项，需要明确机制才能写自动化断言）？
2. 直传成功但从未调用 confirm 的孤儿文件如何处理：是否有过期回收机制，还是完全不管（留给 F-005 之外单独处理）？
3. `adminReorderVehicleImages` 传入的图片 ID 列表与实际不一致（缺失/多余/重复）时，服务端应拒绝整个请求还是部分生效？
4. 图片说明文案是否有长度上限？是否允许为空？
