## 我理解的需求

管理员在管理后台给每辆车（以 F-001 技术主键为关联锚点，ADR-005）上传图片（下限 4 张、无上限）与第三方评估报告文件（PDF/PNG/jpeg），可拖拽调整图片顺序、给单张图片加说明文案（条数无上限）。图片和评估报告落对象存储 + CDN，不进应用服务器本地磁盘。访客在前台只读查看图片、图片说明、评估报告，前台无登录态。不做图片在线编辑、不做视频、不做审核流程。F-001 的发布前置校验（ADR-003）依赖本 feature 提供"图片数量 ≥ 4"的数据，校验逻辑在 F-001 侧执行，F-003 只需被动提供数据。车辆下架时图片是否联动处理，本 feature 需要给出裁决（F-001 conflicts.md 问题 24）。

## 我的方案倾向

- **上传路径：客户端直传对象存储 + 预签名 URL，服务端只做元数据落库**。理由：principles.md 明确图片/评估报告是长期主要成本项，评估报告为 PDF 可能体积不小，若走服务端中转会让应用服务器承担不必要的带宽和内存压力；100 台车的规模下预签名 URL 机制实现成本可控。上传流程建议为：①管理后台请求服务端签发预签名 URL 与临时文件 key；②前端直传对象存储；③前端携带 key 回调服务端"确认"接口，服务端此时才写入图片/报告的正式记录。第③步是唯一的数据可见性开关，避免"OSS 有文件、DB 无记录"或反过来的不一致状态直接暴露给业务。
- **排序保存用"整单替换"而非逐条移动**：拖拽结束后前端一次性提交完整的图片 ID 顺序数组，服务端在一个事务里按数组顺序批量更新 `sort_order`，不接受"上移一位/下移一位"这种增量语义的接口，避免并发下的顺序错乱和中间态。
- **软删除 + 异步清理对象存储**：图片/报告删除时先做 DB 软删除（前台立即不可见，满足强一致要求），对象存储文件的物理删除走异步任务/生命周期规则，并保留一张"待清理"记录表或依赖 DB 状态做定期对账，防止清理任务漏跑导致存储成本长期泄漏。
- **图片新增+删除，不支持"原地替换"内容**：如需换图，走"新增一张 + 删除旧的一张"，不复用同一个对象存储 key 覆盖内容，避免 CDN 边缘缓存返回旧内容造成的隐性错配风险。
- 数据量级上（100 台车、每车预计几十张图以内），`(vehicle_id, sort_order)` 复合索引即可满足列表查询，不需要分库分表或额外的搜索设施。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 上传一致性窗口未设计 | 无论中转还是直传，都存在"对象存储已有文件、DB 未落记录"或反向的中间状态。若不设计明确的两阶段确认 + 对账补偿机制，网络重试/客户端崩溃会导致孤儿文件（成本泄漏）或"数据库有记录但文件取不到"（前台 500/破图，触碰 principles"内容准确"红线）。 |
| 高 | 删图破坏发布前置条件的行为未定义 | ADR-003 只规定了"发布时"校验图片≥4张，没有覆盖"已上架车辆的图片被删到 4 张以下"这个场景。若不加控制，会出现前台展示中的已上架车辆图片数低于业务底线，且没人报错——这是 principles"内容准确 > 功能丰富，有疑问时砍功能不砍校验"要重点堵的漏洞。 |
| 高 | 图片说明文案数据模型歧义 | brief"条数无上限"存在两种读法（单图多条说明 vs 多图各一条说明），直接决定是 1:1 字段还是 1:N 子表。现在不澄清，等实现或联调阶段发现会导致表结构和接口契约返工。 |
| 中 | 排序批量保存的并发覆盖 | 多个管理员/多标签页同时对同一车辆排序，后提交者会静默覆盖先提交者的结果，且当前方案（整单替换）没有天然的冲突检测。虽然 principles 把"图片加载顺序"列为可带上线的瑕疵，但静默覆盖若丢失了刚保存的说明文案关联（如 1:N 模型下说明文案挂在排序记录上），后果不止是顺序问题。 |
| 中 | F-001 反查 F-003 计数的一致性口径未定 | ADR-003 要求 F-001 发布前反查 F-003 图片数量，但"计数"是否包含软删除/上传中未确认的记录没有约定，口径不一致会导致 F-001 校验结果与前台实际展示的图片数不一致。 |
| 中 | 对象存储孤儿文件清理缺失设计 | 软删除、上传中断留下的临时文件如果没有生命周期规则或定期对账任务，会在"图片是主要成本项、月度云支出上限 500"的约束下持续隐性增长，属于成本失控风险而非功能缺陷，容易被忽略。 |
| 低 | 上传数量无上限缺少软性约束 | 误操作或脚本重复提交可能让单车图片数暴涨到几百张以上，虽不阻塞当前功能，但会拖慢列表查询和管理后台页面体验，建议至少加日志/告警而非强制上限。 |

## 对其他端的隐含要求

- **对 F-001（服务端内部）**：需要提供一个供 F-001 发布动作调用的"有效图片计数"查询能力（进程内方法调用即可，不必是 HTTP 接口），且必须明确只统计已确认、未软删除的图片；F-001 与 F-003 需要对齐车辆技术主键的可用时机——图片上传是否要求车辆已存在（哪怕是草稿态）才能挂载，还是允许在车辆创建流程尚未完成时先传图片再关联（本评审倾向前者，但需要 F-001 侧确认草稿创建后主键立即可用）。
- **对管理后台前端**：①拖拽排序必须在结束后一次性提交完整顺序数组，不能逐条调用移动接口，否则并发/网络抖动下无法保证顺序正确性；②若采用预签名直传方案，前端要多做一轮"申请上传凭证 → 直传对象存储 → 回调确认"的流程，比传统的表单上传复杂，需要在前端工作量评估里体现，尤其要处理直传失败后的重试与凭证过期；③服务端会对文件类型/大小做二次校验（不能只信前端），前端提示的错误码需要能覆盖服务端拒绝的场景；④图片说明文案的编辑 UI 依赖上面"我需要别人回答的问题"里数据模型的裁决结果，1:N 模型需要设计增删多条的交互，不是单个输入框。
- **对前台**：①图片列表接口必须返回服务端持久化的排序结果与对应说明文案，且排序保存后前台读取要与 ADR-005"下架强一致、不做缓存延迟"同等对待——图片顺序变更后前台不能因为 CDN/接口缓存而滞后展示旧顺序；②评估报告"直接展示"要求服务端在文件的 Content-Type/Content-Disposition 上做对，保证浏览器内联预览而非强制下载，这一点需要写进契约给前台联调用；③前台是纯客户端渲染、无登录态，图片与评估报告的对象存储/CDN 访问方式（是否公开直链）会直接影响前台请求方式，需要与前端约定清楚 URL 形态是否稳定（不能因为签名 URL 有效期过期导致前台刷新后图裂）。
- **对 F-005（回收站，未来）**：本 feature 若不为图片/评估报告表预留软删除或车辆维度的联动标记，F-005 落地时大概率要对 F-003 的表结构和接口再做一次迁移，这与 ADR-005 对 `vehicles` 表"本期不预留、F-005 落地时再迁移"的取舍是一致的代价，但需要显式记录下来，避免到时候被当作意外返工。

## 我需要别人回答的问题

1. 图片/评估报告上传走"服务端中转"还是"客户端直传对象存储 + 预签名 URL"？这决定服务端要不要处理大文件流量、以及一致性保障方案的复杂度（本评审倾向直传方案，需要业务侧/主会话确认是否接受相应的前端实现复杂度）。
2. 图片说明文案"条数无上限"具体指什么：是允许给单张图片写多条说明（列表形式），还是允许在无上限数量的图片上各写一条说明？这直接决定数据模型是 1:1 字段还是 1:N 子表。
3. 已上架车辆若被删除图片导致数量跌破 4 张，是否允许这个删除动作？若允许，是否需要联动自动下架，还是放任车辆带着"低于门槛"的图片数量继续展示，等下次手动发布/重新上架时才会被 ADR-003 的校验拦下？
4. 车辆下架（以及未来 F-005 软删除）时，F-003 的图片和评估报告是否需要联动做任何处理（例如冻结编辑、仅管理后台可见），还是完全不受车辆状态影响？（F-001 conflicts.md 问题 24，需要本 feature 给出裁决）
5. 评估报告文件是否有数量上限？允许多份评估报告并存，还是只保留一份、新上传直接覆盖旧的（若覆盖，是否需要保留历史版本记录）？
6. 图片单文件、评估报告单文件的大小上限分别是多少？这会影响上传方案选型（中转 vs 直传）以及对象存储/CDN 的成本测算（对照月度云支出上限 500 元）。
7. 图片是否允许"替换"某个排序位置上的内容（保留位置、换图），还是只能"删除旧图 + 新增新图"？如果要支持替换，需要额外设计 CDN 缓存刷新策略。
8. 图片和评估报告的访问链接是否需要访问控制（例如带签名/有效期），还是和前台展示一样完全公开直链？评估报告里是否可能包含不适合被搜索引擎或非目标访客直接访问到的敏感信息？
