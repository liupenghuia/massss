## 我理解的需求

管理员为车辆（关联 F-001 技术主键）上传图片（≥4 张无上限）和评估报告文件，支持排序、图片说明、删除、批量拖拽上传。客户端直传对象存储 + 预签名 URL，服务端仅做元数据落库确认。访问链接为公开直链，不做鉴权，下架不联动清理。已上架车辆图片数低于 4 张时拒绝删除。权限本期为单一管理员全权限，操作纳入统一操作日志。ADR-008/009/010/011 已把主要交互与存储决策定稿，本次评审聚焦服务端实现层面的幂等、并发、迁移与失败补偿风险。

## 我的方案倾向

- 预签名 URL 走"申请预签名 → 客户端直传 → 服务端确认落库"三段式，确认接口做成幂等（同一 objectKey 重复确认返回同一条元数据记录，不重复插入）。
- 预签名申请与确认之间设置短 TTL（如 1 小时），未确认的预签名不占用任何数据库资源，避免产生"孤儿"记录；对象存储侧的孤儿文件（申请了预签名但从未确认或客户端直传后从未调确认）本期不做扫描清理，等 F-005 一并处理，与 ADR-009"删除不同步清理"口径一致。
- 图片数量下限校验（<4 张拒绝删除）与排序更新，用车辆行级锁或简单的"先查后判断"+ 唯一约束兜底即可，不需要引入分布式锁：ADR-008 已明确排序并发冲突"后写覆盖可接受"，但删除导致的数量校验建议在同一事务内做"查询当前数量 → 校验 → 删除"，避免两个管理员同时删除导致跌破 4 张下限（这条不属于"排序"，属于零容忍相邻的数据完整性风险，值得在事务内加保护，即使成本很低）。
- 批量拖拽上传的"部分失败不影响其余"，落地为逐文件独立的预签名+确认调用，服务端不做批量事务打包，失败文件由前端单独提示重试，不需要服务端记录批量任务状态。
- 图片说明（1:1）作为图片记录的一个字段，与图片元数据同表或同行更新，不必单独建表，减少一次关联查询。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 中 | 预签名确认接口非幂等会导致重复记录 | 客户端网络抖动重试"确认"请求时，如果没有基于 objectKey 的唯一约束去重，会产生同一文件的多条元数据记录，前台展示出现重复图片。需要在确认接口上加唯一键（车辆ID+objectKey）幂等保护。 |
| 中 | 预签名申请后未直传/未确认的孤儿文件 | 管理员点了上传但中途关闭页面，预签名 URL 已生成、文件可能已直传到对象存储但从未调用确认接口，导致存储侧产生不会被任何元数据引用、也不会被后续删除流程清理的孤儿文件，长期累积成本。spec 未提及是否需要定期清理或 TTL 策略。 |
| 中 | 删除导致跌破 4 张下限的并发窗口 | 两个管理员几乎同时各删一张图片，若服务端各自"查询数量→判断→删除"缺乏事务/锁保护，可能同时通过校验，最终图片数低于 4 张但双方都认为操作成功，属于隐性数据完整性问题，建议在删除逻辑上加事务内重新计数。 |
| 中 | 单车图片数超 100 张只告警不阻断，但未定义告警去向 | spec 只写"告警"，未说明告警落在操作日志、监控还是无处可查；如果只是打日志没人看，等同于没有防线，超量车辆可能无限增长图片数，直接推高对象存储成本（图片是主要成本项，属于成本敏感点）。 |
| 低 | 评估报告"允许挂多份、按上传时间倒序"，无手动排序 | 已在 ADR-008 定稿，只是提醒实现时报告列表查询要有稳定排序键（建议用创建时间+自增ID联合排序，避免同一秒上传多份报告时顺序不稳定）。 |
| 低 | 公开直链无鉴权，下架不失效 | 已在 ADR-009 定稿并知晓代价，仅确认服务端实现上无需额外工作（不生成签名URL、不做referer校验），避免过度设计。 |

## 对其他端的隐含要求

- 管理后台：批量上传需对每个文件独立展示进度与失败状态，不能因单文件失败让整批显示为失败；上传中途关闭页面前建议做未确认文件的轻量提示或离开确认，降低孤儿文件概率。
- 管理后台：删除操作被服务端拒绝（跌破4张下限）时，需要展示明确的业务错误文案，不能只显示状态码。
- 前台（public-web）：图片/报告链接为公开直链，前台组件需处理链接直接失效（如对象被误删、跨域）时的裂图/加载失败占位，不能假设链接永远可用。

## 我需要别人回答的问题

1. 预签名 URL 生成后长期未确认（如超过 TTL）的记录，是否需要定时任务回收，还是本期彻底不管、留给 F-005 一并处理？
2. 单车图片数超过 100 张的"告警"，具体落地为操作日志一条记录即可，还是需要能被人工看到（如后台某处提示）？若只落操作日志，是否等同于当前不做任何提示，需要产品侧确认这个默认是否可接受。
