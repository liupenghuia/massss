## 我理解的需求

管理员在车辆编辑页对单车维护图片（≥4张、无上限）和评估报告文件：上传（客户端直传对象存储+预签名）、
拖拽排序、加/改单图说明文案、删除（需二次确认）。评估报告支持多份、按时间倒序、点击新标签页打开原文件。
无独立状态机，增删改即时生效，可见性由车辆 published 状态决定。本期单一管理员角色全权限，操作纳入
ADR-006 统一操作日志。图片数超 100 只告警不阻断；已上架车辆删除图片导致 <4 张时服务端拒绝。

## 我的方案倾向

- 沿用现有车辆编辑页的双栏/卡片布局，图片区做成网格缩略图+拖拽排序（沿用价格历史等列表已有的拖拽交互模式，一致性优先）。
- 批量拖拽上传复用现有"虚线投放区"组件（principles.md 已定），逐文件展示上传进度条+成功/失败状态图标，失败文件保留在列表内可重试或移除，不因单个文件失败中断整体流程。
- 删除操作统一走二次确认弹窗（沿用回收站同款交互），若服务端因"<4张"拒绝，前端需在弹窗内直接展示服务端返回的拒绝原因，不做前端预先拦截判断（避免前后端校验口径不一致）。
- 图片说明为随图片行内编辑的文本框，失焦或点击保存即提交，不做单独的"说明编辑弹窗"，减少操作层级。
- 评估报告列表按上传时间倒序展示文件名+上传时间+操作人（若操作日志可查），点击态用 `target="_blank"` 新标签打开。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 批量上传部分失败的呈现方式未在 spec 中定义 | spec 只写"部分失败不影响其余"，未定义前端如何逐文件展示成功/失败/重试，若不明确容易做成"整批转圈到底"，违反 principles.md 长任务进度反馈要求 |
| 中 | "删除导致<4张"由服务端拒绝，但前端何时感知未定义 | 若前端不做任何预判，管理员勾选删除、点确认后才收到失败提示，体验较差；需明确前端是否可在勾选阶段就禁用/提示（如显示"当前4张，无法继续删除"） |
| 中 | 图片数超100"只告警不阻断"，告警展示位置未定义 | 是上传时 toast 提示，还是编辑页常驻角标提醒，需要明确，否则管理员可能忽略持续超量上传 |
| 低 | 排序保存的触发方式未明确 | spec 提到"排序后保存或发布"，需明确拖拽后是否自动保存还是需要显式点"保存排序"按钮，影响是否会有未保存丢失的风险 |

## 对其他端的隐含要求

- server：批量上传接口需要返回逐文件级别的成功/失败结果（而非整批 all-or-nothing），供后台展示；删除拒绝需返回明确可读的失败原因文案供前端直显。
- server：需暴露操作日志按车辆/图片维度的查询，供后台在报告列表旁展示"谁上传的"（若要做该展示）。
- public-web：不涉及本端职责变化，前台展示逻辑已在 spec 中与本端解耦。

## 我需要别人回答的问题

- 批量上传部分失败时，是否要求逐文件展示失败原因并支持单文件重试，还是仅提示"N张失败，请重新上传"即可？
- 报告/图片列表是否需要展示"上传人"字段（依赖操作日志），若需要是否本期就做还是可带上线？
