## 一致项

- 价格记录表为 append-only，不可篡改，字段含变动前值、变动后值、时间、操作人（api/domain/qa/admin）。
- 当前价格 = 该车最新一条记录的变动后值，不建当前价格快照表（api/domain/qa）。
- 「已填写」= 至少一条价格记录，面谈视为已填写（api/domain/qa）。
- 本期不做审批、批量改价、导出、二次确认、按价格状态筛车（domain/qa/admin）。
- 价格记录独立管理，不落在车辆主表（api/domain）。
- F-001 反查「是否已填写」若失败必须报错阻断发布，不得静默视为未填写（api/admin）。
- 前台/后台只做只读展示，具体展示文案/条数/分页推迟到 F-002（miniapp/domain/qa）。
- 本期登录管理员权限一致，都能改价（admin，无角色异议）。

## 冲突项

### C-1 「最新一条记录」的排序依据
- 各方主张：api 倾向索引可建在 `(vehicle_id, created_at DESC)` 或 `(vehicle_id, id DESC)`，将二者视为可互换选项／domain 明确反对用时间戳排序，主张必须用单调递增的写入序号（如自增 ID），理由是并发改价或时钟回拨会导致时间戳排序取到错误的"当前价格"，触碰价格显示错误的零容忍线。
- 分歧根因：api 未把时间戳与自增序号视为有本质差异，domain 认为二者在并发/时钟异常场景下结果不同。
- 选项 A：以 created_at 时间戳排序 — 代价：并发写入或服务器时钟回拨时可能取到错误的"当前价格"。
- 选项 B：以单调递增序号（自增 ID/序列）排序 — 代价：需要确保该序号严格单调且在实现层强制作为排序唯一依据，不能退化为时间戳兜底。

## 无人认领的空白

- 并发改价的事务/锁策略：api 认为"读最新一条+比较+条件写入"需要事务+行锁或乐观锁防止记录错乱，但承认这只是自己的实现倾向，"spec 未明确写并发控制策略"；domain 与 qa 也各自提出同样的风险点，但三方均未确认 spec 是否已裁定，也没有人认领由谁在 spec 层面定下并发控制的最终要求。
- 数值归一化/精度标准：domain 提出"10.1 与 10.10 是否算相同金额"未定归一化口径，qa 提出金额上限缺失下的极大数值在存储/序列化/展示时是否溢出或精度丢失，两者都指向"金额应如何存储（decimal/整数分/浮点）"，但没有任何角色（含 api）明确表态由谁定义该存储类型与比较规则。
- 创建车辆带初始价格时是否生成价格记录：domain 提出车辆行与首条价格记录的事务边界未定义（同一事务提交/回滚与否），qa 提出"创建时是否等价于首次设价写记录"两种实现验收结果不同；两份评审都只是提问，没有角色说明由谁（api 还是 domain）拍板该规则并写回 spec。
- 操作人字段的可读展示：admin 要求服务端返回可读的操作人标识（账号名/昵称而非纯 ID）供列表渲染，但 api 的接口方案倾向里未提及该字段的返回形态，没有人认领这个字段契约。
- 反查失败与「未填写」的错误区分：admin 要求发布校验页面对"系统异常"和"业务未满足（未填写）"用不同错误码/文案区分，api 只提到"必须报错阻断发布"，未提及是否会返回可区分的错误类型；服务端与管理后台之间这一契约细节无人认领。
- 无二次确认下的误改价缓解：admin 提出用"提交前展示变动前→变动后对比"的非阻断提示来降低无二次确认的风险，但这只是 admin 自己的方案倾向，其他角色未呼应或反对，也没有人确认这是否需要写入 spec 作为强制要求。
- 回收站车辆的价格记录展示/清理：api 与 admin 都明确提到"留给 F-005"，但均未指出 F-005 评审时具体由谁（哪个角色）确保接住这个问题。
- 微信分享卡片摘要中"面谈"文案的歧义风险：miniapp 提出如果分享摘要引用价格字段，"面谈"可能被误读为价格为 0，该问题被标注"归 F-002"，但未指定 F-002 评审谁负责核实这一展示细节。

## 需要用户裁决的问题

1. 「当前价格=最新一条记录」的排序依据用时间戳（created_at）还是单调递增序号（自增 ID/序列），以避免并发改价或时钟回拨导致取值错误。
2. 并发改价（同一车辆被多个管理员几乎同时提交不同价格）是否需要强制的并发控制（事务+行锁/乐观锁），还是接受"后写入者生效"。
3. 金额的存储类型与比较归一化规则（如是否统一存为最小货币单位整数分），以及"变动判定"中数值相同的精确等价类定义。
4. 创建车辆草稿带初始价格时，是否同时生成一条价格记录（变动前=未填写），以及车辆行与该首条价格记录是否要求同一事务提交/失败整体回滚。
5. 价格记录列表中"操作人"字段展示登录账号名还是需关联后台账号昵称。
6. F-001 反查「是否已填写」失败时，是否需要向管理后台返回区别于"未填写"的独立错误码，供前端展示不同提示文案。
