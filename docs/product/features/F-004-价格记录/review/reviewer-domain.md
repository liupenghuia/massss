## 我理解的需求

F-004 独立管理"车辆价格"这个资产，核心是两个概念：

1. **当前价格**：挂在某辆车（F-001 技术主键）上的一个值，取值要么是"具体数值"，要么是"面谈"。
2. **价格记录（历史）**：每次价格发生变动时自动生成一条不可篡改的记录，包含变动前值、变动后值、变动时间。

对外提供两类能力：
- 管理后台：设置/修改价格（数值或"面谈"）。
- 前台：展示当前价格 + 历史变动记录。

对 F-001 提供一个只读判断：该车"价格是否已填写"（ADR-003 发布校验依赖，"面谈"视为已填写）。

按 ADR-007，车辆核心表（F-001）不落任何价格字段，价格与价格记录完全在 F-004 自己的存储里，通过 F-001 的技术主键关联。

## 我的方案倾向

- **价格不单独建"当前价格"表，用"最新一条价格记录"作为当前价格的唯一事实来源**（即当前价格 = 按时间倒序取最新记录的"变动后值"）。理由：避免"当前价格快照"和"历史记录"两份数据分裂，写入时只需一次 INSERT，天然满足"历史记录不可篡改"和"当前值与历史一致"这两个零容忍项，不需要额外的跨表事务同步。
- **价格值用判别类型建模**，例如 `{ type: 'amount', amount: number } | { type: 'negotiable' }`，而不是"数值字段 + 是否面谈布尔位"两个可能互相矛盾的字段并存。变动前值/变动后值都用这个统一结构存储，避免"面谈"和"数值"混填导致的脏数据。
- **首次设价不是"变动"，是"初始化"**：车辆刚建好、还没设过价时，不存在价格记录，"变动前值"应为一个显式的"未填写"值（而非 0 或空字符串），第一条记录的"变动前值"就是这个"未填写"占位，"变动后值"是管理员填的第一个价格。这样"价格是否已填写"= 是否存在至少一条价格记录，判断逻辑简单且没有死角。
- **价格修改需要与 F-001 编辑操作一样的乐观锁/并发保护**（参照 ADR-005 对 F-001 的处理），防止两个管理员同时改价时出现"变动前值"与实际当前值不一致的错乱记录。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 价格能否"清空"回未填写状态未定义 | 如果允许把已设价格清空为"未填写"，会出现"已上架车辆价格突然不满足发布前置条件"的悖论状态（车辆状态是"已上架"，但按 ADR-003 的口径已经不满足发布门槛）。需要明确：价格一旦设置，能否被清空；若能清空，是否连带触发车辆自动下架，还是允许"已上架但价格未填写"这个不一致状态长期存在。 |
| 高 | 并发改价缺少一致性保护 | brief 未提并发控制。两个管理员同时改价可能导致后写入的记录"变动前值"与实际当次真实的前一个值不符，直接违反 principles.md「价格历史记录丢失或错乱」零容忍项。 |
| 中 | "变动前值/变动后值"双存的设计本身有冗余风险 | 若实现时把"变动前值"独立写死在记录里（而不是从上一条记录派生），一旦某次写入出错（如漏写、脏数据回填），会导致相邻两条记录"后值"与"前值"对不上，历史链断裂却难以被发现。需要在实现层面强约束：新记录的"变动前值"必须等于该车最新一条记录的"变动后值"（或初始占位），不能允许调用方任意传入。 |
| 中 | 价格字段的数值精度、单位、取值范围未定义 | 未说明价格单位（元/万元）、是否支持小数、是否允许 0 或负数、上限。这类边界不清会导致前后台展示口径不一致，属于"内容准确"红线相关问题。 |
| 中 | 价格记录与车辆删除（F-005）的一致性边界未定义 | F-005 目前是空 brief，ADR-005 明确本期不预留软删除字段，届时要对 vehicles 表迁移。F-004 的价格记录以车辆技术主键关联，一旦 F-005 落地删除/恢复机制，需要明确删除车辆时价格记录是保留还是级联清理——级联清理会直接违反"价格历史记录丢失"零容忍项，必须显式禁止。 |
| 低 | "价格记录"对前台访客是否全量可见未在成功标准里限定范围 | brief 只说"访客能看到...价格变动记录"，未说明是否有条数上限/时间范围，长期运营后单车价格记录可能积累很多条，前台展示策略未定义。 |

## 对其他端的隐含要求

- **对 F-001**：F-001 的发布/重新上架动作需要在同一次校验里反查 F-004 的"该车是否存在至少一条价格记录"（ADR-003 已定），这要求 F-004 提供一个稳定、可被同进程内部调用的查询能力（不是简单前台 API），且该查询在车辆刚创建、F-004 尚未写入任何记录时必须返回明确的"未填写"而不是报错或空异常。此外，如果本评审"价格能否清空"的问题裁决为"允许清空"，F-001 的状态机（ADR-004：草稿→已上架⇄已下架，无退回草稿路径）需要重新评估"已上架车辆价格被清空后如何处理"，因为 ADR-004 现有状态机里没有对应的过渡动作。
- **对 F-002（前台车辆展示）**：F-002 目前 brief 为空，但 F-004 的成功标准要求"访客能看到当前价格和价格变动记录"，这意味着 F-002 的展示范围必须包含价格历史区块，而不仅仅是当前价格；F-002 评审时需要明确这一点，否则会漏做。同时按 ADR-005「`/public/*` 严格按 status 过滤」的原则，价格记录的公开查询接口也应只对"已上架"车辆开放，已下架/草稿车辆的价格历史不应通过前台接口可查——这条约束需要 F-004 自己的 contracts 里显式声明，不能假设 F-002 会做这层过滤。
- **对 F-003（图片与评估报告）**：无直接耦合，但两者都以 F-001 技术主键做关联锚点，F-004 的 contracts 设计应遵循同样的关联方式，避免出现车架号或其他标识混用。
- **对 F-005（回收站）**：F-005 尚未设计，但价格记录的保留策略必须在 F-005 的删除/恢复机制设计时提前对齐——F-005 评审时需要显式回答"车辆删除后，F-004 的价格记录是否保留、是否在回收站详情里仍可查看"，否则容易在 F-005 落地时才发现价格历史被级联删除。
- **对 F-006（后台账号管理）**：F-006 brief 目前为空，未定义角色权限模型。价格属于敏感经营数据，"后台账号越权"是零容忍项，F-004 需要 F-006 明确"改价权限"是否所有管理员账号都可执行，还是需要更高权限角色；这条应作为跨 feature 待裁决问题记录，不能在 F-004 内部自行假设为"所有管理员都能改价"。

## 我需要别人回答的问题

1. 已设置的价格能否被清空回"未填写"状态？如果可以，对已上架车辆意味着什么（是否自动下架、是否阻止后续操作、还是允许"已上架但未填价"这个状态长期存在）？
2. 价格数值的单位、精度、取值范围是什么（元还是万元、是否允许小数、是否允许 0 或负数、有无上限）？
3. 价格修改是否需要并发保护（乐观锁/事务串行化）？如果两个管理员几乎同时改同一辆车的价格，期望的行为是什么（后写覆盖、还是报错要求刷新重试，参照 F-001 ADR-005 的做法）？
4. 前台展示的价格变动记录是否有条数上限或时间范围限制？长期运营后单车记录条数不断增长，是否需要分页？
5. F-005（回收站）的删除机制落地后，被删除车辆的价格记录如何处理（保留/隐藏/仍可在回收站详情查看）？这需要 F-005 评审前给出方向，还是可以先在 F-004 内部按"永久保留、不级联删除"假设推进？
6. 改价操作是否对所有管理员账号开放，还是需要 F-006 定义的特定角色/权限？
7. 车辆首次创建（草稿阶段）时是否允许直接同时设置价格，还是价格只能在车辆已存在（有技术主键）之后单独设置？
