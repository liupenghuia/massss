## 我理解的需求

管理员在管理后台为车辆设置/修改价格，价格支持"具体数值"或"面谈"两种形式；每次价格变动都会自动生成一条不可篡改的价格记录（变动前值、变动后值、变动时间）；前台访客可见车辆当前价格与价格变动历史；本 feature 与 F-001（车辆核心信息）解耦——价格字段完全由 F-004 独立管理（ADR-007），但 F-001 的发布校验需要能读取"价格是否已填写"这一状态（"面谈"视为已填写，ADR-003）。价格显示错误、历史记录丢失或错乱属于 principles.md 的零容忍项。

## 我的方案倾向

principles.md 中 ADR-001 已明确：全项目（前台 + 管理后台）走 Web，不做微信小程序，移动端体验通过响应式/自适应网页兼容手机浏览器实现，不引入小程序技术栈。据此，F-004（价格设置、价格记录、前台价格展示）不涉及任何小程序特有能力，我的方案倾向是：

- 不需要评估 openid/unionid 获取时机、小程序类目资质与审核规则、`wx.authorize` 隐私接口与授权弹窗、分包与包体积——这些关注点在本 feature 中均不适用。
- 前台价格与价格记录展示页面按普通移动端网页处理即可，遵循 principles.md"移动端优先"的取向（响应式布局、竖屏优先），无需为微信小程序单独适配。
- 若未来出现"在微信内分享车辆价格页面"这类获客诉求，用 H5 网页在微信内置浏览器打开即可满足，不需要为此单独立项小程序，这与 ADR-001 一致，不构成对现有决策的冲击。

## 对其他端的隐含要求

虽然本 feature 不涉及小程序，但小程序评审关注点在 Web 语境下有等价物，会转化为对前台/管理后台/服务端的隐含要求，逐条列出：

1. **登录态等价物（管理后台）**：小程序视角关注 openid/unionid 获取时机，Web 语境下的等价关注点是管理后台的登录态（session/token）在改价操作上的校验时机。隐含要求：服务端的改价接口必须在写入价格记录前校验操作人登录态与权限，避免出现 principles.md 零容忍项"后台账号越权"。brief.md 目前定义的价格记录字段只有"变动前值、变动后值、变动时间"，未包含操作人标识——若涉及多管理员账号，隐含要求服务端在价格记录表中补充"操作人"字段以便审计追溯，这一点需要产品侧确认（见下节问题）。

2. **隐私接口/授权弹窗等价物（前台）**：小程序场景关注用户授权弹窗与隐私接口调用，Web 语境下的等价约束是 principles.md"前台无用户体系"——前台价格与价格记录展示页面不应采集访客任何身份信息、不引入需要用户授权的三方 SDK（含微信 JS-SDK 类接口），隐含要求前台该页面保持纯只读展示，不埋点采集用户身份。

3. **微信审核规则/类目资质**：不适用（不上架小程序/公众号服务）。若日后价格详情页需要在微信生态内被分享打开，隐含要求服务端提供的页面 URL 需具备正常的可分享性（合法的 HTTPS 域名、合适的 meta 信息），但这是一般 Web 分享的基本要求，不构成对小程序类目资质的依赖。

4. **首屏性能/分包等价物（前台）**：小程序关注分包与首屏加载，Web 语境下的等价要求是价格记录列表页面的首屏性能，尤其在 principles.md"移动端优先"的取向下。隐含要求：当某车辆价格变动记录条数较多时，前台/服务端应考虑分页或懒加载展示历史记录，避免一次性拉取全部记录拖慢移动端首屏——这一点需要在前台展示相关的 feature（而非 F-004 本身）中落实为具体的分页设计，此处仅作为跨端提醒。

## 我需要别人回答的问题

1. 价格记录是否需要记录"操作人"字段用于审计？brief.md 当前只定义"变动前值、变动后值、变动时间"三个要素，未提及操作人。若管理后台存在多个管理员账号，缺少操作人字段会削弱"后台账号越权"问题的可排查性（principles.md 零容忍项之一）。此问题超出小程序范畴，但请产品侧确认是否要在价格记录的字段设计中补充。
2. 是否存在通过微信生态（公众号文章、好友/群聊转发链接等）触达车辆价格页面的获客场景？如果存在，请确认现有 ADR-001（不做小程序，Web 页面在微信内置浏览器打开）是否已完全覆盖这一诉求，还是需要针对微信内置浏览器场景做专项体验优化（不在本 feature 范围内，但需要有人明确归属到哪个 feature）。
