## 我理解的需求

管理员可以给车辆设置/修改价格，价格取值为「具体数值」或「面谈」两种形式之一。每次价格发生变动，系统自动生成一条不可篡改的价格记录（变动前值、变动后值、变动时间）。访客在前台可以看到车辆的当前价格和价格变动历史。

本 feature 与 F-001 存在双向耦合：
- ADR-007 确定车辆核心字段（F-001）不包含价格，价格数据完全落在 F-004 自己的表里，通过车辆技术主键（ADR-005）关联。
- ADR-003 确定 F-001 的发布/重新上架动作要反查 F-004，判断"价格是否已填写"（"面谈"视为已填写），由 F-001 主动查询、F-004 不反向感知 F-001 的状态流转。

价格记录本身不做审批流程、不做批量改价、不做促销折扣（brief 明确排除）。

## 我的方案倾向

- **数据模型分两张表**：`vehicle_prices`（当前价格快照，按 vehicle_id 唯一）+ `price_change_records`（价格变动历史，append-only，按 vehicle_id + 自增序列/created_at 索引）。价格值统一用 `price_type`（AMOUNT / NEGOTIABLE）+ `amount`（NEGOTIABLE 时为 null）两列表达，避免用魔法数字（如 0 或 -1）表示"面谈"。
- **写路径原子性**：一次改价请求 = 更新快照表 + 插入一条历史记录，两者必须在同一数据库事务内完成，任一失败整体回滚，绝不允许"快照已变但历史记录没写"或反之——这是 principles.md 明确的零容忍项。
- **顺序性用数据库自增序列/事务串行化保证，不用应用层时间戳排序**（同一车辆的并发改价请求，时间戳可能精度不够或时钟回拨导致历史记录顺序错乱）。
- **改价接口要求幂等键**（沿用 ADR-005 对 F-001 创建接口的同一思路），防止前端网络重试对同一次用户操作重复生成两条历史记录。
- **"无实际变化"不生成历史记录**：仅当新值与当前快照值（含 type + amount）不同时才写历史记录，避免管理员重复点击"保存"刷出大量无意义历史。
- **F-004 对 F-001 暴露的判断能力做成同进程内的模块级查询函数**（不是走 HTTP 内网调用），因为 principles.md 明确"服务端合一"，两者在同一服务进程里，没必要为一次内部判断引入网络往返和额外的失败模式。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 快照表与历史表双写非事务化 | 如果实现时把"更新当前价格"和"写历史记录"拆成两次独立写入（例如先 commit 当前价快照，再异步/单独写历史），任何一步失败都会导致 principles.md 零容忍的"价格历史记录丢失或错乱"。必须强调用同一事务、同一次提交完成。 |
| 高 | 改价接口缺少幂等保护 | 若无幂等键，管理员在弱网环境下点击"保存"后重试，可能在服务端产生两条内容相同的历史记录，污染前台展示给访客的"价格变动记录"，属于零容忍范畴的"历史记录错乱"。 |
| 高 | 并发改价的顺序确定性 | 两个管理员几乎同时修改同一车辆价格，若无锁/无事务隔离保证顺序，可能出现"后提交的历史记录时间戳早于先提交的"这种乱序，或者两次写入互相覆盖丢失一条记录。需要行级锁或乐观锁（比照 ADR-005 对 F-001 编辑接口的乐观锁思路）。 |
| 中 | "价格是否已填写"查询在草稿态语义不清 | 车辆刚创建（草稿）尚未设置过价格时，F-004 侧没有任何记录，F-001 发布校验查询应返回"未填写"。需要明确：这个查询是查"当前价格快照是否存在"，还是"历史记录表是否非空"，两者在"从未设置过价格"的情况下结果一致，但实现选型不同，需要在契约里写清楚，避免 F-001、F-004 各自理解不一致。 |
| 中 | F-001 反查 F-004 失败时的降级策略未定义 | ADR-003 只定义了"校验通过/不通过"，没定义 F-004 内部查询本身出错（如数据库瞬时故障）时 F-001 该怎么办：阻塞发布报错，还是视为"未填写"直接拒绝发布？两种语义对运营体验影响不同，需要显式约定，不能隐式吞异常当成"未填写"处理（否则可能出现明明填了价格却发布不了，运营侧难以排查）。 |
| 中 | 价格记录数据量与索引未设计 | 车辆数量按 ADR-007 会持续增长（不是 100 台硬上限），加上每车可能有多次改价，`price_change_records` 需要 `vehicle_id + created_at`（或自增序列）复合索引支撑前台分页查询和后台列表查询，brief 未提及索引/分页设计，需要在 contracts 阶段补上。 |
| 低 | "改错价格"的纠正手段缺失 | 历史记录不可篡改意味着管理员手误改错价格后，只能再次改价"纠正"，但这会在前台的价格变动记录里留下一条对访客造成困惑的错误记录（例如从 10万→1万→10万）。brief 未说明是否需要某种"标记/隐藏错误记录"的手段，还是接受这个代价。 |

## 对其他端的隐含要求

- **对 F-001（车辆信息管理）**：F-001 的发布/重新上架动作需要在同一事务或至少同一次请求处理中调用 F-004 提供的"价格是否已填写"查询能力，且这个调用的失败语义（超时、DB 异常）需要与 F-004 共同约定，不能各自假设。此外，F-004 需要用 F-001 的车辆技术主键（自增 ID，ADR-005）作关联锚点，不能用车架号，F-001 若变更主键生成策略需要提前通知 F-004。
- **对 F-002（前台车辆展示）**：F-004 需要提供 `/public/*` 前缀下的两个只读接口——"当前价格"（单条）和"价格变动历史"（分页列表）。当前价格的序列化格式（数值 vs "面谈"）需要一个统一的结构（如 `{ type, amount }`），F-002 前端是"哑终端"（principles.md），不能自己判断展示逻辑，所有"该显示数字还是显示面谈文案"的判断必须由 F-004 在响应里给全，F-002 只做渲染。分页参数（页码/页大小/排序方向）需要 F-004 在 contracts 里定义清楚，避免 F-002 各自猜测默认值。
- **对 F-005（回收站）**：车辆被软删除后，价格记录归属如何处理（是否随车辆一起在前台隐藏、后台是否仍可查看历史）需要 F-004 与 F-005 提前对齐接口边界；虽然 ADR-005 决定本期不预留软删除字段，但 F-004 的价格记录查询逻辑（尤其是给前台的公开接口）需要预留"车辆不可见时价格记录也不可查"的过滤点，避免 F-005 上线时需要连带改造 F-004 的查询路径。
- **对 F-006（后台账号管理）**：brief 里价格记录只提到"变动前值、变动后值、变动时间"，没有提"操作人"。但 principles.md 零容忍"后台账号越权"，且 ADR-006 已经要求 F-001 记录操作日志（操作人、操作时间、车辆 ID、变更前后状态）。F-004 作为同样敏感的核心资产（价格），是否也需要在价格变动记录里落"操作人"字段，需要和 F-006 的账号体系对齐，这是我认为应当补齐的字段，而不是可选项。

## 我需要别人回答的问题

1. 价格变动记录是否需要记录"操作人"（对应哪个后台账号做的改价）？brief 目前只写了"变动前值、变动后值、变动时间"，但 principles.md 对越权零容忍，且 ADR-006 已经给 F-001 加了操作日志，F-004 是否比照办理？
2. F-001 反查 F-004 判断"价格是否已填写"时，如果 F-004 侧查询本身失败（如数据库异常），F-001 应该阻塞发布报错，还是视为"未填写"直接拒绝？这个失败语义谁来定义？
3. 车辆创建（草稿态）时是否允许在创建车辆的同一动作里直接带初始价格，还是必须先建车辆、再单独调用一次改价接口？如果是后者，"从空到有值"这第一次算不算一条价格变动记录？
4. 管理员改错价格后，是否需要提供"标记/隐藏某条历史记录"或类似的纠正机制，还是接受"错误记录也会永久出现在前台价格历史里"这个代价？
5. 价格变动历史对前台访客是否需要分页/限制展示条数上限？如果一台车改价几十次，是否全量展示给访客，还是只展示最近 N 条？
6. 价格记录是否需要对接 F-005 的软删除/恢复流程（车辆恢复后价格历史是否完整保留并重新对前台可见）？
