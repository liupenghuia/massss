## 我理解的需求

管理员可为车辆设置/修改价格（具体数值或「面谈」）；每次真实变动（与当前值不同）自动生成一条 append-only、不可篡改的价格记录（变动前值、变动后值、时间、操作人）。当前价格 = 最新一条记录的变动后值。访客在前台能看到当前价格与变动记录（展示策略推迟到 F-002）。F-001 发布校验需要能读取「价格是否已填写」状态（面谈算已填写）。价格不落在车辆表，独立管理。不做审批、批量改价、促销/折扣。

## 我的方案倾向

- 价格记录作为核心资产，测试应覆盖「变动判定」「幂等/无记录写入」「反查失败即报错」三条主线，这些是零容忍项（价格历史丢失或错乱）的直接防线。
- 边界值测试集中在金额校验（>0、最多2位小数、面谈与数值互转）和"完全相同不写记录"的判定上，这类规则最容易被实现悄悄放宽。
- 权限与可见性测试（未上架车辆前台不可查、回收站车辆记录处理）留到 F-005/F-006 落地时联调，本期只验证"不报错、不越权"的最小面。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | "变动判定"边界未给可验证的等价类清单 | spec 只说"面谈↔数值算变动；完全相同则成功且不写记录"，但未说明"数值 100.00 → 100.0 是否算相同"、"金额字符串格式不同但数值相等"是否算相同，需要精确到比较规则才能写自动化断言 |
| 高 | 反查失败报错的可观测性未定义 | "反查失败必须报错，不得视为未填写"——报错后 F-001 发布流程的表现（阻止发布/展示错误/重试）未说明，无法写端到端断言 |
| 中 | 并发改价无约束 | 同一车辆被两个管理员几乎同时改价，最终记录顺序/当前价格取决于写入时序，spec 未提是否需要乐观锁或允许脏写，影响"历史记录不可篡改/不可错乱"零容忍项的判定标准 |
| 中 | 创建草稿带初始价格与"首次设价"记录规则的交互未验证点 | "创建车辆可带初始价格"是否等价于"首次设价写记录，变动前=未填写"，还是创建时不产生记录、留待第一次显式改价才产生，两种实现验收结果不同 |
| 中 | 金额上限缺失的输入校验风险 | "不设上限"意味着需要测试极大数值（如 12 位数）在存储、序列化、前端展示时是否溢出或精度丢失，spec 未提数据类型（decimal/浮点） |
| 低 | "无二次确认"与误操作的可测性 | 不做二次确认意味着测试用例应验证"误改价后只能再改一次纠正"，无法撤销，需在验收标准中明确这是预期行为而非缺陷 |

## 对其他端的隐含要求

**服务端**：需暴露单车只读查询接口供验收测试直接断言价格状态与记录，不能只靠管理后台 UI 间接验证；反查失败需要有可辨识的错误类型（非静默 fallback）。

**管理后台**：车辆详情页改价表单需要对金额格式（2位小数、>0）做前端校验并与服务端一致，避免服务端拒绝但前端提示不明确。

**前台**：只做类型+金额的哑渲染，无展示逻辑分支，测试重点是"未上架车辆不返回价格数据"而非展示样式。

## 我需要别人回答的问题

1. "变动判定"的数值比较规则是否为四舍五入到 2 位小数后严格相等？字符串/数值类型不一致时如何判定相同？
2. 反查失败（F-001 进程内调用异常）时，发布流程应报错阻止发布，还是允许发布但记为未填写？
3. 并发改价场景下是否需要防止记录顺序错乱（如乐观锁/事务隔离级别），还是接受"后写入者生效"？
4. 创建车辆带初始价格时，是否生成一条价格记录（变动前=未填写），还是只写当前价格、记录留到下次改价才产生？
