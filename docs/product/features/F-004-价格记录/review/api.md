## 我理解的需求

管理员为车辆设置/调整价格（数值或「面谈」），每次真实变动都要生成一条不可篡改的价格记录（变动前值、变动后值、时间、操作人）；访客在前台能看到当前价格与价格记录；F-001 发布校验要能查到「价格是否已填写」（面谈视为已填写）；价格不落在车辆主表，独立管理（ADR-007）。当前 spec 已定稿为 append-only 记录表、不建当前价格快照表，当前价格取「最新一条记录的变动后值」。

## 我的方案倾向

- 价格记录表设计为 append-only，字段至少含：车辆技术主键、变动前值（类型+金额，可为空表示未填写）、变动后值（类型+金额）、操作人、created_at，主键自增或雪花 ID，不允许 UPDATE/DELETE，仅 INSERT。
- 唯一索引/查询索引建在 `(vehicle_id, created_at DESC)` 或 `(vehicle_id, id DESC)`，取当前价格用「按车取最后一条」，数据量级（百台车、每台改价次数有限）下无需额外快照表，直接查询即可满足性能，不需要引入缓存层。
- 「变动」判断（面谈↔数值、数值不同才写记录）必须放在服务端同一事务内做「读最新一条 + 比较 + 条件写入」，不能由调用方传入变动前值直接信任，防止并发下产生不一致的前值记录。
- F-001 发布校验的「是否已填写」通过进程内方法查询（spec 已定），该方法应直接查最新一条是否存在，避免维护冗余的已填写标志位，减少双写不一致风险。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 并发改价的读-比较-写非原子操作可能产生记录错乱 | 若两个管理员几乎同时改价，"读取当前值→比较是否变动→写入新记录"这一序列若不加事务/行锁，可能出现两条记录的"变动前值"都基于旧的当前值，导致价格记录链不连续，触碰零容忍项（价格历史丢失或错乱）。需要在实现层用事务 + 行级锁（如对该车最新记录加锁）或乐观锁保证串行化，spec 未明确写并发控制策略。 |
| 中 | "完全相同则成功且不写记录"的幂等语义未覆盖网络重试场景 | 若管理员端因超时重试同一次改价请求，第一次已写入记录，第二次因当前值已等于目标值而"成功不写记录"，这是合理的幂等结果；但若请求体本身允许省略/依赖客户端携带的"变动前值"做校验，则需要明确服务端以自己查到的当前值为准，忽略客户端传入的旧值，避免因客户端过期数据导致误判。 |
| 中 | append-only 表随时间增长，`vehicle_id` 查询若无合适索引会影响车辆详情页与发布校验的响应 | 当前 100 台车量级不明显，但价格记录逐台车持续追加，长期需保证 `(vehicle_id, created_at)` 或等价索引存在，否则"取最新一条"和"列出该车全部记录"都会退化为全表扫描。 |
| 低 | 删除车辆（进回收站）后价格记录不级联删除，留给 F-005，但需明确回收站保留期到期批量清理车辆时是否级联清理价格记录 | spec 已注明细节留给 F-005，此处仅提示：若 F-005 清理逻辑遗漏价格记录会造成孤儿数据长期累积，建议 F-005 评审时接住。 |

## 对其他端的隐含要求

**管理后台**：改价接口应做到失败时给出明确、可区分的错误（如车辆不存在 vs 未变动 vs 校验失败），前端按错误类型分别处理，不能把"未变动不写记录"当错误展示给用户。

**前台**：价格与价格记录均为只读展示，不应在前端做金额格式化以外的业务判断（如是否"已填写"），一律由服务端返回的数据形态决定。

**F-001（车辆发布）**：发布校验依赖 F-004 的进程内方法而非跨服务调用，若该方法调用失败（如异常），必须视为校验失败并报错阻断发布，不能静默放行导致未填价格的车辆上架。
