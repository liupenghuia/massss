## 我理解的需求

价格记录是一张 append-only 的表，挂在 F-001 车辆技术主键下：管理员可对已存在车辆设价/改价，或在建车辆草稿时带初始价格；每次「与当前值不同」的变动生成一条不可篡改记录（变动前值、变动后值、时间、操作人）。不建当前价格快照表，「当前价格」= 该车最新一条记录的变动后值；「已填写」= 至少一条记录，面谈视为已填写。价格一旦设置不可清空回未填写。前台/后台只读该车记录，本 feature 不做审批、批量改价、导出、二次确认、按状态筛车。ADR-015/016/017 已把绝大多数分歧收敛为「本期收窄范围」的裁决，spec 已进入 implementing。

## 我的方案倾向

单表 append-only + 「当前价 = 最新记录」的模型是对的：避免了快照表与历史表的双写一致性问题，是零容忍项（价格错乱）下最简单可靠的选择。「未填写」用显式占位值（非 0、非空字符串）也是正确的方向，避免和「0 元」「未设置」混淆。倾向在 contracts 层面把「未填写」占位固定成一个专门的类型态（如枚举 `UNSET`），不要用可空字符串隐式表达。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 中 | 创建车辆带初始价格的事务边界未定义 | spec 只说「创建草稿车辆时…内部走一次设价逻辑生成第一条记录」，但未说明车辆行（F-001）与首条价格记录（F-004）是否在同一数据库事务内提交。若非同事务且价格记录写入失败，会出现「车辆已存在但无价格记录」，此时该车会被判定为「未填写」，与创建者的意图不符；反过来若车辆创建失败但价格记录已写入，则出现孤儿价格记录（无主记录，违反「价格与车辆错配」类零容忍精神）。 |
| 中 | 「最新一条记录」的排序依据未明确 | 当前价格 = 最新记录的变动后值，但判定「最新」是靠单调递增的技术序列（如自增 ID/序列号）还是靠时间戳？若靠时间戳，在并发改价（同一车辆被两个管理员几乎同时提交不同价格）或服务器时钟回拨场景下，可能导致「当前价格」取到错误的一条，直接触碰价格显示错误的零容忍线。建议排序依据用单调递增的写入序号而非墙钟时间。 |
| 低 | 「完全相同则不写记录」的数值归一化规则未定义 | ADR-015 规定金额相同（类型+数值都同）时返回成功但不生成记录，用于避免误触刷历史。但「10.1」与「10.10」这类同值不同表示是否算相同，spec 未给出归一化口径（如统一存储为最小货币单位整数分）。规则本身不影响正确性红线，但会影响幂等判断是否可靠触发。 |

## 对其他端的隐含要求

**服务端**：需要给「当前价格」的判定选用不受并发/时钟影响的排序键（如自增序列），并保证「车辆创建+首条价格记录」在同一事务内提交或失败回滚，避免孤儿记录或未填写误判。

**管理后台**：改价表单需按 ADR-016 不做二次确认、不分权限，但应在 UI 上清晰区分「面谈」与「具体数值」两种录入模式，避免管理员在两种模式间误切换产生非预期的历史记录。

**前台**：目前只消费 F-004 给的类型+金额两个字段，无需额外状态判断；「未填写」占位不应该出现在 `/public/*` 返回里（只有已上架车辆可见，且发布前已强制过滤未填写车辆），前台无需处理该占位态，但如果服务端契约把占位值和「面谈」在字段结构上不做区分，会给前台埋误判风险。
