## 我理解的需求

车辆删除采用软删除：在 `status`（草稿/已上架/已下架）之外新增正交字段 `trashedAt`/`purged`，
不并入原三态状态机。删除、恢复、到期彻底清除构成第二条独立生命周期线，二者通过「公开可见性 =
`published AND trashedAt IS NULL`」以及「所有写接口需排除 `trashedAt IS NOT NULL`」两条规则耦合。
恢复后一律落草稿，重新走发布前置校验；彻底清除只置 `purged=true`，主记录不物理删除，对象存储异步
删除，价格记录永不级联删除。

spec.md 已完成 26 项裁决并落地 RFC，正交字段建模方式清晰、状态转换表无死状态、幂等语义已写明，
本轮评审在此基础上，只补充尚未覆盖的领域风险。

## 我的方案倾向

正交字段（而非把 trashed 塞进 `status` 枚举）是对的：避免了「回收站中的已上架车」这种需要在三态
基础上再叠一维的状态爆炸，公开可见性判定条件单一（两个字段的 AND），符合"状态机自洽、无歧义"的
要求。赞成维持现状，不建议改回单一状态机。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 中 | 清除任务与恢复请求的并发一致性边界未落到数据层规则 | spec 只写"恢复请求优先于尚未跑完的清除任务"，但清除任务是"扫描→逐条处理"，若恢复发生在扫描之后、更新 `purged` 之前，会形成竞态窗口。建议清除任务对每条记录用乐观锁（`version`）或"清除前重查 `trashedAt IS NOT NULL`"做二次确认，这属于实现约束而非需要用户裁决的业务规则，标记为风险不升级为问题。 |
| 中 | 对象存储异步补偿删除缺少终止条件 | "可补偿重试"未定义重试上限/死信处理，长期失败的文件会永久占用存储成本（principles 里图片是主要成本项，成本上限 500/月），建议实现时补充最大重试次数与告警，不阻塞本 feature 定稿。 |
| 低 | `purged=true` 记录永久保留导致 `vehicles` 表只增不减 | spec 已作为已知限制记录且本期不做归档，量级一百台以内风险很低，仅记录以防未来遗忘。 |
| 低 | VIN/主键彻底清除后永久禁止复用 | 若现实中同一台实体车辆被清除后又被重新收购入库，需要建一条新记录且无法复用原 VIN 建立关联；这是已在 spec/ADR-030 中拍板的设计，不重开，仅提示这是一条真实业务约束，不是技术副作用。 |

## 对其他端的隐含要求

- **服务端**：清除定时任务与恢复接口之间需保证对同一条记录的操作互斥（乐观锁或二次校验），避免恢复后紧接着被误清除。
- **管理后台**：需在回收站列表 UI 上体现「只读」边界（禁用编辑类按钮而非仅靠后端拒绝），避免用户点击后才收到 409。
- **前台**：无隐含要求，本 feature 不改前台展示逻辑，前台侧风险为零。
