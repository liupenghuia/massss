## 我理解的需求

回收站是管理后台内部功能，不涉及小程序（ADR-001 已确认不做）。我从「微信内 H5」视角评审的
是：车辆被删除/清除后，是否会在微信环境下（好友分享卡片、微信内置浏览器打开 `/public/*`）
出现"零容忍"要求的残留可见问题；以及回收站相关改动是否对前台微信内 H5 打开体验有隐含要求。

spec.md 已明确：公开接口对回收站中及已清除车辆一律返回 404，ADR-019 零缓存（TTL=0），前台不
改展示逻辑、继续只打 `/public/*`。

## 我的方案倾向

- 认可 spec 现有方案：服务端 404 兜底 + TTL=0，是微信内 H5 环境下阻止"删除后仍可见"最可靠的
  手段，不依赖前端/微信侧任何配合。
- 已知限制里"微信分享卡片标题/封面无法强制撤回，书面接受"这一条判断合理，不建议在本 feature
  内新增撤回机制（成本高且微信侧无官方接口支持主动撤回卡片缓存）。
- 建议详情页 404 态在微信内置浏览器里要有清晰的中文提示与返回入口，而不是白屏或原生错误页
  （这属于前台展示层，非本 feature 直接负责，但请求路径命中回收站车辆时后端应返回可被前端
  正常渲染的 404 语义，而不是裸 HTTP 404 页面）。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 中 | 微信分享卡片点进后仍显示旧标题/封面，用户点击"查看详情"才触发 404 | spec 已书面接受该限制，但需确认前台详情页对 404 车辆的降级 UI 已设计（是否属于本 feature 交付物，还是留给前台 feature），避免出现"点进去白屏"这种可带上线之外的真实缺陷 |
| 低 | 微信内置浏览器对被删除车辆的旧链接会命中浏览器/微信自身的页面缓存 | TTL=0 只控制服务端响应缓存，微信 X5 内核对同一 URL 短时间内可能仍走本地缓存展示旧 DOM，属已知限制范畴，无需新增机制，但建议在「已知限制」里补一句以免被误当遗漏 |

## 对其他端的隐含要求

- 服务端：对回收站中/已清除车辆返回的 404，响应体需带业务错误码（如 `VEHICLE_NOT_FOUND`）供前台识别渲染友好提示，不能只是裸 404 状态码。
- 前台：微信内置浏览器按普通手机浏览器测（principles 已定），详情页需处理"车辆不存在"这一异常态并给出返回入口，不能空白。
- 管理后台：本 feature 主战场，无微信侧隐含要求。
