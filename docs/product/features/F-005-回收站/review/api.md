## 我理解的需求

`vehicles` 表用正交字段 `trashedAt`/`purged` 实现软删除，不并入 F-001 三态状态机。删除/恢复接口
带乐观锁，公开端一律用 `published AND trashedAt IS NULL` 过滤且零缓存；每日定时任务扫描到期
（30 天）记录做彻底清除，主记录保留、`purged=true`，对象存储文件异步补偿删除，价格记录不级联删。
所有在管列表与写接口都要额外排除 `trashedAt IS NOT NULL` 的车辆。spec.md 已给出较完整的状态机、
接口边界与前置依赖，本评审在此基础上核对服务端实现层面的幂等/并发/数据量/迁移/补偿风险。

## 我的方案倾向

- `trashedAt`/`purged` 均需建索引：在管列表按 `trashedAt IS NULL` 过滤、回收站列表按
  `trashedAt DESC, id` 排序、定时清除任务按 `trashedAt <= cutoff AND purged = false` 扫描，
  三类查询共用一个复合索引 `(purged, trashedAt)` 即可覆盖，百台量级下无需分表。
- 迁移只加两个可空字段，不需要回填历史数据、不改变现有查询语义，属于低风险迁移；但**所有已有
  的"在管列表"/"公开列表"查询点都要逐一加上 `trashedAt IS NULL` 条件**，这是本迁移真正的风险点
  ——遗漏一处即破坏"已删除车辆仍在前端可见"的零容忍红线，建议迁移完成后对现有写接口/查询接口
  做一次穷举核对（Grep `WHERE`/ORM 查询构造处），而不是只信任评审文档。
- 定时清除任务的补偿重试用"下次调度自然重试"已经足够（spec 已定），但对象存储异步删除失败需要
  记录失败原因/次数，避免无限重试同一失败对象；建议清除时记录一条本地补偿日志（哪怕只是一行
  日志或简单状态字段），而非纯靠外部对象存储返回值静默重试。
- 乐观锁 + 幂等短路的检查顺序（spec 已定：不存在 → 已清除 → 幂等短路 → 状态特有分支 → 乐观锁）
  是合理的，能避免"重复点击删除"因版本号不一致而报错，认同该设计。

## 反对/风险
| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 删除与恢复期间的并发写競态未覆盖到"删除瞬间正在进行中的写请求" | 管理员 A 正在保存草稿/发布（写接口 A 已通过"未在回收站"校验，正在提交），管理员 B 同时执行删除，若两者提交顺序交错，可能出现"车辆已在回收站但刚保存的编辑生效"或反之。乐观锁能防止覆盖，但要确认删除接口与其余写接口用的是同一份 `version` 字段、同一事务隔离级别，否则乐观锁形同虚设。 |
| 中 | 定时清除任务与恢复请求的竞态窗口 | spec 要求"恢复请求优先于尚未跑完的清除任务"，但清除任务通常是批量扫描+逐条处理，若某条记录已被清除任务读出准备处理、此时恢复请求先落库改了 `trashedAt=NULL`，清除任务后续写 `purged=true` 时需要用乐观锁或"处理前重新校验 trashedAt 未变"兜底，否则会把已恢复的车误标记为已清除。 |
| 中 | 对象存储异步删除与"半清除窗口内直链可能短暂仍可访问"已知限制 | spec 已书面接受，但未定义补偿的最大重试次数/失败后的可观测性（日志、告警），长期堆积失败任务无人发现会导致存储成本持续增长，与"月度云支出上限 500"的原则冲突，建议至少记日志可追溯。 |
| 中 | VIN/主键"彻底清除后禁止复用"如何保证 | 若主键是自增 ID，天然不复用；若涉及 VIN 唯一性校验，需要确认唯一索引是否包含 `purged=true` 的记录（即 VIN 唯一约束在整表范围生效，不因清除而释放），否则未来新建车辆可能撞车。 |
| 低 | 回收站关键字搜索的查询性能 | 百台量级下无索引问题，但若关键字命中车架号/车型等多字段模糊匹配，建议复用 F-001 现有搜索实现，不新增全文索引，避免重复建设。 |

## 对其他端的隐含要求
- 管理后台：所有编辑/发布/改价/改图等写操作触发前，必须先判断 `trashedAt`/`purged` 只读字段禁用对应按钮，不能只靠服务端 409 兜底导致用户点了没反应。
- 管理后台：回收站列表与在管列表是两个独立入口/路由，不能复用同一分页状态，避免筛选条件串页。
- 前台：无需改动，但如遇缓存层（CDN/网关）需确认对 404 响应遵循 TTL=0，不做旧链接的边缘缓存。
