## 我理解的需求

管理员可将草稿/已上架/已下架的车辆删除进回收站（`trashedAt` 正交字段，不并入 F-001 三态），
进站后前台立即 404 不可见。回收站保留约 1 个月，到期由每日定时任务彻底清除
（`purged=true`，主记录保留、对象存储异步删除、价格记录不级联删）。恢复后车辆一律落草稿，
可再编辑/保存/发布（复用原公开 URL）。删除/恢复接口对称、幂等、带乐观锁；删除需二次确认，
恢复不需要。回收站列表独立、只读、支持关键字搜索与分页，不做批量操作与导出。

## 我的方案倾向

- 用状态矩阵（trashedAt × purged × originalStatus）驱动测试用例设计，而非按接口枚举，
  可系统性覆盖“进站前状态是否影响恢复后行为”“重复删除/恢复幂等”“已清除后再操作”等分支。
- 保留期与定时清除是时间驱动逻辑，建议时钟可注入（mock 当前时间）而非等真实 30 天，
  否则该场景在自动化中不可验证。
- 乐观锁并发场景（删除与恢复竞态、清除任务与恢复竞态）需要专门的并发用例，人工点击难以复现，
  必须走接口层自动化。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 恢复请求与清除任务竞态的可测性未定义 | spec 称“恢复请求优先于尚未跑完的清除任务”，但清除任务是异步批处理，如何在自动化测试中稳定触发“任务正在跑到一半时发起恢复”这一时序未给出机制（如任务锁粒度、单条处理是否可中断）。没有可观测的中间态，此项验收标准无法转成确定性用例。 |
| 高 | 半清除窗口内前台仍可能命中直链的时间边界未定义 | “对象存储异步删除、可补偿重试”与“前台零容忍不可见”是两条规则的叠加：数据库层已 404，但已知限制里承认对象存储直链可能短暂可访问。需要明确“短暂”的上限（如必须在 N 分钟内完成），否则该风险无法设阈值断言，也无法判断上线是否达标。 |
| 中 | 到期清除的“今天恰好到期”边界未给出精确判定规则 | 保留期按“trashedAt + 30×24h ≤ now”计算，但删除时间精确到时分秒，管理后台展示的是“剩余保留天数”（整数天）。天数展示的四舍五入/取整规则未定义，可能出现列表显示“剩 1 天”但下一次任务扫描已判定到期清除的展示与实际不一致，需明确取整方向（向上/向下）。 |
| 中 | 重复删除“不刷新 trashedAt”与前端展示的联动未覆盖 | 若管理员对已在回收站的车辆重复点击删除（如误触或网络重试），返回幂等成功但保留期不变；管理后台是否需要提示“该车辆已在回收站，保留期未变”？若无提示，用户可能误以为重新计时，属于体验歧义而非纯接口问题，建议明确前端提示文案要求或验收标准里加一条断言。 |
| 中 | F-006 账号停用后会话失效的“立刻”生效边界未定义 | spec 要求账号停用后“立刻”不能删除/恢复，但“立刻”依赖 F-006 的会话失效机制（是即时踢出还是下次请求校验时失败）。若是后者，停用瞬间已在途的请求是否允许完成，未定义，影响该联动项的可测性判定标准。 |
| 低 | 关键字搜索的匹配字段范围未列出 | 回收站列表“支持关键字搜索”，但搜索字段（车型/VIN/id 是否都算）未列出，只能按在管列表的搜索规则类推，若两者字段范围不同会导致用例设计基线不一致。 |

## 对其他端的隐含要求

- **服务端**：定时清除任务需暴露可测试的触发/时钟注入方式（而非仅靠 cron 真实等待），否则到期清除场景无法自动化回归。
- **管理后台**：需对“已清除车辆”“回收站中车辆”“重复操作幂等成功”三种情形分别给出明确的空态/禁用态/提示文案，供 UI 自动化断言可用的 DOM 标识或文案锚点。
- **前台**：需确认 404 响应体格式（是否与其他 404 场景一致）以便前台错误页/测试用例复用同一断言逻辑，不需要为回收站单独适配。

## 我需要别人回答的问题

1. 恢复请求与清除任务的竞态，是否有可观测的中间状态或任务粒度（如逐条加锁）供自动化测试触发和验证“恢复优先”这一规则？
2. 对象存储异步删除后前台仍可能短暂可访问的时间窗口，是否有明确的上限阈值（如 5 分钟内完成）作为验收标准，还是仅作为已知限制不设阈值？
3. 管理后台“剩余保留天数”的取整规则（向上取整/向下取整）是什么？
4. 回收站列表关键字搜索覆盖哪些字段，是否与在管列表搜索规则一致？
