## 我理解的需求

管理后台新增一个独立的「回收站」列表页，与在管列表互斥。管理员可对在管车辆（草稿/已上架/已下架）执行删除，删除后车辆进入回收站，前台立即不可见；回收站内车辆完全只读（可查图片/报告/价格历史，不可编辑/发布/下架/改价/改图），支持关键字搜索、分页、删除时间倒序展示，展示到期日/剩余天数；恢复操作把车辆落回草稿态，不需二次确认，删除需二次确认；任何已登录管理员可操作全部回收站记录，不做记录级权限、不做批量操作、不做导出。保留期 1 个月，到期由服务端每日任务自动彻底清除，管理端对已清除记录仍可按 id 只读检索。

## 我的方案倾向

- 回收站作为独立路由/菜单项，不与在管列表复用同一张表格组件的可编辑态，直接用只读态渲染，避免因误改共享组件导致回收站内出现可编辑入口。
- 列表行内提供「恢复」按钮（费茨定律：高频操作大而近），删除操作放在在管列表的行内/详情页而非回收站页。
- 删除二次确认用弹窗提示「删除后前台立即不可见，1 个月后自动彻底清除且不可恢复」，让管理员理解后果；恢复不加确认，符合 spec 定义。
- 剩余保留天数、到期日直接使用服务端返回字段渲染，不在前端做日期计算，避免时区/时钟不一致（服务端已用 Asia/Shanghai 计算）。
- 已清除车辆的只读检索做成回收站页内的单独 tab 或搜索模式切换，而非独立页面，减少入口数量。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 乐观锁冲突（409）与幂等成功的区分未在前端体现会导致误导 | trash/restore 均带 version；若前端把"已在目标态幂等成功"和"version 冲突失败"用同一套提示，管理员会误以为操作失败而重复点击，需分别设计提示文案。 |
| 高 | 已彻底清除记录与回收站中记录共用一个页面查询时，若前端未区分 `purged` 状态展示，管理员可能对"已清除"记录误触发恢复 | `AdminRecycleBinItem` 结构未明确是否会把已清除记录也混在回收站列表分页结果里返回；若是，前端需按 `purged` 隐藏恢复按钮并提示"已彻底清除，不可恢复"。 |
| 中 | 回收站列表与已清除车辆检索是否为同一个查询接口/同一套字段未定，直接影响页面结构（一个列表 vs 一读一查） | 需要明确接口设计后再定 UI 结构，避免做完后返工。 |
| 中 | 删除操作入口在在管列表按钮較多（编辑/下架/删除等），费茨定律要求高频操作大而近，但删除是低频破坏性操作，需与常用操作做视觉区分（如置于更次要位置、用警示色）防止误触 | 属于本端可自行把控的交互细节，非阻塞问题，记录以防实现时被忽略。 |
| 中 | F-006 账号停用后需要「立刻」使已登录管理员的删除/恢复会话失效，前端需在收到鉴权失效响应后统一跳转登录，而非在回收站页单独处理 | 需确认是否已有全局的 401/会话失效拦截器（跨 feature 依赖 F-006），若无需与 F-006 协调，非本 feature 内独立解决。 |
| 低 | 回收站里删除时间倒序 + id 二级排序，分页/搜索无匹配返回空结果不报错，前端需正确渲染空态（符合 principles 异常态必须有对应界面的要求），不是"可带上线"瑕疵而是硬性要求 | 提醒实现时补空态、加载态、错误态三种界面，容易被当作简单列表漏做。 |

## 对其他端的隐含要求

- 服务端：`AdminRecycleBinItem` 是否包含 `purged` 标记以及分页接口是否会把已清除记录一并返回，需要明确字段与查询语义，否则前端无法正确区分展示。
- 服务端：需确认回收站列表与已清除车辆按 id 检索是否为两个独立接口，还是同一查询的不同参数，直接决定管理后台页面结构。
- 服务端（跨 F-006）：账号停用后使会话立即失效的机制（token 黑名单/主动踢出）需明确触发方式，管理后台才能据此统一处理跳转登录。
