## 我理解的需求

访客无需登录，通过 `/public/*` 只读接口浏览已上架车辆的列表（聚合卡片：核心字段 + 封面图 + 当前价）与详情（图片、评估报告、价格历史）。服务端负责：状态过滤（published 硬过滤）、当前价计算、搜索/筛选（关键字、价格区间、年份区间、里程区间，AND 组合）、分页（固定 pageSize=20，id 降序）、字段脱敏（禁止 VIN、操作人、内部备注、version 泄漏）、GET 禁缓存（TTL=0）、IP 级限流。前台是哑终端，不做任何本地过滤/排序/价格计算。本 feature 不新增任何写入能力。

## 我的方案倾向

- 「当前价」建议在车辆表冗余一个只读投影字段（写价格记录时同步更新），而不是每次列表查询都对每台车做子查询取最新价格记录 —— 100 台规模内两种方式性能都够用，但冗余字段能让价格区间筛选直接走索引，避免后续量级增长后退化成关联子查询 + 全表扫描。
- 关键字模糊匹配（品牌+车型，不区分大小写 trim 后 LIKE）在百台量级下无需特殊索引，直接全表扫描可接受；不建议现在引入全文索引或搜索引擎，避免过度设计（YAGNI），但应在代码里留注释标注这是量级依赖的简化实现。
- 价格区间 / 年份区间 / 里程区间三个维度建议建组合索引或至少各自单列索引，配合 `published` 状态列做联合索引（如 `(published, price_current)` `(published, register_year)` `(published, mileage)`），避免筛选走全表扫描叠加分页。
- IP 级限流若服务端合一部署为单实例，用进程内存计数即可；一旦水平扩展需要切到集中式存储（如 Redis），建议现在就把限流实现封装成可替换的接口，避免以后扩容时的返工成本，但不必现在就接入 Redis（无该依赖时不引入新依赖）。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 中 | 「当前价」计算方式未定 | spec 只说「服务端计算」，未定是冗余字段实时更新还是每次查询时子查询最新价格记录。后者在价格区间筛选 + 分页组合下容易导致全表扫描或 N+1 查询，需要在实现前定下来，否则后续改存储结构是迁移成本。 |
| 中 | offset 分页与实时变化数据集的一致性 | 列表用 `id` 降序 + offset 分页，若翻页间隔内有车辆上下架，会出现漏看或重复看到某条记录。前台无用户身份、无会话状态，这个瑕疵可接受，但需要写清楚这是已知代价而非缺陷，避免后续被当 bug 提出。 |
| 中 | IP 限流的存储与部署形态耦合 | spec 只写「加基础 IP 级限流」，未定实现载体。若用进程内存计数，多实例部署时限流形同虚设；若现在就接 Redis，属于新依赖，需先问用户。建议先按单实例内存实现，接口层留出可替换的抽象。 |
| 低 | 关键字模糊匹配无法走索引 | LIKE '%kw%' 在百台规模无压力，但 overview 提到车辆总量级预计增长，此实现方式是量级敏感的，建议代码注释标注，避免后续误以为是永久方案。 |
| 低 | 详情页 404 与旧图片直链仍 200 的不一致 | spec 已判定为可接受的已知限制（ADR-009/019），非本轮新风险，仅确认无遗漏。 |

## 对其他端的隐含要求

- **前台**：分页与筛选参数需严格按服务端返回的 `items`/分页信息渲染，不得因为「当前价」在极端情况下（新上架但尚无价格记录）为空而自行拼装展示文案。
- **管理后台**：编辑车辆价格时应确保「最新价格记录」写入与车辆当前价（若采用冗余字段方案）在同一事务内完成，否则前台可能读到不一致的中间态。
- **管理后台**：无其他新增写入面要求，本 feature 明确不改车辆/图片/价格写入接口。

## 我需要别人回答的问题

1. 「当前价」是车辆表冗余字段（写价格记录时同步更新）还是查询时实时从价格记录表取最新一条？这决定索引设计与写路径的事务边界。
2. IP 级限流现在按单实例进程内存实现即可，未来水平扩展时再引入集中式存储，是否认可这个分期方案？
