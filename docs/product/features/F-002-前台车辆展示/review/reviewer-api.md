## 我理解的需求

F-002 是访客侧只读展示：不登录、Web 打开链接，浏览**已上架**车辆的列表与详情。前台是哑终端，只渲染 `/public/*` 已返回的数据，不做上架过滤、不做「面谈还是数字」判断。

成功标准要求详情含公开信息、图片（含说明）、评估报告、当前价格与价格变动记录。brief 写明：**展示条数、是否分页、面谈文案（如「面议」）必须在本 feature 内定稿**。草稿 / 已下架 / 回收站车辆前台不可见，过滤在服务端按 published，前台不二次判断。评估报告按 ADR-010 新标签打开原文件直链；图片按公开接口顺序与直链展示。手机竖屏优先。

明确不做：登录/收藏/询价/对比/交易、SEO SSR、小程序、前台状态过滤与价格类型判断、任何车辆/图片/价格写入接口。

现有契约（`contracts/openapi.yaml`）已提供只读公开路径，且声明不覆盖 F-002 的页面结构与展示文案：`GET /public/vehicles`、`GET /public/vehicles/{id}`、`GET .../images`、`GET .../reports`、`GET .../price`、`GET .../price-records`。列表响应不含价格与图片；公开详情不含 VIN；价格为 `{type, amount}`，不规定「面议」文案；价格记录预留分页，默认条数未定（ADR-017 取代 ADR-014 的「最近 20 条」）。

## 我的方案倾向

- **不新增写入、不拆微服务。** 前台与后台同服务，`/public/*` 无鉴权、只读。F-002 以现有公开契约为事实来源，缺展示字段时优先「后台加字段 / 改公开响应」，而不是前台拼业务。
- **可见性只信服务端硬过滤。** 列表与详情、图片、报告、当前价、价格记录一律只查 `published`；非 published 或不存在一律 `404 VEHICLE_NOT_FOUND`，禁止 403、禁止客户端传 `status`。回收站（F-005）若引入删除态，公开查询必须继续排除，不能把过滤推给前台。
- **幂等。** 公开接口全是 GET：重复请求无副作用。价格记录分页必须稳定排序（契约已写时间倒序）+ 稳定 `page`/`pageSize`，避免重试或「加载更多」跳页、漏条、重复条。列表默认 `id` 降序，分页按可增长规模设计（ADR-007：一百台是当前规模不是硬上限）。
- **竞态。** 管理员下架/进回收站与访客浏览并发时：列表已发出、详情稍后请求可能 404，属正确行为；禁止缓存把已下架车继续当 200。对象存储直链下架后不失效（ADR-009/契约）：公开接口不得再返回这些 URL，但直链本身仍可被收藏/转发打开——这是已知取舍，F-002 不能靠前端藏链接来满足「已删除车辆仍在前端可见」零容忍（可见性以 `/public/*` 查询为准）。
- **聚合 vs 多次请求。** 现状列表无封面、无价格，详情无价格；前台若要卡片有图有价，必须 N+1 打 images/price。车辆量级小，可接受，但移动端优先时倾向在公开列表（或详情）由服务端下发展示所需最小聚合字段（封面 URL、当前价 type/amount、面谈展示文案），避免前台自行拼装。**是否改契约须用户裁决，禁止本评审擅自当已定。**
- **面谈文案。** principles 要求展示逻辑由后台数据决定。倾向公开价格响应增加服务端给出的展示字符串（或等价结构化 display），前台只渲染；若坚持文案写死在 Web，则违背哑终端，且与 brief「本 feature 定稿文案」冲突点必须显式裁决。
- **索引与成本。** 公开列表过滤 `status=published` + 分页，`status`（及排序键）需有索引。价格记录按 `vehicleId + createdAt` 查询。图片走对象存储 + CDN，不进应用盘。公开 GET 可短缓存，但**下架必须尽快失效**（短 TTL 或主动刷新），价格错误与下架仍可见同属零容忍。
- **失败重试。** 前台对 5xx 可重试 GET；对 404 不得重试当成功、不得回退展示过期本地副本冒充仍上架。报告/图片直链失败由浏览器处理，服务端不转码、不代理文件（与 ADR-010 一致）。
- **向后兼容。** F-002 不应改 F-001/003/004 写入。若必须给列表加封面/价格/文案，走 RFC 扩公开响应，保持字段只增不改语义；公开端继续禁止出现 `vin` / `operatorId`。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 面谈文案与「哑终端」未对齐 | brief 要求本 feature 定稿「面议」等文案，契约与 ADR-017 规定 F-004 只给 type+amount、不下发文案。若文案只存在于前台，前台就在做业务判断，违反 principles。未裁决则无法实现且不踩红线。 |
| 高 | 价格记录展示条数/分页未定 | ADR-014「最近 20 条」已作废。默认 pageSize、是否全量、列表是否「加载更多」未定。不定稿则实现者会猜，移动端一次拉全量或漏展示都会在联调爆。 |
| 高 | 下架/删除与 CDN/直链竞态 | `/public/*` 可立刻 404，但图片/报告/可能的 HTTP 缓存仍可能打到旧资源。价格或车已下架而图还在分享链上，触达「已删除车辆仍可见」「图车错配」的边缘。公开接口过滤不够，还要定缓存失效策略。 |
| 中 | 公开列表不含图与价 | 契约明确列表无 vin/价格/图片。卡片若需要封面与当前价，前台会对每车额外请求，放大失败面与竞态（列表里还在、price 已 404）。是否扩列表 DTO 未定。 |
| 中 | 浏览中途 404 的产品语义 | 非 published 一律 404，不区分不存在、下架、回收站。前台无法展示「已下架」而只能当找不到。是否接受未写。 |
| 中 | 列表排序仅 id 降序 | 无「最近上架/最近改价」等运营排序。若产品期望按更新时间，现契约不够，且会涉及索引。 |
| 中 | 无请求限流与枚举成本 | `/public/*` 无登录，可按 id 扫详情。规模小但价格历史与直链仍可被爬。是否限流、是否接受被枚举未定。 |
| 低 | 分享元信息未在公开契约 | ADR-017 将微信打开与分享信息归 F-002。无登录 SSR；分享图/标题若要做，缺公开字段或 HTML 头策略，易被做成前端写死。 |

## 对其他端的隐含要求

- **对 F-001（车辆与状态）**：公开列表/详情继续只返回 published；状态变更后公开查询立即不可见。编辑已上架字段不改 status（ADR-004），公开详情会马上读到新字段，F-002 无草稿预览。主键稳定，禁止公开端出现 VIN。列表排序/分页变更需改公开车辆契约，不是前台本地排。
- **对 F-003（图片与报告）**：公开 images 必须按「当前排序」全量有序返回说明与直链，顺序即展示顺序，前台不得重排。公开 reports 按 uploadedAt 倒序给原文件 URL。下架不失效直链，因此公开列表不得再包含该车媒体；已上架删图跌破 4 张由 F-003 拒绝，F-002 不校验张数。objectKey 不得进公开响应。
- **对 F-004（价格）**：公开当前价与记录仅 published，否则 404。响应保持结构化 type+amount，无操作人。分页参数已预留，**默认条数与是否允许拉全量由 F-002 裁决后必须写回契约说明**，避免 F-004 实现自选 20。若裁决「文案由服务端下发」，F-004 公开 DTO 要扩字段，走 RFC，不能让 Web 根据 type 分支。
- **对 F-005（回收站）**：删除/恢复不得让前台靠猜状态。回收站中的车对所有 `/public/vehicles*`（含 images/reports/price/price-records）必须与未上架相同（404）。软删字段不能泄漏到公开 JSON。
- **对 F-006（账号）**：前台无用户体系，公开接口禁止依赖登录、cookie、CSRF 用户态。管理员会话不得误绑到 `/public/*`。
- **对管理后台前端**：上下架/改价/改图后，运营用同一条访客链接应立刻看到新结果或明确「下架即 404」。不要假设前台还会显示「已下架」占位。改价频率影响价格记录体积与公开分页。
- **对前台 Web（本 feature 实现方）**：只消费 `/public/*`；禁止请求 `/admin/*`、禁止传 status、禁止本地判断面谈 vs 数字（除非用户明确把文案裁定为前端常量，且那会与 principles 冲突，需记录 ADR）。列表若契约无图无价，不得用管理接口补。报告只用返回的 url 新开标签，不下载转码。404 不得展示缓存里的旧价旧图冒充仍在售。
- **对 CDN/对象存储**：直链与缓存策略必须服务「下架后公开 API 不再返回」；短缓存可接受展示瑕疵，但不能把错误价格或已下架车详情缓存成长期 200。
- **对契约仓库**：F-002 定稿的条数、分页、文案归属、列表是否聚合封面/价格，若与现 OpenAPI 不一致，必须 RFC 后改 `contracts/`，F-002 实现不得私自加未契约字段。

## 我需要别人回答的问题

1. 价格「面谈」在前台的展示文案是否唯一固定为「面议」？由公开接口下发字符串，还是允许前台写死？多种文案是否要支持？
2. 价格变动记录前台默认展示几条？是否分页/加载更多？是否允许访客看该车全部历史？pageSize 上限是多少？
3. 车辆列表是否必须展示封面图和当前价格？若必须，是否扩 `GET /public/vehicles` 聚合字段，还是允许前台对每条再打 images/price？
4. 访客打开已下架/回收站/乱猜 id 的详情时，是否一律当「不存在」，还是需要可区分文案（仍不能暗示车曾存在）？
5. 公开车辆列表除 `id` 降序外，是否还要按上架时间、更新时间或其他运营排序？
6. 公开 GET 是否允许 CDN/HTTP 缓存？下架或改价后可接受的最长可见延迟是多少？
7. 评估报告多份时，详情默认打开哪一份、是否全部列出？契约是 uploadedAt 倒序列表，产品是否要「主报告」标记？
8. 微信/浏览器分享时，标题、摘要、分享图从哪来？是否要公开接口或静态页提供？本 feature 是否包含分享信息，还是只保证链接能打开？
9. 公开接口是否需要限流或防遍历？可接受被按 id 爬取已上架车及其价格历史吗？
10. 列表与详情的公开字段清单（除价格/图片/报告外的「核心字段」）以 F-001 公开 schema 为准是否足够？是否还有 brief 未写、但访客必须看到的字段？
