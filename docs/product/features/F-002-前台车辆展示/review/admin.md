## 我理解的需求

F-002 本质是前台只读展示 + 服务端聚合/筛选接口，对管理后台的改动范围极小：仅在车辆详情页新增一个「复制前台链接」入口——已上架车辆可复制 `{PUBLIC_WEB_ORIGIN}/vehicles/{id}`，未上架时入口置灰并注明原因。spec 已明确本包「不给后台加新菜单、筛选、批量、导出」，管理后台自身的筛选/搜索能力（ADR-006，属 F-001）本期不变。

## 我的方案倾向

- 复制链接做成纯前端拼接（`{PUBLIC_WEB_ORIGIN}` 来自构建期环境变量 + 车辆详情已有的 `id` 字段），不新增 admin API，符合"本包不改车辆/图片/价格写入接口"的边界，也避免多一个后端往返。
- 置灰逻辑复用车辆详情页已有的 `published` 状态字段做前端判断即可，不需要服务端额外返回字段。
- 复制成功给一个轻量 toast 反馈（符合 principles 200ms 可感知反馈要求），不做审计记录——这只是读操作的入口，不写数据。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 中 | `PUBLIC_WEB_ONLY` 环境变量在管理后台未必已配置 | 若前台与后台是不同部署环境/域名，管理后台构建时需要知道前台生产域名才能拼出正确链接；若该变量此前不存在，属于新增部署配置项，需要运维侧确认。 |
| 低 | 「未上架时置灰并注明原因」的文案未定 | spec 只说"置灰并注明原因"，没给出具体文案（如"仅已上架车辆可分享"），实现时需要一个默认文案，建议按 principles 默认协议直接定小文案，不升级为待裁决。 |
| 低 | 复制入口的权限范围未提及 | overview 里管理员与超级管理员权限已经很清楚（两者都能管理车辆），复制链接是只读辅助操作，理论上两级账号都应可见，不需要单独裁决，按默认协议处理。 |

## 对其他端的隐含要求

- 服务端：需保证详情页已加载的车辆对象中已带 `id` 与 `published` 字段（现状应已满足），管理后台不额外请求新接口。
- 前台：复制出的链接格式 `/vehicles/{id}` 需要和前台深链规则（spec 已定稿）保持字面一致，管理后台不能自造别的路径形式。
- 服务端/运维：若前台与管理后台走不同域名部署，需要提供 `PUBLIC_WEB_ORIGIN` 这个环境变量给管理后台构建/运行时使用。
