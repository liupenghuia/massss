## 我理解的需求

F-002 做的是**访客侧只读展示**：不登录、打开链接就能看已上架车辆的列表和详情（核心字段、图片及说明、评估报告、当前价格、价格变动记录）。前台是哑终端，只渲染 `/public/*` 返回的数据，不上架过滤、不做「面谈 vs 数字」判断。

对管理后台而言，本 feature **不改写入接口**，也不新增车辆 CRUD。运营实际用法是：在 F-001/F-003/F-004 里把车备好、发布，把前台链接发给客户。本包要定的是「客户到底看到什么、看到多少条、面谈怎么写」，这些一旦定稿，会反过来约束运营怎么填数据和怎么对客解释。

已有相关裁决（本评审不当作本包新发明，只当边界）：前台不展示 VIN（ADR-002）；发布门槛图≥4、价格已填含面谈（ADR-003）；已上架编辑立即生效、不经二次发布（ADR-004/ADR-008）；图片/报告公开直链、下架后链接仍可访问（ADR-009）；报告新标签打开原文件（ADR-010）；价格记录含操作人、后台不做价格导出与独立历史页（ADR-016）；价格接口只给类型+金额，条数/分页/「面议」文案归 F-002（ADR-017）。原则：前台无用户体系、不做导出/看板、账号越权零容忍。

## 我的方案倾向

- **本包不要给管理后台加新菜单、筛选、批量、导出。** 运营找车、改价、上下架仍走 F-001/F-004；F-002 只消费公开读模型。与 ADR-006「本期不做车辆导出」、ADR-016「本期不做价格记录导出」一致，也不要在前台侧开后门导出访客可见清单。
- **权限：公开接口一律匿名只读；管理写接口继续登录。** F-006 未落地前，不在本包拆「谁能预览前台」。不要把 `/admin/*` 的草稿/下架数据混进 `/public/*`。
- **运营高频动作是「发链接前自己先当访客看一遍」。** 倾向：后台车辆详情提供「打开前台页」入口（仅 `published` 可打开，否则明确不可用），用同一套 `/public/*`，避免后台页和客户页两套字段。本包若不做该入口，至少要规定后台字段集合 ⊇ 前台公开字段，并标明 VIN/操作人等后台专用项不得出现在公开响应。
- **价格历史：公开接口不要下发操作人。** 操作人是审计字段（ADR-012/016），给访客会暴露内部账号。后台详情仍可看全量记录+操作人。前台条数/分页未定时，公开读接口应与后台读接口字段分离，禁止直接复用管理列表 DTO。
- **审计：本包不要求前台访问日志/谁点了链接**（明确不做用户态）。可追溯性继续落在发布/改价/改图的已有操作日志；本包不新增「前台曝光」类日志页。
- **列表：公开列表不要做运营级筛选/排序配置台。** 排序规则必须由服务端数据决定（原则：哑终端）。若列表只要「已上架全量、固定排序」，管理后台就不要做「前台置顶/推荐位」——brief 没提，加了就是新运营能力，应另开需求。

## 反对/风险
| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 已上架编辑立即进前台，运营没有「预览未发布稿」 | ADR-004/008：改字段/图/价保存即对已上架生效。发错价、错图、错说明会直接被客户看到，撞上价格错误、图车错配零容忍。本包若没有「先下架再改」的操作指引或「与客户所见一致的预览」，运营会继续在已上架详情里改，把后台当草稿箱。 |
| 高 | 公开价格历史可能带出操作人/内部口径 | 价格记录含操作人。若 `/public` 与 `/admin` 共用记录结构，访客能看到谁改过价。这是信息泄露，也和「前台无用户体系」无关的后台账号暴露。必须在本包切公开 DTO。 |
| 高 | 下架/进回收站后公开直链仍可用 | ADR-009：对象存储公开、下架不失效旧链。brief 只保证「列表/详情按 published 过滤」。客户收藏的图链、报告链、被转发的详情 URL 仍可能打开文件。前台「车辆不可见」与「文件不可见」不是一回事；运营会以为下架=全部消失。文件级回收属 F-005/存储，但本包必须写清对客话术和详情 404/空态，避免运营误判。 |
| 中 | 前台价格条数与后台详情不一致 | ADR-017 把条数/分页推到本包。运营在后台看全历史，客户只看截断列表时，对客解释会打架（「你们不是改过三次吗」）。未定稿前不要默默截 20 条。 |
| 中 | 面谈文案未定，后台录入与前台用词可能不一致 | 后台可能显示「面谈」，前台若写「面议」，运营培训和截图验收会对不上。文案应一处定义、两端展示同一词，仍由公开接口给结构化类型、文案可在前台写死但必须本包定稿。 |
| 中 | 无角色模型时，「能登录后台的人都能改已上架且立即公开」 | 原则零容忍越权。F-006 未到不能在本包发明角色，但公开面放大了误操作半径：任意后台账号改价即对客可见。应在 F-006 评审时把「改价/上下架」标成高风险权限，本包不要假装已有审核。 |
| 低 | 公开列表无可运营配置的排序/筛选 | 一百台内可接受。若运营想「先发某几台、隐藏某几台但不下架」，当前状态机只有上下架，没有「上架但不出现在列表」。本包不要偷偷加推荐位。 |

## 对其他端的隐含要求

- **服务端 `/public/*`：** 只返回 `published` 车辆；草稿/下架/回收站一律不可枚举、详情应与列表一致（不存在列表没有但 URL 能打开的车，除非本包另裁「直链详情」——当前 brief 要求不可见，应按统一不可见）。公开响应禁止 VIN、操作人、后台备注类字段。列表排序字段必须下发或由服务端排好序，前台不按品牌/价格自行重排。价格只给类型+金额，不给展示文案（除非本包裁决改契约）。图片顺序与直链、多份评估报告顺序遵循 F-003 已有约定。
- **服务端 `/admin/*`：** 本包不要求改写入；若提供「打开前台」链接，只能对 published 生成与访客相同的 public URL。管理读价格记录仍含操作人、全量历史。不要为了省事让前台调用 `/admin`。
- **F-001 管理后台：** 运营需要能从车辆详情稳定拿到「可发给客户的链接」；未上架时不能生成看起来能用的前台链。列表筛状态已在 ADR-006，本包不重复做。已上架编辑的文案/确认是否加强，不在 F-002 改状态机，但验收前台时必须覆盖「后台改完刷新访客页立即变」。
- **F-003：** 前台按返回顺序展示图与说明、报告新标签打开。后台改排序/说明/删图保存即对客生效。运营删除报告前必须理解：旧直链可能仍能打开文件。公开页不要提供下载统计或鉴权。
- **F-004：** 公开与管理查询必须分 DTO。当前价=最新记录变动后值，前台不得自己算。面谈金额为空时前台不得显示 0。历史条数/是否分页由本包裁决后，公开接口按该策略截断或翻页；后台详情仍建议全量只读。
- **F-005：** 进回收站后前台必须不可见；与「对象存储文件仍在」的缺口要在回收站设计里收，不能在 F-002 前台做删除。
- **F-006：** 本包不实现账号；上线前任意登录用户都能制造前台可见变更。角色设计时应把发布、改价、改图当作影响访客的敏感操作；操作日志至少能回答「这台车当时为什么被客户看到这个价」。
- **前台 Web：** 不做登录/收藏/筛选业务；手机竖屏优先。分享（微信内打开）的标题/摘要/封面若做，只能用公开字段，不要带内部编号策略以外的后台信息；具体分享字段未在 brief 写死，不能假定有 OG 配置台。
- **契约：** 不改写入接口。若 F-002 需要 F-004 下发文案或固定「最近 N 条」，走 RFC，不能前台写死又与契约打架。

## 我需要别人回答的问题

1. 运营发链接前，是否需要管理后台「以访客身份打开前台页」？未上架车辆是否允许内部预览（走 admin 预览而非 public）？
2. 前台价格变动记录展示几条、是否分页、是否展示全部历史？后台详情是否必须能看到比前台更多的条数？
3. 「面谈」在前台固定文案是什么（例如「面议」）？是否与后台用词必须完全一致？
4. 公开价格历史是否**禁止**展示操作人、操作账号、任何内部备注？（我倾向禁止，需确认）
5. 访客打开已下架/回收站车辆的旧详情 URL，应 404、空态文案，还是提示「已下架」？旧图片/报告直链是否接受继续能打开？
6. 公开列表排序规则是什么（上架时间、改价时间、后台手动顺序）？要不要置顶？brief 未写，不能默认。
7. 公开列表是否只要全量已上架、不要搜索/筛选（品牌、价格区间）？
8. 是否提供可复制的单车前台链接？链接标识用内部车辆 ID 还是别的？ID 可被遍历是否可接受（一百台内）？
9. 微信/浏览器分享卡片的标题、描述、封面图是否本包要做？不做的话运营只能发裸 URL，需确认。
10. 评估报告多份时前台如何列出（文件名、上传时间）？是否展示上传人？
11. 图片说明为空时前台是否留空、是否允许运营不填说明就上架？（发布校验目前只卡张数）
12. 本包是否明确**不做**前台访问审计、浏览次数、链接打开统计？
13. 已上架车辆被改价后，客户正在打开的详情页要不要强调「以刷新后服务端数据为准」？要不要任何缓存头/CDN 策略让运营知道「改完最多多久客户能看到」？
14. 列表一页多少条、是否分页，一百台是否一页倒完？手机优先下的默认策略要产品定，管理后台不代定。
