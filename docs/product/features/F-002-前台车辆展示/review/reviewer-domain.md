## 我理解的需求

F-002 不引入新的写侧聚合，只消费已有实体在「已上架」上的只读投影：

- **车辆**（F-001）：品牌、车型、上牌年份、里程、颜色、车况描述、能源类型及联动选填字段；**不含** VIN/价格/图片。
- **图片**（F-003）：有序直链 + 每图一段说明。
- **评估报告**（F-003）：一车多份，上传时间倒序，新标签打开原文件直链。
- **当前价格 / 价格记录**（F-004）：结构化「类型 + 金额」，记录 append-only；可见性跟随车辆。

访客无身份。前台是哑终端：只渲染 `/public/*` 已返回的数据，**不**做状态过滤、**不**做「面谈 vs 数字」业务判断。可见性唯一真相是 F-001 的 `published`：草稿、已下架、回收站中的车对前台不可见。列表与详情是同一聚合根的不同读模型，详情再组合图片、报告、价格接口。交付为 Web，手机竖屏优先。

本 feature 须在域内定稿：价格记录展示条数、是否分页、面谈对外文案。不改任何写入接口。

## 我的方案倾向

- **不新增状态机。** 前台无独立生命周期。访客侧只有两种观测：列表/详情能读到该车，或一律视为不存在（与契约「非 published → 404，禁止 403」一致）。避免「下架中 / 已过期」等前台伪状态。
- **一致性边界按读组合、不按跨表事务。** 车辆、图片、报告、价格已是分 feature 聚合。一次详情页是多次只读查询的组合；不以跨聚合事务保证「同一毫秒快照」。发布前置（≥4 图、价格已填）保证上架瞬间齐套，上架后编辑立即生效（ADR-004/008），访客可能看到「刚改完的一半字段」。价格零容忍要求：**当前价必须等于最新一条记录的变动后值**，由 F-004 保证，前台不得自行拼当前价。
- **可见性只信 `/public/*`。** 不得用直链是否还能打开反推车辆是否在售（ADR-009：下架后对象直链不失效）。列表接口不含价/图，详情页必须按契约分别拉，禁止前台猜字段或回退到 `/admin/*`。
- **展示策略与「哑终端」对齐。** 条数、分页、面谈文案若在前台用 `if type==negotiable` 分支，即业务判断。倾向：要么服务端下发已定稿的展示字段，要么契约写死唯一映射且前台零分支；具体选哪条不编造，见问题。
- **列表按可增长设计**（ADR-007），不按「一百台」做成一次拉全量。

## 反对/风险
| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 面谈文案 / 条数 / 分页未定，且与「哑终端」冲突 | brief 要求本 feature 定稿；ADR-017 规定 F-004 只给类型+金额。若前台自己把类型译成「面议」，违反 principles「前端不做业务判断」，也容易和后台用语不一致，踩「价格显示错误」零容忍。 |
| 高 | 读模型组合窗口 | 浏览中下架/改价/改图立即生效且无缓存延迟（ADR-005）。列表有车、详情 404、或价与图来自相邻两次写入，是跨聚合读的固有缝。前台若「缓存上一辆的图/价」会直接命中图车错配或价格错乱。 |
| 中 | 「回收站不可见」在 F-005 未落地前语义不清 | 状态机只有 draft/published/unpublished。F-005 前删除路径未纳入 F-001。brief 把回收站当作已存在的不可见源，域上可能不存在该状态。 |
| 中 | 列表契约与「能浏览列表」成功标准不对齐 | `publicListVehicles` 明确不含价格、图片。列表卡片要不要封面/价，brief 未写。若产品期望列表出价或出图，当前读模型不够，不能由前台拼凑 admin 数据。 |
| 中 | 直链泄漏与「不可见」不是同一概念 | 下架后 `/public/*` 不再返回，但历史直链、微信缓存页仍可能打开文件。域上「不可见」只约束接口投影，不约束对象存储。 |
| 低 | 能源联动空字段 | 排量/电耗/电池按能源类型可空。前台若自行隐藏空字段即业务判断；若原样渲染可能出空白行。归属未定。 |

## 对其他端的隐含要求

- **对服务端 / F-001**：`/public/vehicles` 与 `/public/vehicles/{id}` 必须硬过滤 `published`，禁止客户端传 status。非 published 与不存在统一 404，禁止 403（避免枚举状态）。响应不得含 `vin` / `vinMasked`。下架后立即从公开读模型消失，不做缓存延迟。列表分页按可增长设计，默认排序与契约一致（id 降序）时前台不得改排序语义。
- **对服务端 / F-003**：图片、报告公开接口与车辆同一套可见性；车不可见时返回 `VEHICLE_NOT_FOUND`，不得用资源 404 暗示「车还在但没图」。顺序与直链即展示真相；不得要求前台重排。报告 url 必须是可新标签打开的原文件。对象直链不随下架失效，因此「保密」不能指望前台不渲染。
- **对服务端 / F-004**：公开当前价与记录仅 published；车不可见 404。DTO 不得含操作人。当前价与最新记录变动后必须一致。分页参数已预留，默认 pageSize/是否截断须与本 feature 裁决一致后写进契约，避免前台默默截 20 条（ADR-014 已废）。若裁决「文案由服务端给」，需 RFC 改 F-004/公开 DTO，不能只改前台。
- **对管理后台 / F-001·003·004**：上架后任何编辑立即进入前台投影。运营须理解：改错字、改图序、改价没有「前台延迟发布」。已上架删图不得跌破 4 张，否则前台可能短暂少图——服务端已拒删，后台不得绕过。不得假设前台会再校验「有价有图」。
- **对 F-005**：回收站/硬删必须保证公开列表与所有 `/public/vehicles/{id}/*` 立即不可见，与下架同等。价格记录、图片元数据清理策略不得让公开接口因 500/脏关联而「车没了价还在」或相反。恢复上架前仍走发布前置，避免空壳车出现在前台。
- **对 F-006 / 鉴权**：前台无用户体系，公开路由无登录。身份只存在于 `/admin/*`。禁止把 admin cookie 复用到公开页当「内部预览」而不做独立、显式的预览模型（brief 未要预览）。
- **对前台实现（本 feature 落地）**：只打 `/public/*`。详情需组合车辆、图片、报告、当前价、价格记录；缺一不可用本地假数据补。价格类型到文案的映射不得散落在组件里，除非裁决允许且只有一处与契约一致的死映射。手机竖屏是信息架构第一约束：长图集、多报告、价格历史分页都按竖屏定义，桌面只加宽，不改可见性规则。
- **对渠道 / 微信内置浏览器（ADR-017 划给 F-002）**：分享出去的是 Web URL，不是小程序码。分享卡片标题/图/摘要若要做，属于本读模型的衍生，不得另造一套「分享专用价」。微信缓存旧页与「下架立即不可见」可能冲突，域上仍以接口为准。
- **对 contracts/**：公开列表/详情/媒体/价格的字段裁剪、404 语义、分页默认值、是否下发展示文案，必须在契约写死；F-002 不得在实现期发明字段。

## 我需要别人回答的问题

1. 价格记录前台默认展示几条？超出是分页、加载更多，还是仅截断且不提供更早记录？是否允许访客看全量历史（涉及议价策略，ADR-014 已作废）？
2. 「面谈」对访客的唯一文案是什么？决策权在服务端下发展示字符串，还是允许前台对 `type` 做唯一死映射？后台是否必须与前台用同一文案？
3. 公开列表是否要展示封面图、当前价格？若要，是扩展 `publicListVehicles`，还是允许前台对列表每一项再打图片/价格接口？
4. F-005 上线前，「回收站中不可见」如何验收？是否本期只约束 draft/unpublished，回收站等 F-005？
5. 访客持有已下架车辆的详情 URL 或图片/报告直链时，页面与文件各应呈现什么（仅 404 / 空白 / 仍能打开文件）？是否接受直链在下架后仍能打开？
6. 能源联动空字段、无评估报告、价格历史只有「未填写→首价」一条时，前台是原样展示服务端字段，还是允许按空值不渲染？谁定义「空」？
7. 微信分享是否需要专用标题、描述、缩略图？这些字段来自车辆哪几个已有属性，还是本 feature 新增只读投影？
