## 我理解的需求

前台是无登录的响应式 Web（ADR-001，不做小程序），访客主要通过微信分享的链接在微信内置浏览器（WebView）中打开列表页 `/` 和详情页 `/vehicles/{id}`，浏览车辆卡片、图片灯箱、价格历史、评估报告。spec 已明确：不接入微信 JS-SDK、不做自定义分享卡片、不做微信小程序转发壳，评估报告用「新标签→当前 WebView→提示手动打开」的三级降级链，图片走灯箱不跳出详情页。我从「微信内 H5 实际体验是否可用」的角度评审，不重复讨论要不要做小程序。

## 我的方案倾向

按 spec 现状即可，不需要额外接入微信专属能力。但有几处微信 WebView 的环境特性会实际影响能不能看到车、能不能看报告，建议在测试矩阵里补充针对性用例，而不是只做"能打开就算过"的抽检。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 域名可能被微信拦截为"已停止访问该网页" | 主站域名和 OSS 图片/报告域名若未完成 ICP 备案，或被微信安全中心判定异常（举报、无备案、访问量突增），微信内置浏览器会直接整页拦截，访客完全看不到车辆，这是比 5xx/超时更彻底的失败态，且不在 spec 的错误态表里，前台代码也无法感知或降级。 |
| 中 | 评估报告降级链在微信内的真实行为未经真机验证 | spec 定义了"新标签→当前 WebView 打开→提示手动打开"三级降级，但微信内置浏览器对 `window.open` 通常直接拦截并弹出系统级"在浏览器打开"提示（而非静默失败进入下一级），PDF 类文件还可能被强制走微信文件预览器而不是直接展示。测试矩阵只写"微信 iOS/Android 内置浏览器手动抽检"，未明确必须覆盖"点击评估报告"这一具体交互，建议补一条专项用例。 |
| 中 | 灯箱左右滑动与 iOS 全面屏边缘返回手势冲突 | 详情页图片灯箱要求"手机端左右滑动切换，不跳出详情页"，若灯箱容器未拦截触摸事件、图片在最左/最右张时继续左滑，可能触发 iOS Safari/微信 WebView 的边缘返回手势，把访客带离详情页，这属于交互层缺陷而非展示瑕疵，会直接打断浏览。 |
| 低 | 分享出去是裸链接，缺少车辆信息预览 | spec 已知限制里写明"微信可能不读取 OG 头，分享出去可能只是裸链接样式"，接受即可，仅提醒这是访客点击意愿的实际影响因素，不建议现在为此引入 JS-SDK。 |

## 对其他端的隐含要求

- 服务端：图片/评估报告所在对象存储域名与主站域名都需要具备可在微信生态内正常访问的备案状态，这不是代码能解决的问题，需要业务方在上线前确认。
- 管理后台：复制的前台链接分享出去后若被微信拦截，客服/运营侧需要有备用告知方式（如提示"请在系统浏览器打开"），管理后台本身不需要为此加功能。
- 服务端：公开接口本身无需为微信场景做任何区分处理（UA 判断、专属参数等），保持"哑数据源"即可，兼容性问题应留在前台展示层解决。

## 我需要别人回答的问题

1. 主站域名与图片/评估报告所在的对象存储域名是否已完成 ICP 备案、是否需要额外在微信安全中心做域名检测/申诉，以避免被拦截为"已停止访问该网页"？
2. 评估报告的三级降级链（新标签→当前 WebView→提示手动打开）是否已在微信 iOS/Android 真机上实测过 PDF 与图片两种文件类型，还是仅为设计预期，尚未验证？
