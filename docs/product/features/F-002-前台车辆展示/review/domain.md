## 我理解的需求

F-002 是纯读侧投影：访客通过 `/public/*` 浏览"车辆卡片"（列表）与车辆详情（图片+说明、车辆描述、评估报告、当前价、价格记录全量），不做任何写入，也不做业务判断（可见性、价格类型、图片顺序均由服务端决定）。核心实体（车辆、图片、图片说明、评估报告、价格记录）的写入语义和状态机归属 F-001/F-004/F-005，本 feature 只消费其只读投影。spec v1.4 已把展示层的空值映射、价格/报告/图片渲染规则、筛选边界、深链、错误态逐条定稿，域内歧义已基本收敛。

## 我的方案倾向

- 把"车辆卡片"（列表聚合模型）视为服务端计算的**只读投影（read model）**，不是独立聚合根；一致性边界完全在服务端（同一次请求内对车辆+封面图+当前价做一次性组装），前台不参与、不缓存、不做本地拼接，这与 TTL=0、哑终端原则一致，认可现有设计。
- 价格记录在前台只渲染"类型 + 金额 + 日期"三元组，不展示"变动前值"，比 overview 术语表里"价格记录=变动前后值+时间"的定义窄，这是投影裁剪，不是模型缺陷，但建议在 spec 里显式说明"前台只消费价格记录的子集字段"，避免后续误以为前台也要动"变动前值"。
- 认可"面议"作为价格类型的一个取值、金额置空的死态处理（禁止显示 0/空占位），空值映射表覆盖了 null/""/0 三种情况，状态收敛，无死状态。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 低 | 封面图选取规则不在本 feature 定义域内 | 列表卡片依赖"封面缩略图 URL"，其选取规则（是否恒为首图、是否可独立指定）属服务端/F-001 概念，本 feature 只是消费方，需保证该字段语义稳定，否则列表封面与详情图片顺序可能出现认知不一致（如封面不是详情第一张图）。 |
| 低 | "车辆卡片"作为聚合读模型未在 spec 正文中显式点名 | overview 术语表定义了"车辆卡片"这个概念，但 F-002 spec 通篇未使用该词，读者需要自行在脑中把"公开列表聚合读模型"和术语表的"车辆卡片"对应起来，容易在后续文档演进中概念漂移。 |
| 低 | 价格记录展示字段是原始实体的子集 | 详情页价格记录只展示"类型+金额+日期"，未展示"变动前值"，与 overview 中价格记录的定义（含变动前后值）不完全对齐；建议 spec 中一句话说明这是有意裁剪的展示子集，而非遗漏。 |

## 对其他端的隐含要求

- 服务端：`封面缩略图 URL` 与详情图片列表中某一张图必须是同一份资源标识（同 URL 或明确的对应关系），否则列表/详情图片认知不一致；当前价字段必须保证在列表接口与价格记录接口之间取值一致（同一次请求窗口内）。
- 管理后台：本 feature 不新增写入能力，若后续调整价格记录字段（如新增"变动前值"展示需求），需先确认前台是否要跟进渲染，避免服务端加字段后前台悄悄不用。
