## 我理解的需求

访客无需登录，通过链接浏览已上架车辆的列表与详情（核心字段、图片+说明、评估报告、当前价、价格历史）。前台是哑终端，只渲染 `/public/*` 返回的数据，不做状态过滤、不做价格类型判断。草稿/已下架/回收站车辆前台不可见（服务端过滤）。评估报告新标签打开原文件；图片按接口返回顺序展示。手机竖屏优先，桌面兼容。

## 我的方案倾向

- 自动化以公开接口契约测试为主：覆盖可见性过滤（published/draft/unpublished/不存在 id）、字段泄漏（VIN/操作人/内部备注不得出现）、分页边界、404 语义。
- 价格、图片归属、报告归属属零容忍项，需针对性构造"跨车混淆"用例（如连续请求两台车详情，断言字段不串号）。
- 手动抽检覆盖手机竖屏（微信内置浏览器 + 系统浏览器）与桌面，重点验证空态/错误态/加载态不空白。
- 面议车辆、空值字段（图片说明为空、无报告）需单独构造夹具用例，因为这是"隐藏 vs 展示空占位"的易错点。

## 对其他端的隐含要求
- 服务端：`/public/*` 接口必须保证已下架/草稿/回收站车辆返回 404 或从列表剔除，且响应体不得包含 VIN、操作人等敏感字段，这是前台"哑终端"假设成立的前提。
- 服务端：图片、评估报告、价格记录必须与车辆 ID 严格一一对应返回，接口层面的任何归属错误都会直接导致前台"串车"这一零容忍问题，需要服务端自身有归属校验测试。
- 服务端：价格当前值与历史记录的"面谈/数字"判断逻辑必须完全在服务端完成并以确定字段下发，前台不重复判断，否则前台测试无法明确断言展示文案的正确性。
