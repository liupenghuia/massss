## 产品取向

**前端是哑终端。** 后台传什么，前端展示什么。
展示逻辑、字段可见性、排序规则一律由后台数据决定，前端不做业务判断。
新增展示字段时，优先考虑"后台加字段"而非"前端加逻辑"。

**内容准确 > 功能丰富。** 车辆信息、价格、评估报告是核心资产，
展示错误的代价远高于功能少。有疑问时砍功能，不砍校验。

**UI 必须全面、简单、流畅，符合人机交互原理。** 这是前台与管理后台共同的验收标准，不是可选项：
- 全面：核心信息与操作一屏内可达，不因为"精简"漏掉用户需要的字段或入口；异常态（加载中、空态、错误态、权限不足）必须有对应界面，不能空白或卡死。
- 简单：默认展示做减法，次要操作折叠/收起而非平铺；同一层级操作不超过用户能一眼扫完的数量，禁止为了"看起来功能多"堆砌控件。
- 流畅：操作反馈在 200ms 内可感知（loading 态、按钮态变化），跳转与刷新不打断当前上下文；长任务（批量上传、报告生成）要有进度反馈，不是转圈到底。
- 符合人机交互原理：遵循费茨定律（高频操作大而近）、米勒定律（同层级选项控制在可记忆范围）、就近原则（操作按钮贴近其作用对象）、一致性（同类交互在全站用同一种模式，不重复发明）。

出现明显反例（如需要滚动很远才能找到保存按钮、错误提示只显示状态码、同一操作在两个页面交互方式不一致）判定为缺陷，与"可带上线"的展示瑕疵区分对待。

**前台移动优先，后台桌面优先；两端都必须能在手机浏览器里完整看、完整点。**
交付是响应式网页（ADR-001），不是小程序、不是单独再做一套手机 UI。
视觉语言（Organic：色板、字体、圆角、胶囊控件）两端共用，手机适配只改排版密度和折行，不改皮肤、不另起组件体系。

冲突时怎么选：
- 前台：手机竖屏是第一画布，桌面只加宽、不改信息架构。两者打架以手机为准。
- 后台：桌面是第一画布（顶栏、卡片网格、双栏编辑），允许在手机上折行、叠栏、区内横滑；但主操作（登录、筛选、新建、保存、上传）必须仍在屏内可点，禁止靠裁切或整页左右滚动来「塞进去」。
- 设计稿在 390 宽仍保持的结构（如前台详情规格两列、列表搜索+筛选同一信息层级），手机上不得擅自压成另一套信息架构。

手机端展示硬规则：
- 验收宽度：手机竖屏最小 **375px**，平板中间档，桌面最小 **1024px**（与 ADR-021 一致）。三档布局不破。
- 禁止整页横向滚动。宽表、多段状态条可以在**组件内部**横滑，不能把页面撑破。
- 主按钮、搜索、分段开关被挤出屏幕 = 缺陷，不是「桌面优先所以不管」。
- 不出现系统原生文件选择器（Choose Files）破坏版面；上传用同一套虚线投放区，点击与拖拽都能用。
- 输入框在 iOS 上须避免聚焦被放大（字号不够 16px 会触发）；刘海/安全区不能挡住顶栏和主按钮。
- 键盘可操作，焦点可见。微信内置浏览器当普通手机浏览器测，不做微信专属能力。
- 图片裂图、空态、错误态在手机上同样要有占位，不得只留桌面才看得懂的空白。

**UI 实现门禁（admin-web / public-web，可执行）：**
- 新页面必须复用已有组件类：`.btn` / `.card` / `.tag` / `.input` / `.seg` / `.table` / `.dialog`（定义在 `shared/shell.css` + token 在 `shared/organic.css`）。
- 新增全局视觉类或第二套控件皮肤必须先写 ADR，禁止页面私自发明一套按钮/卡片。
- 破坏性操作用站内 `.dialog`；**禁止 `window.confirm` / `window.alert`**。
- 内联 `style` 只允许动态计算值（如进度宽度、拖拽位移）；字面量颜色、字号、间距收回 `shell.css`。
- 最小正文字号 **12px**；iOS 输入框仍须避免低于 16px 触发聚焦放大（见上条手机硬规则）。
- 涉及 UI 的改动必须具备加载态、空态、错误态；改完在对应子项目跑 `lint`、`typecheck`、`build`。

## 质量底线

**零容忍：**
- 价格显示错误、价格历史记录丢失或错乱
- 图片与车辆错配（A 车展示了 B 车的图）
- 评估报告文件损坏或串号
- 已删除车辆仍在前端可见
- 后台账号越权（低权限账号能改不该改的东西）

**可带上线：**
- 图片加载顺序、缩略图裁切比例等展示层瑕疵
- 后台表格列宽、排序等操作体验问题
- 回收站 UI 不够精致

## 技术偏好

**服务端合一。** 前台展示接口与管理后台接口在同一个服务里，
用路由前缀区分（如 `/public/*` 与 `/admin/*`），不拆微服务。

**前台无用户体系。** 前台不做登录、不做收藏、不埋用户身份。
需要用户态的功能一律推到下一期重新评估。

   **技术栈：** 
稳定可靠（具体帮我定下来就行）

确认（见 ADR-001）：前台与管理后台均采用 Web，不做微信小程序。移动端体验用响应式/自适应网页兼容手机浏览器，不引入小程序技术栈。

   **SEO 是否重要？** 
- 只是发链接给客户看 → 纯客户端渲染即可，简单得多

**图片是主要成本项。** 每车最少 4 张、数量无上限，
图片存储与流量会是长期支出大头。选型时优先考虑对象存储 + CDN，
不把图片塞进应用服务器本地磁盘。

  **车辆数量级：** 
一百台以内

| 统一叫法 | 指什么 | 是否需登录 |

## 评审与改需求的默认协议

> 这是**流程默认值**，不改变上面的产品取向。用来避免把已写明的规则再问一遍。
> 零容忍项、状态机、权限、价格对错，仍须用户明示，禁止用本节省略。

**提问纪律（评审 / RFC）：**
- `principles.md`、`overview.md`、已 Accepted 的 ADR 里写明的内容，**不要**再列入「我需要别人回答的问题」。
- 已确认不做微信小程序（ADR-001）时，不要再问「要不要做小程序」。
- 「可带上线」的展示瑕疵不要升级成待裁决。
- 每道待裁决问题一行；能合并的合并。

**尚未裁且不踩零容忍时，默认：**
- 选范围更小、本期能上线的一档
- 无人认领 → 写入「明确不做」，或推迟到该管的 feature，并写明不阻塞本 feature
- 非法操作：返回明确错误（与幂等成功区分：已在目标态的重复调用才幂等）

**改已定稿需求：**
- 文案、已有范围内加字段：小改 + 一条新 ADR，不开五方评审
- 状态机 / 权限 / 价格对错 / 跨端接口：`/rfc`，且**只派受影响的 1～2 个 reviewer**
- 跨端 + 状态机 + 钱或权限同时涉及：才允许 `/review` 全角色

**编码：**
- 只读该 feature 的 `spec.md`、其 frontmatter 列出的 ADR、`contracts/` 中相关 path
- 禁止通读 `review/`、`conflicts.md`、其他 feature 的评审全文
