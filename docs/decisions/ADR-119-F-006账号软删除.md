# ADR-119 F-006 账号软删除

Status: Accepted
Date: 2026-08-24
Feature: F-006
Supersedes: -

## Context

ADR-026 曾裁决"停用是状态转移，不做物理删除，可重新启用"。用户现在明确提出新增需求：
超级管理员目前只能新建、停用账号，希望补一个删除功能，删除前二次确认，删除后不可恢复。
该需求经 RFC（docs/rfc/2026-08-24-F-006-账号物理删除.md）评审并裁决，本 ADR 记录最终决策，
不修改 ADR-026 原文（ADR-026 关于停用/角色升降级的裁决仍然有效，删除是在其基础上新增的
下一步状态转移，而非替换）。

## Decision

### 删除范围与前置条件
- 删除范围：管理员、超级管理员账号均可被删除，含超管本身。
- 前置条件：仅"已停用"状态的账号允许删除；启用中账号调用删除接口返回 409。
- "不能删除自己"不作为独立校验规则新增：因为 ADR-026 已禁止"停用自己"，
  而删除的前置条件是"已停用"，两条规则组合后超管天然无法把自己降到可删状态，
  属于隐含防御，契约文档中显式写明原因。

### 软删除
- 账号表新增 `deleted_at` 字段，删除即置该字段，不物理清除行。
- `GET /admin/accounts` 等列表查询默认过滤已删除账号；审计记录不做级联删除，
  展示层对已删除账号关联的审计记录显示"已删除账号"兜底文案。
- 删除后 `loginName` **不释放、不可复用**，与 ADR-026 现有"已停用账号 loginName
  永久占用不可复用"的规则保持一致，避免新账号复用旧 loginName 后审计记录展示错乱。

### 接口语义
- `DELETE /admin/accounts/{accountId}`，仅超级管理员可调用。
- 404：账号不存在，或已被软删除（重复调用视同不存在，不采用幂等成功语义——
  删除是不可逆操作，需要明确反馈而非静默成功）。
- 409：账号当前不是"已停用"状态。
- 204：删除成功。
- server 端实现删除前置状态检查时，须在数据库层用条件更新
  （如 `UPDATE ... WHERE id=? AND status='disabled' AND deleted_at IS NULL`
  判断受影响行数）判断是否满足前置条件，不得"先 SELECT 状态、再 UPDATE"两步式判断，
  避免并发删除/并发重新启用下的竞态窗口。

### 交互与审计
- 管理后台账号列表对"已停用"账号展示「删除」按钮，点击后弹出简单二次确认弹窗
  （非输入账号名确认），文案明确提示"删除后不可恢复"。
- 删除操作按 ADR-028 现有审计机制落审计记录（操作人、操作时间、操作对象、操作类型 = delete）。

## Consequences

+ 软删除既满足"删除后不可恢复地找回"的产品诉求，又避免外键/审计关联的级联清理复杂度。
+ loginName 永久不释放，避免了"新账号复用旧 loginName 导致审计记录展示指向错乱"的隐患，
  与账号创建接口既有承诺保持一致。
+ 404 而非幂等成功的重复删除语义，让调用方能明确感知到"这个操作没有再次生效"，
  防止误以为重复点击删除仍然安全。
+ 显式要求 DB 层条件更新，从设计阶段堵住了并发场景下的竞态窗口，不依赖实现者自行发现。
- 账号表会随删除操作不断累积软删除行，若干年后行数增长，但后台账号规模通常为几十到
  几百条，当前不构成性能问题。
- "不能删除自己"完全依赖另外两条规则的组合推导，而不是显式校验，未来如果 ADR-026
  的"停用自己"限制被修改，需要同步重新评估删除接口是否要补一条显式校验。
