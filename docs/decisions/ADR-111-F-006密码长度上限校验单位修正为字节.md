# ADR-111 F-006 密码长度上限校验单位修正为字节

Status: Accepted
Date: 2026-08-23
Feature: F-006
Supersedes: ADR-105（部分：上限校验的计量单位）

## Context

ADR-105 裁决密码上限 72 字符，动机是"与 bcrypt 等哈希算法的常见安全长度上限对齐"，
同时允许任意可打印 UTF-8 字符（含中文、emoji 等非 ASCII 字符）。

功能审计发现：bcrypt（含本项目使用的 bcryptjs）对输入按 **字节** 截断到 72，不是按字符。
原实现 `passwordMeetsPolicy` 按 `plain.length`（JS 字符串的 UTF-16 code unit 数）校验上限，
当密码含多字节字符时，字符数 ≤ 72 但 UTF-8 字节数可能远超 72（例如 30 个汉字 = 90 字节）。
此时 bcrypt 只用前 72 字节参与哈希，超出部分被静默截断——用户以为设置了完整密码，
实际密码强度被削弱，任何与前 72 字节相同、后缀不同的字符串都能通过校验。

## Decision

密码长度上限校验单位由"字符数"修正为"UTF-8 字节数"：`Buffer.byteLength(plain, 'utf8') <= 72`。
下限（≥8）维持按字符数校验不变（下限场景不涉及截断风险，改字节数无必要）。
字符集限制不变（仍只拒绝控制字符，其余可打印 UTF-8 不限）。

此修正意味着：含较多非 ASCII 字符的密码，实际能输入的**字符数**会少于 72
（取决于字符的 UTF-8 编码字节数），但保证密码策略允许的每一个字符都真正参与哈希验证，
不会出现"看似合法的密码实际强度被截断削弱"的情况。

## Consequences

+ 消除 bcrypt 静默截断导致密码强度被削弱的隐患，校验单位与哈希算法的实际行为一致。
- 全角字符/emoji 较多的密码，可输入字符数会明显少于 72（如纯 emoji 密码约上限 18 个字符），
  与 ADR-105 原文"72 字符"的字面预期不完全一致，需要前端/文案层面知悉这一点。
