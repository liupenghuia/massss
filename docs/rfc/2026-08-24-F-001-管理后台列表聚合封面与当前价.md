# F-001 管理后台列表接口：聚合封面与当前价

## 动机

管理后台车辆列表卡片需要封面和当前价，运营才能扫一眼核价。  
`GET /admin/vehicles` 的 `AdminVehicle` 仍不含图、不含价（ADR-007 / ADR-113）。前端兜底对每页 20 条再打 20 次 images + 20 次 price，合计约 **41 次请求**。已收成一次 setState，不再闪动，但翻页仍等最慢的那条。

公开列表早已用 `PublicVehicleSummary.coverImageUrl` + `currentPrice` 一次带回（RFC 2026-08-19 F-002）。后台应对齐同一模式，而不是继续 N+1。

价格仍归 F-004：不落车辆表、不靠车辆行上的快照列。本 RFC 只让**列表读模型**带上服务端算好的只读聚合字段。

## 提议

### 1. 新增 `AdminVehicleSummary`，仅给列表用

`GET /admin/vehicles` 的 `AdminVehicleList.items` 从 `AdminVehicle` 改为 `AdminVehicleSummary`。

`AdminVehicleSummary` = 现有 `AdminVehicle` 全部字段 + 两个只读聚合字段：

```yaml
coverImageUrl:
  type: [string, "null"]
  description: |
    封面图 URL，与 F-003 顺序第一张相同；无图时为 null。
    服务端保证字段存在，不由前端拼 CDN。口径与 PublicVehicleSummary.coverImageUrl 一致。
currentPrice:
  description: |
    当前价 = 该车最新一条价格记录的变动后值（与 GET /admin/vehicles/{id}/price 的 current 同一口径）。
    从未设价（草稿常见）时为 null。面谈为 { type: negotiable, amount: null }。
  oneOf:
    - $ref: "#/components/schemas/PriceValue"
    - type: "null"
```

字段名跟公开列表对齐（`coverImageUrl` / `currentPrice`），不另造 `coverUrl` / `price`。

### 2. 明确不变

- `GET /admin/vehicles/{id}` 仍返回 `AdminVehicle`，**不加**这两个字段。编辑页继续用既有 images / price / price-records。
- URL、方法、查询参数（`status` / `q` / `page` / `pageSize`）不变。
- 不按价格筛、不按价格排（后台列表仍状态 + 关键字）。
- 回收站列表不加封面/价（本 RFC 不做）。
- 不改公开接口。
- 不在 `vehicles` 表加价格列或封面列；列表查询用 JOIN / 子查询一次取出。

### 3. 前端在契约落地后

删除 `VehiclesPanel` 里对列表项的并行 `GET .../images` 与 `GET .../price`。卡片直接读 `item.coverImageUrl`、`item.currentPrice`。某车无图/无价用 null 占位（封面走既有空占位，价显示「未设价」），不得把整页判失败。列表数据源与编辑页 images/price **不得**共用同一套「少字段」缓存。

### 4. 当前价口径（与 F-004 对齐，不另裁）

批量查出的 `currentPrice` 必须与 `GET /admin/vehicles/{id}/price` 的 `current` **同一条记录**：按价格记录自增主键最大者（ADR-073），禁止列表用时间、详情用 id。无图/从未设价时 JSON **键必须在、值为 null**，禁止省略字段。

## 影响面

| 端 | 影响 |
|---|---|
| 契约 | `AdminVehicleList.items` 改 `$ref`；新增 `AdminVehicleSummary` |
| 服务端 | `adminListVehicles` 一次查出封面 URL + 当前价；详情/改价/改图接口不变 |
| 管理后台 | 列表卡片少 40 次请求；解构多两个字段 |
| 前台 | 无 |
| F-004 | 价格仍只来自价格记录；列表只读聚合，写路径不变 |
| F-003 | 封面定义仍是顺序第一张；改序/删图后下一次列表请求看到新封面（零缓存，与现状一致） |

## 契约变更

只改 `contracts/openapi.yaml`（落地须走 contract-keeper，本 RFC 不直接改文件）：

1. 新增 `components.schemas.AdminVehicleSummary`（如上）。
2. `AdminVehicleList.properties.items.items.$ref`：`AdminVehicle` → `AdminVehicleSummary`。
3. `AdminVehicle` 的 description 可注明「详情用；列表见 AdminVehicleSummary」。
4. 不改 `GET /admin/vehicles/{id}` 的响应 schema。

服务端实现约束（写进 RFC，供落地）：对当前页 id 集合批量取「每车第一张图 URL」和「每车最新价格记录」，禁止在 Node 里对每条再查库（把前端 N+1 搬到服务端不算完成）。

## 不做的替代方案

| 方案 | 不选的原因 |
|---|---|
| 维持前端 2N 兜底（ADR-113） | 已能看价，但翻页体感差；百台可撑、再增长会顶限流 |
| 把字段加进 `AdminVehicle`（详情也带） | 详情本来就要拉全量图片和价，加两个字段收益小，还扩大所有返回 AdminVehicle 的接口表面 |
| 车辆表加 `cover_url` / `current_amount` 快照列 | 违反 ADR-007/015 价格不落车辆表；改图/改价要双写，容易和记录不一致（零容忍：价格对错） |
| 列表只加封面、不加价 | 核价才是列表要解决的事；只加封面剩 20 次 price，问题还在 |
| 后台按价格筛选/排序 | 超出本 RFC；ADR-006 后台仍是状态 + 关键字。要做另开 RFC |

## 待裁决

1. 列表项 schema：新建 `AdminVehicleSummary`（推荐），还是把两字段直接加进 `AdminVehicle`（详情一并返回）？  
   **已裁：Summary。** ADR-114。
2. 从未设价时 `currentPrice` 用 JSON `null`，还是做成 `unset`？  
   **已裁：`null`。** ADR-114。
3. 回收站列表要不要同样带封面/当前价？  
   **已裁：本 RFC 不做。** ADR-114。

## 评审意见

### api（2026-08-24）

同意独立 Summary、未设价 `null`、回收站本期不做。  
风险：列表与详情「当前价」必须同一排序键（自增主键，ADR-073），否则并发改价会选错行（零容忍）。批量 JOIN 要有按 `vehicle_id` 取第一张图/最新价的索引，禁止循环查库。契约 `$ref` 切换后 typed 后台须同发。  
落地后应废止 ADR-113 里「列表契约不加价、卡片走独立价格接口」的展示条款；写路径与 F-004 归属不变。

### admin（2026-08-24）

同意字段名与公开列表一致。卡片：`null` 封面占位、`currentPrice === null` 显示「未设价」、面谈走现有「面议」格式。整页错误只留给列表请求失败。禁止把列表聚合字段接到编辑表单。待裁决 1–3 倾向 RFC 推荐档。
