# F-006 后台账号新增删除功能

## 动机

用户明确提出需求：目前超级管理员只能新建、停用账号，无法删除。用户希望补一个删除功能，
删除前需二次确认，且删除后不可恢复。

该需求直接推翻 [ADR-026](../decisions/ADR-026-F-006账号生命周期与超管制衡.md) 中
"停用是状态转移，不做物理删除，可重新启用"的裁决，以及 spec.md「明确不做」第 103 行
"不做账号物理删除"，因此走 RFC 而非小改。

## 提议

- 新增 `DELETE /admin/accounts/{accountId}` 接口，仅超级管理员可调用。
- **删除范围**：管理员、超级管理员账号均可被删除（含超管本身）。删除超管时校验规则与
  ADR-026 现有的停用/降级校验一致：不能删除导致「零个启用超级管理员」的操作——但由于
  前置条件要求账号必须先停用，而 ADR-026 已经保证"不能停用最后一个启用超管"，
  所以实际上不会出现"删除最后一个启用超管"的场景；这里仍显式声明校验规则，作为兜底防御。
- **前置条件**：仅"已停用"状态的账号允许删除，启用中账号直接调用删除接口返回明确错误
  （409，提示需先停用）。
- **软删除**：账号表新增 `deleted_at` 字段，删除即置该字段，不物理清除行。
  查询账号列表默认过滤已删除账号；审计表通过账号 ID 关联时，展示层对已删除账号
  显示"已删除账号"兜底文案，不做级联删除、不影响审计记录完整性。
- **审计**：删除操作本身按 ADR-028 现有机制落审计记录（操作人、操作时间、操作对象、
  操作类型 = delete）。
- **前端交互**：管理后台账号列表对"已停用"账号新增「删除」按钮，点击后弹出二次确认
  弹窗（简单确认型，非输入账号名），文案明确提示"删除后不可恢复"。

## 影响面

| 端 | 影响 |
|---|---|
| server | 新增 DELETE /admin/accounts/{accountId} 接口；账号表加 deleted_at 字段与迁移；账号列表查询过滤软删除；审计写入沿用现有机制 |
| admin-web | 账号列表页对已停用账号增加删除按钮 + 二次确认弹窗 |
| contracts | openapi.yaml 新增 DELETE /admin/accounts/{accountId} 路径定义 |

## 契约变更

- 新增 `DELETE /admin/accounts/{accountId}`：
  - 权限：仅超级管理员。
  - 前置：目标账号状态必须为「已停用」，否则 409 + 明确错误信息。
  - 响应：204 成功；404 账号不存在或已被删除；409 状态不满足（启用中，或会导致零启用超管——理论兜底）。
- 账号列表/详情响应结构不变，`deleted_at` 为内部软删除标记，不对外暴露字段；
  已删除账号不出现在 `GET /admin/accounts` 列表返回中。
- 具体字段与错误码由 contract-keeper 落地到 contracts/openapi.yaml，本 RFC 只列变更点。

## 不做的替代方案

- **不做"输入账号名二次确认"**：用户明确选择简单二次弹窗确认，输入确认的方式交互成本更高，
  当前误删风险可控（前置要求先停用，且有二次确认弹窗兜底）。
- **不做级联删除审计记录**：审计记录是行为留痕，与账号实体是否存在无关；级联删除会破坏
  审计链完整性，用户已明确要求保留。
- **不做真正的物理删除（硬删除数据库行）**：软删除既满足"用户不可见/不可恢复地找回"的
  产品诉求，又避免外键/审计关联的复杂清理，是更小风险的实现方式。

## 评审意见

- 【阻塞】`loginName` 复用规则与 ADR-026/adminCreateAccount 现有文案冲突：openapi.yaml 中
  `adminCreateAccount` 明确写着"已停用账号的 loginName 永久占用不可复用"，本 RFC 引入软删除后
  未说明删除后 `loginName` 是否可被重新占用。若允许复用，会与"永久占用"的既有承诺矛盾，且要
  处理"新账号复用已删除账号 loginName 后，审计记录按 loginName 关联展示会错乱指向新账号"的
  风险（若审计展示层是按 accountId 关联则无此问题，但 RFC 未明确审计关联键是 id 还是
  loginName）。建议维持"loginName 删除后仍永久占用不可复用"，与既有创建接口文案保持一致，
  并在契约变更里显式写明这一条，而不是留给 contract-keeper 自行判断。
- 【阻塞】"仅已停用账号可删"与"停用会作废该账号全部会话"叠加后，删除前置状态检查存在
  TOCTOU 竞态：若两个超管并发对同一账号发起删除请求，或删除与"重新启用"并发，需要在 DB 层
  用条件更新（如 `UPDATE ... WHERE id=? AND status='disabled' AND deleted_at IS NULL`
  判断受影响行数）而非"先 SELECT 状态、再 UPDATE"两步式判断，否则并发下可能出现
  "已启用账号被删除"或重复删除返回不一致错误码的情况。RFC 未提及这一实现约束，需要补充，
  否则 server 端可能按最朴素的读后写实现，引入竞态窗口。
- 【建议】DELETE 接口的 404/409 语义基本合理（对齐 status 接口的既有短路检查顺序），但建议
  RFC 明确一条：删除已删除账号（重复调用）应返回 404 还是 409？按 `adminSetAccountStatus`
  的幂等设计惯例（同状态视为幂等成功），这里若照搬"幂等"语义会与"删除不可逆、需要明确反馈"
  冲突，建议返回 404（视同不存在）更符合软删除语义，且需要在契约里显式写出，不要交给
  contract-keeper 自行拍板。
- 【建议】"CANNOT_DISABLE_SELF"类的自我操作限制在 status/role 接口都存在，但本 RFC 未提及
  删除接口是否需要"不能删除自己"的检查——由于前置条件要求先停用，而 status 接口已禁止
  停用自己，理论上超管永远无法把自己停用到可删状态，天然规避了这个场景，属于设计上的隐含
  防御，但建议在契约描述里显式写一句说明原因，避免后续读者误以为是遗漏。
- 【建议】RFC 遗漏"登录校验查询是否需要过滤 `deleted_at`"这一点：账号已被软删除后理论上不可能
  处于"启用"状态（前置条件保证），因此登录接口按现有"仅启用账号可登录"的校验已自然排除已删除
  账号，无需额外改查询逻辑；但建议在「影响面」表格里显式点一句"登录校验无需改动，原因为
  删除前置要求已停用"，避免实现时因为看不到这条说明而重复添加冗余的 deleted_at 过滤条件到
  多处查询、造成条件遗漏不一致的风险。
- 【建议】`deleted_at` 索引与查询性能未提及：`GET /admin/accounts` 列表查询默认要过滤
  `deleted_at IS NULL`，账号表数据量小（后台账号通常几十到几百条），暂不构成性能问题，
  不要求本 RFC 补充索引方案，仅记录以备量级变化时复核。
- 【建议】契约变更描述基本可供 contract-keeper 直接落地（新增路径、权限、前置状态、
  204/404/409 语义均已给出），但如上所述需先补齐"loginName 复用"和"重复删除返回码"两点
  确定性描述，否则 contract-keeper 落地时会需要自行做业务判断，不符合"contracts 只能由
  contract-keeper 按明确输入落地"的项目铁律。

**用户裁决（2026-08-24）：**
- `loginName` 删除后**不允许复用**，与现有创建接口"已停用账号 loginName 永久占用不可复用"
  文案保持一致，删除不释放 loginName。
- 重复调用 DELETE 已删除账号，返回 **404**（视同不存在，不采用幂等成功语义，
  因为删除是不可逆操作，需要明确反馈而非静默成功）。
- 删除前置状态检查需在 DB 层用条件更新（`WHERE status='disabled' AND deleted_at IS NULL`
  判断受影响行数）避免 TOCTOU 竞态，不做"先 SELECT 再 UPDATE"两步式判断。
- "不能删除自己"作为隐含防御（先停用才能删 + 不能停用自己 → 自然规避），
  契约描述中显式写明原因，不作为独立校验规则新增。
- 登录校验无需改动（已停用账号本就不可登录，删除只是在此基础上追加软删除标记）。
