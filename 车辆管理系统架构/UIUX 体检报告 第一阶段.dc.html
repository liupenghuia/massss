车辆信息展示系统
界面与体验诊断

读的是 mallsss/ 下的实际代码：public-web、admin-web、shared/。技术栈 React 19 + Vite + react-router，无 UI 框架，样式为自建 shared/organic.css token 层 + shared/shell.css 布局层。下列每条都指到文件与行。

整体印象

这套界面的底子比大多数同阶段项目好：token 层是真的、骨架屏空态错误条齐全、focus-visible 环和 prefers-reduced-motion 都写了、移动端 safe-area 和 16px 输入框也考虑到了。问题不在"糙"，在三处具体的洞。

最要命的三个：普通管理员没有任何修改自己密码的入口（改密表单埋在超管专属的账号页里）；后台车辆列表每翻一页要发 20 个额外请求取封面，还触发 20 次重渲染；录入表单没有任何字段级校验，填错年份要等服务端 400 才在页顶看到一句笼统报错。此外 4 处破坏性操作用的是浏览器原生 window.confirm，和整套视觉完全脱节。

两处我按代码推断、未向你确认：目标用户取自 docs/product/overview.md（访客 / 管理员 / 超管三角色）；最高频操作我假设是「录入并发布一辆车」「改价」「访客筛选看车」。如果实际不是这三个，第 4、14、22 条的优先级要调。

25 条。P0 阻断核心任务，P1 高频路径受损，P2 体验与一致性，P3 打磨。

成熟度评分

3/5
信息架构与导航
层级浅、路由守卫写得规矩，扣分全在改密入口对普通管理员不可达，以及新建的两段式流程没有引导。
4/5
布局与视觉层次
留白、栅格、粘性侧栏都到位。扣分在后台卡片漏掉价格这个最该在列表出现的字段，以及缩略图下常驻删除按钮。
3/5
设计系统一致性
token 层是真的、两端共用，这是最大的加分项。扣分在重复定义与失效 token、散落的内联字面量、无 z-index 层级、已有的 .dialog 闲置。
3/5
交互与反馈
loading / empty / error / 骨架 / 按钮禁用都有，比预期好。扣分在成功路径静默、确认规则不一致、原生 confirm、banner 不消失。
2/5
表单与数据录入
最弱的一项。没有字段级校验、没有必填标识、数值输入无边界、错误只在页顶，双写分支还让新建与编辑行为不一致。
3/5
表格与列表
车辆列表分页、空态、骨架完整。扣分在回收站 50 条上限无分页无提示，以及表格没有批量操作（删多辆车只能一辆一辆点）。
4/5
响应式与多端
1100 / 720 / 640 三档断点、safe-area、移动端 16px 输入框防缩放，都做了。扣分只在窄屏表格靠横滚而非卡片化。
3/5
可访问性
全局 focus-visible、aria-label、aria-live、灯箱焦点陷阱、visually-hidden 都有。扣分在拖拽排序无键盘路径、aria-grabbed 已废弃、若干 11–12px 小字。
2/5
性能带来的体验损耗
后台列表的 N+1 封面请求 + 20 次逐条 setState 是明确的体感问题：卡片持续闪动、封面一张张跳出。VehiclesPanel 懒加载和骨架屏是加分。
4/5
文案与微内容
术语统一（草稿 / 已上架 / 已下架 / 面议贯穿两端），空态文案都给了下一步。扣分在「筛选」当动词用，以及前台把所有失败收敛成同一句。
