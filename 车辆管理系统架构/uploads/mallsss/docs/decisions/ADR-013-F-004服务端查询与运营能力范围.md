# ADR-013 F-004 服务端查询与运营能力范围

Status: Accepted
Date: 2026-08-19
Feature: F-004
Supersedes: -

## Context

`/conflicts F-004` 问题 1、2、11、12、15、16、18、19、21：操作人字段、权限分级、
F-001 反查失败的降级策略、查询能力形态、车辆删除后价格数据处理、后台列表/筛选、
导出、批量改价成本、二次确认，是本 feature 服务端与运营能力层面的一组决策。

## Decision

- 价格记录补充"操作人"字段，与 ADR-006/ADR-009 的操作日志同一口径，本期用登录账号标识，
  不等待 F-006 最终角色模型定稿。
- 改价权限本期不做角色区分，按"登录即可改价"推进，待 F-006 定义角色分级后再收紧。
- F-001 反查 F-004"价格是否已填写"时，若查询本身失败（如数据库异常），F-001 阻塞发布
  并报错，不允许静默当作"未填写"处理。
- F-004 向 F-001 暴露的查询能力做成进程内方法调用（服务端合一），并支持批量车辆 ID 查询，
  供管理后台列表核对未定价车辆使用。
- 车辆被删除/进回收站后，其价格记录保留只读，不清理，留给 F-005 设计落地时统一处理
  （与 ADR-009 对 F-003 图片文件的处理取向一致）。
- 管理后台需要按价格状态（未填价/面谈/已定价）筛选车辆的能力；不做独立的价格历史列表页，
  历史记录在车辆详情页内查看。
- 本期不做价格记录导出。
- 不做批量改价：100 台车规模下，即使需要整体调价，运营手动逐台修改的工作量可接受，
  批量能力带来的实现复杂度（批量校验、批量事务、批量历史生成）本期不值得投入。
- 改价操作不需要二次确认：价格改错可以再次修改覆盖，不是不可逆操作，与删除类操作不同。

## Consequences

+ 操作人、失败语义、权限口径都与 F-001/F-003 已有决策保持一致，降低认知和实现成本。
+ 批量车辆 ID 查询能力让运营能快速核对哪些车还没定价，配合 ADR-003 的发布前置校验使用。
+ 不做批量改价、不做导出、不做二次确认，避免了本期的过度设计。
- 价格历史缺少独立的查看/筛选页面，运营查"这台车改过几次价"只能进入详情页逐条看，
  数据量大时体验一般，可接受但不是最优。
- 权限暂不分级意味着任何登录管理员都能直接改价，是 principles.md"后台账号越权"零容忍项
  在价格这个敏感字段上的一个已知风险敞口，待 F-006 落地后收紧。
