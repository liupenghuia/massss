# ADR-008 F-003 数据模型与交互规则

Status: Accepted
Date: 2026-08-19
Feature: F-003
Supersedes: -

## Context

`/conflicts F-003` 问题 1、4、5、9、10、18、19、21、22、23、24：图片说明的数据模型、
删除替换规则、评估报告基数、排序与编辑的生效时机、批量上传、并发排序、删除方式等，
是本 feature 数据模型和交互层面的一组相关决策。

## Decision

- 图片说明为 1:1 关系：一张图片配一段说明文字，字数不限；"无上限"指图片数量无上限，
  不是单张图片可挂多条说明。
- 图片/评估报告支持删除，删除需二次确认；"替换"实现为"新增一张 + 删除旧的"，不做原地覆盖。
- 删除后对象存储文件直接物理删除，不做软删除/异步清理/历史版本保留。
- 评估报告允许一辆车挂多份（不同机构/时间），按上传时间倒序展示，不支持手动排序；
  一份报告对应一个文件，不支持多文件组成一份报告。
- 图片排序、说明文案、评估报告等增删改都是"编辑"动作（呼应 ADR-004），保存后立即生效，
  不存在独立于车辆 published/unpublished 状态之外的"已保存未发布"中间态。
- 图片上传要求车辆已存在（哪怕草稿态），用 F-001 的技术主键做关联锚点。
- 管理后台支持批量选择/拖拽多文件一次性上传，要有进度反馈，部分文件失败不影响其余文件成功。
- 不做多人同时排序的并发冲突检测，后写覆盖可接受（图片顺序属于 principles.md"可带上线"的瑕疵）。
- 不做"打包下载某车全部图片/报告"的能力。

## Consequences

+ 数据模型简单（1:1 说明、单文件报告），减少不必要的子表和交互复杂度。
+ 批量上传覆盖了运营最高频的操作场景（下限 4 张，实际会传更多）。
+ 编辑即生效、无中间态，交互心智模型简单，管理后台不需要额外的"发布图片"按钮。
- 不做并发冲突检测意味着极端情况下多人同时排序会互相覆盖，但概率低、后果可接受。
- 物理删除意味着误删且未二次确认失误的情况无法恢复，需要依赖二次确认这道防线。
