# ADR-030 F-005 回收站接口契约定稿

Status: Accepted
Date: 2026-08-19
Feature: F-005, F-001, F-003, F-004
Related: ADR-023（状态建模与生命周期）、ADR-024（彻底清除与对象存储）、ADR-025（权限操作与公开侧表现）
RFC: docs/rfc/2026-08-19-F-005-回收站接口.md（Accepted，契约已改）

## Context

ADR-023/024/025 裁决了回收站的业务规则，但未落到接口契约的具体形态。RFC 落地评审中
reviewer-domain、reviewer-qa、reviewer-api 各自发现契约设计缺口（trash/restore 不对称、
幂等与乐观锁顺序未定义、"从未删除车辆调用恢复"的边界缺口、AdminRecycleBinItem 字段用省略号
代替真实定义等），用户授权按推荐方案自行决断定稿。契约已由 contract-keeper 依此改入
`contracts/openapi.yaml` 与 `contracts/errors.yaml`。本 ADR 记录最终定稿的接口边界规则。

## Decision

### 接口
- 新增 `POST /admin/vehicles/{id}/trash`（删除到回收站）、`POST /admin/vehicles/{id}/restore`
  （恢复），两者**对称**：都支持 If-Match 或 body.version 二选一乐观锁。
- 新增 `GET /admin/recycle-bin`（列表，支持 keyword 搜索+分页）、
  `GET /admin/recycle-bin/{id}`（只读详情）。

### 检查顺序（trash / restore 一致）
1. 车辆不存在 → 404 `VEHICLE_NOT_FOUND`
2. 已彻底清除（`purged=true`）→ 404 `RECYCLE_BIN_ITEM_PURGED`（trash/restore 对称，均用此码）
3. **幂等短路优先于乐观锁校验**：已处于目标状态（trash 遇到已在站、restore 遇到已恢复）
   直接 200 成功，**不比对 version**，即使客户端带的 version 已过期。
4. restore 额外分支：车辆**从未进入回收站**（`trashedAt` 一直为空）→ 新增错误码
   409 `VEHICLE_NOT_IN_RECYCLE_BIN`，**不当幂等成功**处理，避免掩盖前端误调用。
5. 以上均不命中时才校验乐观锁，不一致 409 `VEHICLE_VERSION_CONFLICT`。

### AdminRecycleBinItem
- **不含 `status` 字段**：车辆在回收站期间 `status` 本身不变（ADR-023 正交建模），
  `originalStatus` 已完整表达"删除前状态"，避免两个字段语义重叠引起混淆。
- **不含价格字段**：价格统一走既有 `GET /admin/vehicles/{id}/price-records`
  （已放宽为对回收站/已清除车辆同样可访问），避免两套价格查询口径不一致。
- **含 `version` 字段**：供前端调用 restore 时作为 body.version 或拼 If-Match，
  列表/详情响应不返回 ETag header，version 走响应体。
- `purgeDueAt` **严格等于 `trashedAt` + 720 小时**，不做自然月/日历对齐；多次「删除→恢复→
  再删除」循环后基于最新一次 `trashedAt` 重新计算。

### 既有接口收窄
- `AdminVehicle`（在管详情主接口）新增两个**非 required** 只读字段 `trashedAt`、`purged`，
  供管理后台判断车辆可编辑性；该接口对回收站中车辆**仍可访问**（不改 404），
  回收站的只读浏览统一收口到新的 `/admin/recycle-bin/{id}`。
- 全部在管写接口（PATCH/publish/unpublish/price/images 全系列/reports 全系列）对
  `trashedAt` 不为空的车辆一律 409 `VEHICLE_IN_RECYCLE_BIN`，检查顺序为：
  回收站态 → 版本冲突 → 状态转换合法性（回收站态最先短路）。
- `GET .../images`、`.../reports`、`.../price-records` 三个只读接口放宽为车辆存在（含回收站中、
  含已彻底清除）即可访问；已清除车辆的 images/reports 记录仍原样返回，
  服务端不过滤，**前端需自行处理对象存储文件已失效导致的加载失败**。

### 回收站列表边界
- 排序：`trashedAt` 倒序，并列时 `id` 倒序（二级排序键）。
- `keyword` trim 后为空等价于未传；无匹配结果与分页越界均返回空 `items`，不报错。

## Consequences

+ trash/restore 完全对称，前端只需一套乐观锁调用逻辑。
+ "从未删除车辆调用恢复"这个此前完全没被任何评审提出、由 reviewer-qa 在契约评审阶段发现的
  边界缺口，被新增错误码堵上，避免误调用被静默吞掉。
+ AdminRecycleBinItem 去掉冗余的 status 字段与价格字段，模型更干净，价格查询口径统一。
+ 检查顺序显式写入契约 description，避免服务端实现时各自猜测幂等短路与乐观锁的先后关系。
- 新增 3 个错误码（RECYCLE_BIN_ITEM_PURGED、VEHICLE_NOT_IN_RECYCLE_BIN、VEHICLE_IN_RECYCLE_BIN），
  客户端错误处理分支增多。
- `GET .../images`/`.../reports` 对已删除/已清除车辆放宽访问，是对既有契约行为的反向变更
  （以前删除后必 404，现在仍可访问），需要更新对应的既有契约测试用例，否则会被现有"删除后应
  404"的断言误判为回归。
- "恢复优先于清除任务"这一竞态的自动化验收依赖服务端测试环境提供可控调度时钟，本 RFC 不覆盖，
  是遗留给实现阶段的测试基础设施缺口。
