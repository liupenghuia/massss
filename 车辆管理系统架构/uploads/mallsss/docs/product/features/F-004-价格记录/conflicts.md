## 冲突项

### C-1 当前价格是否单独建表（快照表）

- 各方主张：
  - **api** 主张双表：`vehicle_prices`（当前价格快照，vehicle_id 唯一）+ `price_change_records`（历史，append-only），一次改价 = 更新快照 + 插入历史，必须同一事务。
  - **qa** 主张双表：当前价格作为 F-004 自己表里的"最新状态"字段，与历史记录在同一事务内同时写。
  - **domain** 主张单表：不建"当前价格"表，当前价格 = 最新一条价格记录的"变动后值"，写入只需一次 INSERT。
  - **admin** 只主张"价格记录表按事件流水（append-only）设计"，未表态是否另有快照表。
- 分歧根因：对"两份数据分裂风险"与"读性能/查询复杂度"的权重不同。api/qa 认为跨表事务可控且需要独立快照；domain 认为两份数据分裂本身就是零容忍项的来源，宁可不建第二份。
- 选项 A：快照表 + 历史表双表同事务（api、qa）— 代价：每次改价必须保证跨表原子性，api 自己列为「高」风险项（双写非事务化会导致零容忍的历史丢失/错乱）；多一处可能与历史不一致的数据。
- 选项 B：仅历史表，当前价格由最新记录派生（domain）— 代价：每次读当前价格都要按 vehicle_id 取最新记录（domain 未说明该查询的索引/性能代价，api 在另一处指出 `price_change_records` 需要 `vehicle_id + created_at` 复合索引）。

### C-2 首次设价是否算一次"价格变动"、"变动前值"如何表示

- 各方主张：
  - **domain** 主张：首次设价是"初始化"不是"变动"，但仍生成第一条记录，其"变动前值"是一个显式的"未填写"占位（不是 0 或空字符串）。
  - **qa** 列为「高」风险且明确表示未定义：变动前值该是 null？还是根本不生成记录？直接影响表结构与验收用例。
  - **api** 列为待答问题：如果必须先建车辆再单独改价，"从空到有值"这第一次算不算一条价格变动记录。
  - **admin、miniapp** 未提。
- 分歧根因：domain 已给出建模方案，api/qa 认为该点尚无结论、需求侧未定义。
- 选项 A：首次设价生成记录，变动前值 = 显式"未填写"占位（domain）— 代价：变动前值字段必须承载第三种取值（未填写/数值/面谈），前后台展示需要额外处理该占位。
- 选项 B：首次设价不生成记录（qa 列出的备选）— 代价：qa 指出这会改变"价格是否已填写"的判定依据，也改变历史链的起点。

### C-3 "价格是否已填写"的判定依据

- 各方主张：
  - **domain** 主张：= 是否存在至少一条价格记录（"判断逻辑简单且没有死角"）。
  - **api** 明确指出该点未定：是查"当前价格快照是否存在"还是查"历史记录表是否非空"，两者在"从未设置过价格"时结果一致但实现选型不同，必须在契约里写清，否则 F-001 与 F-004 理解不一致。
  - **qa** 只要求返回 `{filled: boolean}`，未主张判定依据。
- 分歧根因：与 C-1 数据模型选型直接绑定。
- 选项 A：查历史记录表是否非空（domain）— 代价：与 C-1 选项 B 绑定。
- 选项 B：查当前价格快照是否存在（api 列出的备选）— 代价：与 C-1 选项 A 绑定；api 强调无论选哪个都必须在契约里显式写死。

### C-4 F-001 反查 F-004 的调用形式

- 各方主张：
  - **api** 主张做成**同进程内的模块级查询函数**，不走 HTTP 内网调用（依据 principles.md「服务端合一」，"没必要为一次内部判断引入网络往返和额外的失败模式"）。
  - **qa** 主张做成 **HTTP 查询接口**（举例 `GET /admin/vehicles/{id}/price-status`，返回 `{filled: boolean}`），并说明"QA 需要这个接口存在才能写 F-001↔F-004 的联调用例"。
  - **admin** 主张"稳定、低延迟的查询接口（**单车或批量车辆 ID** 查询当前价格状态），供 F-001 的 publish 端点同步调用"。
  - **domain** 主张"可被同进程内部调用的查询能力（**不是简单前台 API**）"。
- 分歧根因：api/domain 从"服务端合一、少一层失败模式"出发；qa 从"可被自动化联调测试断言"出发；admin 额外提出批量查询需求（用于运营核对哪些车未定价）。
- 选项 A：进程内模块函数（api、domain）— 代价：qa 明确指出这样 F-001↔F-004 的联调用例无接口可断言。
- 选项 B：HTTP 端点（qa）— 代价：api 指出引入网络往返与额外失败模式；需要额外定义鉴权与失败语义。
- 选项 C：支持批量车辆 ID 查询（admin）— 代价：无角色对批量形态的实现成本作出评估。

### C-5 提交与当前值相同的价格时的行为

- 各方主张：
  - **api** 主张"无实际变化不生成历史记录"：仅当新值（type + amount）与当前值不同才写历史，"避免管理员重复点击保存刷出大量无意义历史"。
  - **qa** 列为「中」风险且明确表示未定义：是应该拦截提交，还是允许并生成一条"无变化"记录，"两种实现对历史记录的干净程度影响很大"。
  - **admin、domain、miniapp** 未提。
- 分歧根因：api 已单方拍定行为，qa 认为该行为尚未被产品定义、影响验收用例预期。
- 选项 A：服务端静默跳过、不生成记录（api）— 代价：api 未说明是否要给管理员返回提示；qa 的验收用例预期需相应确定。
- 选项 B：拦截提交并报错（qa 列出的备选）— 代价：未有角色评估。
- 选项 C：允许并生成"无变化"记录（qa 列出的备选）— 代价：qa 指出会污染历史记录的"干净程度"。

### C-6 改错价格的纠错机制

- 各方主张：
  - **admin** 定为「高」风险，主张必须在**业务流程上明确纠错方式**："运营手滑把 100000 打成 1000000 是大概率会发生的操作失误"，若无标准纠错路径，"运营会本能地想去数据库改，或者反复插入价格来回拉扯真实历史，把价格记录变成噪音"；只在数据层面禁止篡改不够。
  - **api** 定为「低」风险，将其表述为一个待用户确认的取舍：是否需要"标记/隐藏错误记录"手段，"还是接受这个代价"（前台会出现 10万→1万→10万 这样让访客困惑的记录）。
  - **qa** 反向要求：管理后台必须**完全不提供**编辑/删除历史记录的入口，否则"不可篡改"这条零容忍项无法自动化断言。
  - **domain、miniapp** 未提。
- 分歧根因：严重度评级不一致（admin 高 / api 低）；且 admin 要的"纠错路径"与 qa 要的"接口层面完全禁止改动历史"在可选实现上互相约束。
- 选项 A：追加一条"更正记录"覆盖显示（admin 列出）— 代价：前台仍会看到错误记录（api 描述的困惑场景）；需定义"覆盖显示"规则。
- 选项 B：极短时间窗口内撤销最近一条记录（admin 列出）— 代价：qa 指出任何针对已生成记录的删除能力都会削弱"不可篡改"的可验证性。
- 选项 C：完全无纠错手段，只能再改一次价格盖过去（admin、api 均列为备选）— 代价：admin 指出运营会绕过系统直接改数据库或反复拉扯历史；api 指出前台历史会对访客造成困惑。

### C-7 后台是否需要价格记录的查看 / 筛选能力

- 各方主张：
  - **admin** 主张后台至少要有"按价格状态筛选"（未填价 / 面谈 / 已定价）和价格记录的时间范围筛选能力；并明确质疑 ADR-006 定下的"操作日志只落库不做查看页面、只能靠开发协助查数据库"这一基调是否适用于价格这种敏感数据，认为"价格记录需要一个哪怕最简陋的后台查看列表"。
  - **api、domain、qa、miniapp** 均未提及后台查看/筛选能力。
- 分歧根因：admin 认为 ADR-006 的既有基调与价格数据的审计优先级不匹配；其余角色未对此表态。
- 选项 A：沿用 ADR-006 基调，不做后台查看页面 — 代价：admin 指出排查"这台车上个月改过几次价、什么时候从面谈变成数字"会很困难。
- 选项 B：补最低限度的后台筛选 + 价格记录查看列表（admin）— 代价：admin 未评估工作量；与 ADR-006 已有结论不一致（该 ADR 按项目铁律只能新增不能修改）。

### C-8 前台价格展示的决策权归属

- 各方主张：
  - **api** 主张 F-002 是"哑终端"（principles.md），"所有『该显示数字还是显示面谈文案』的判断必须由 F-004 在响应里给全，F-002 只做渲染"。
  - **admin** 主张展示条数、排序方向、混合类型样式、是否拆成两个组件"这些不是 F-004 能替前端决定的"，需要 F-002 明确，F-004 的接口只需能支撑。
  - **qa** 指出"面谈"状态下前台文案（"面议"/"电话咨询"）"由 F-004 定义还是 F-002 定义没有说明"。
  - **miniapp** 把分页/懒加载归给"前台展示相关的 feature（而非 F-004 本身）"。
- 分歧根因：对 principles.md「前台哑终端」的适用范围理解不同——api 认为包含展示文案与展示判断，admin/miniapp 认为展示策略属于前端 feature 的职责。
- 选项 A：F-004 在响应里给全展示所需的一切（api）— 代价：F-004 契约需承载展示文案，admin 认为这超出 F-004 能决定的范围。
- 选项 B：展示策略与文案由 F-002 定义（admin、miniapp）— 代价：F-002 brief 目前为空（domain 指出）；qa 指出文案归属没有说明会导致前台措辞不统一。

### C-9 F-006 权限未定时 F-004 能否先按假设推进

- 各方主张：
  - **admin** 提出两条路："需要 F-006 先给出角色划分，**或者**本期先按『登录即可改价』的最低假设做，待 F-006 补充后再收紧"。
  - **domain** 明确反对内部假设："这条应作为跨 feature 待裁决问题记录，**不能在 F-004 内部自行假设**为『所有管理员都能改价』"。
  - **qa** 引用 principles.md："已确认只有一种管理员角色、不设审批流程，意味着任何登录管理员可以直接改价并立即生效、无第二人复核"，并指出这对零容忍字段风险较高。
  - **miniapp** 只要求服务端在写入价格记录前校验登录态与权限。
- 分歧根因：admin 允许带假设推进以免阻塞，domain 要求阻塞并上升为裁决项；qa 认为 principles.md 已有事实结论。
- 选项 A：按"登录即可改价"最低假设推进（admin）— 代价：domain 指出这是在 F-004 内部自行假设，触碰「后台账号越权」零容忍项的边界。
- 选项 B：阻塞，等 F-006 给出角色划分（domain）— 代价：admin 指出 F-006 brief 当前完全空白，"这一评审职责在当前信息下无法闭环"。

### C-10 F-005 价格记录保留策略由谁先出方案

- 各方主张：
  - **qa** 主张 "F-004 **先给出假设**，并在 F-005 评审时对齐"。
  - **domain** 主张 "**F-005 评审时需要显式回答**『车辆删除后价格记录是否保留、是否在回收站详情里仍可查看』"，同时在待答问题里也留了"还是可以先在 F-004 内部按『永久保留、不级联删除』假设推进"这一备选。
  - **api** 主张 "F-004 与 F-005 **提前对齐**接口边界"，并要求 F-004 查询路径先预留"车辆不可见时价格记录也不可查"的过滤点。
  - **admin** 主张与 F-005 的删除语义对齐，未指定由谁先出方案。
- 分歧根因：F-005 brief 为空（domain、api 均指出），双方都把定义责任指向对方 feature。
- 选项 A：F-004 先按"永久保留、不级联删除"假设推进（qa、domain 的备选）— 代价：F-005 落地时若结论不同，需回改 F-004 查询路径（api 指出这正是要预留过滤点的原因）。
- 选项 B：等 F-005 评审给出方向（domain）— 代价：F-005 尚未设计，F-004 契约中的公开查询过滤逻辑无法定稿。

## 需要用户裁决的问题

1. **价格变动记录是否补"操作人"字段？** api（高）、admin（高）、qa（中）、miniapp 四方一致主张补，理由是 ADR-006 已给 F-001 操作日志定了"操作人、操作时间、车辆 ID、变更前后状态"的口径，价格作为更敏感数据信息量反而更少"说不通"；但四方均要求由用户确认。若补，操作人的识别依据要不要等 F-006 账号模型先定？（admin 问题 1、api 问题 1、qa 问题 4、miniapp 问题 1）
2. **改价权限是否需要角色区分？** F-006 brief 完全空白。admin 允许"本期先按登录即可改价的最低假设推进、待 F-006 后收紧"，domain 明确反对在 F-004 内部自行假设，qa 引用 principles.md 认为"只有一种管理员角色、任何登录管理员可直接改价且立即生效、无第二人复核"。请裁决：阻塞等 F-006，还是按最低假设推进。（C-9）
3. **数据模型：当前价格是否单独建快照表？** api、qa 主张"快照表 + 历史表、同一事务双写"，domain 主张"只建历史表、当前价格 = 最新记录的变动后值"。这一裁决同时决定问题 4 的答案。（C-1）
4. **"价格是否已填写"的判定依据是什么？** 查当前价格快照是否存在，还是查历史记录表是否非空？api 强调无论选哪个都必须在契约里写死，否则 F-001 与 F-004 会各自理解不一致。（C-3）
5. **首次设置价格算不算一次"价格变动"？要不要生成记录？"变动前值"如何表示？** domain 主张生成记录且变动前值用显式的"未填写"占位（不是 0 或空串）；qa（高）指出这是空白，null / 不生成记录两种做法会导致表结构和验收用例完全不同。（C-2）
6. **"面谈"与具体数值互相切换算不算一次价格变动、要不要生成记录？** admin（倾向都算，但要求用户明确确认）、qa（中，列为未定义，"否则测试用例的预期行为无法确定"）。（admin 问题 8、qa 问题 2）
7. **提交与当前价格完全相同的值时如何处理？** api 已单方拍定"不生成记录"；qa 列出三种可能（拦截提交 / 允许并生成"无变化"记录 / 跳过）并指出"两种实现对历史记录的干净程度影响很大"。（C-5）
8. **改错价格的标准纠错流程是什么？** admin 定为「高」并主张必须给出业务流程上的纠错路径（否则运营会去改数据库或反复插入价格拉扯历史）；api 定为「低」并把它表述为"是否接受错误记录永久出现在前台历史里"的取舍；qa 要求后台完全不提供任何编辑/删除历史记录的入口，否则"不可篡改"无法自动化断言。三选一：追加更正记录覆盖显示 / 短时间窗口内撤销最近一条 / 完全无纠错手段。（C-6）
9. **已设置的价格能否被清空回"未填写"状态？** 若可以，对已上架车辆意味着什么——自动下架、阻止后续操作、还是允许"已上架但未填价"长期存在？domain 指出 ADR-004 现有状态机没有对应的过渡动作，若允许清空则 F-001 状态机需重新评估。（G-13）
10. **价格数值的单位、精度、取值范围？**（元还是万元、是否允许小数、是否允许 0 或负数、有无上限、货币是否固定为人民币）domain（中）、qa（中）均指出需求完全未提，直接影响输入校验用例与前后台展示口径。（G-1）
11. **F-001 反查 F-004 时若查询本身失败（如数据库异常），F-001 应阻塞发布报错还是视为"未填写"拒绝发布？** api 强调不能隐式吞异常当成"未填写"（否则明明填了价格却发布不了，运营侧难以排查），并明确追问"这个失败语义谁来定义"。（G-2）
12. **F-004 向 F-001 暴露的查询能力做成什么形态？** 进程内模块函数（api、domain，依据"服务端合一"）还是 HTTP 端点（qa，理由是没有接口就无法写 F-001↔F-004 的联调用例）？是否需要支持批量车辆 ID 查询（admin，用于运营核对哪些车未定价）？该契约由谁主导定义、何时定稿（qa 问题 9）？（C-4、G-11）
13. **前台展示的价格变动记录是全量还是有条数/时间范围限制？是否分页？** 五个评审全部提出该空白。qa 另加一问：向访客展示完整降价历史是否存在业务上的顾虑（议价心理），产品是否已确认要全量展示？（A-10、qa 问题 10）
14. **前台展示的决策权归谁？** api 主张 F-002 是哑终端、所有"显示数字还是显示面谈文案"的判断必须由 F-004 在响应里给全；admin 主张展示条数/排序/样式"不是 F-004 能替前端决定的"；qa 指出"面谈"的前台文案（"面议"/"电话咨询"）由谁定义没有说明。（C-8、G-15）
15. **车辆被移入回收站或彻底删除（F-005）后，当前价格与历史记录如何处理？**（保留只读、禁止再修改、跟随隐藏、还是级联删除）另需裁决由谁先出方案：qa 主张 F-004 先给假设，domain 主张 F-005 评审时显式回答。F-005 brief 目前为空。（C-10、A-9）
16. **后台是否需要价格记录的查看列表与筛选能力？** admin 主张至少要有"按价格状态筛选（未填价/面谈/已定价）"和时间范围筛选，并质疑 ADR-006"操作日志只落库不做查看页面、只能靠开发协助查数据库"的基调是否适用于价格这种敏感数据。其余四方均未表态。（C-7）
17. **价格记录是否需要备注/原因字段**（便于运营复盘调价逻辑），还是严格只存"前值、后值、时间"三元组？（admin 问题 5、G-6）
18. **本期是否确定不做价格记录导出？** admin 要求在本 feature 里显式确认而非默认沿用 ADR-006，并问"如果后续财务需要对账，导出需求预计什么时候会提出"。（G-16）
19. **明确不做批量改价这一既定范围，其操作成本是否可接受？** admin（中）指出价格是运营最高频变更字段，大宗调价只能逐台改成本很高，且短时间内产生大量单条价格记录"容易被误判为价格波动异常"；admin 声明不要求推翻 brief 的结论，但需要用户确认代价可接受。（admin 风险表）
20. **车辆创建（草稿态）时是否允许在同一动作里直接带初始价格**，还是必须先建车辆、再单独调用一次改价接口？（api 问题 3、domain 问题 7、G-17）
21. **改价操作是否需要"二次确认"这类防呆 UI？** qa 指出这属于产品决策，但会直接影响"误操作导致价格显示错误"这类场景的测试用例设计。（G-7）
22. **是否存在通过微信生态（公众号文章、好友/群聊转发链接）触达车辆价格页面的获客场景？** 若存在，请确认 ADR-001（不做小程序、Web 页面在微信内置浏览器打开）是否已完全覆盖；miniapp 声明该诉求不在 F-004 范围内，但"需要有人明确归属到哪个 feature"。（G-8）
