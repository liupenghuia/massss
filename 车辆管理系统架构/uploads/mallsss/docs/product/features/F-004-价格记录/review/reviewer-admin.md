## 我理解的需求

管理员可以给车辆设置/修改价格，价格字段支持两种形态：具体数值或"面谈"。每次价格发生变动（含"面谈"与数值之间的相互切换），系统自动生成一条价格记录，包含变动前值、变动后值、变动时间，且历史记录不可篡改。访客在前台能看到当前价格与价格变动记录。F-004 向 F-001 暴露"价格是否已填写"状态供发布前置校验（ADR-003）使用。价格字段不落在 F-001 车辆核心表里，完全由 F-004 独立管理（ADR-007）。明确不做：价格审批流程、批量改价、促销/折扣机制。

从管理后台角度看，这是一个"高频、单点、强留痕"的操作：运营会频繁地对单台车改价，每次改价都必须留下不可抵赖的痕迹，且这条痕迹最终会被访客看到。

## 我的方案倾向

- 价格修改入口挂在车辆详情/编辑页上，作为独立于 F-001 车辆核心信息表单的一个模块（符合 ADR-007 的边界），单独提交、单独校验，不与 F-001 的保存动作耦合。
- 价格记录表按"事件流水"设计（append-only），只允许 insert，不允许 update/delete，从数据库权限层面而非仅业务逻辑层面禁止篡改，落实 principles.md「价格历史记录丢失或错乱」零容忍项。
- 价格记录必须包含操作人字段（沿用 ADR-006 对 F-001 操作日志"操作人、操作时间、车辆 ID、变更前后状态"的记录口径），价格记录本身就是 F-004 的审计日志，不需要另建一套单独的操作日志表。
- 面向前台的接口与面向后台的接口对同一份价格记录做不同字段裁剪：后台看到完整记录（含操作人），前台只看到值和时间，避免内部信息外泄。
- 本期不做批量改价、不做审批，符合 brief 的"明确不做"，但需要在管理后台列表页给运营留一个"按价格状态筛选"的最低限度能力（如筛选"未填价格""面谈""已定价"），配合 ADR-003 的发布前置校验，方便运营在批量核对哪些车还没定价时不用逐条打开详情页。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 价格记录缺少"操作人"字段 | brief 中价格记录字段只列了"变动前值、变动后值、变动时间"，没有操作人。如果多个管理员账号共用后台，价格改错了却查不到是谁改的，等价于 principles.md 零容忍项「价格历史记录丢失或错乱」的可追溯性缺失，也和 ADR-006 里 F-001 操作日志"操作人、操作时间、车辆 ID、变更前后状态"的记录口径不一致，F-004 作为更敏感的价格数据反而信息量更少，说不通。 |
| 高 | 权限模型未定义，价格修改权限无从谈起 | F-006（后台账号管理）brief 目前完全空白，没有角色划分。价格是最容易被滥用/误操作的敏感字段，"关注点：权限模型与角色划分"这一评审职责在当前信息下无法闭环——不知道是否所有登录后台的账号都能改价，还是需要更高权限角色。这直接关系到 principles.md「后台账号越权」零容忍项。 |
| 高 | 价格记录"不可篡改"但没有纠错机制 | 运营手滑把 100000 打成 1000000 是大概率会发生的操作失误。历史记录不可篡改是对的，但如果没有"追加一条更正记录"的标准操作路径，运营会本能地想去数据库改，或者反复插入价格来回拉扯真实历史，把价格记录变成噪音。需要在业务流程上明确纠错方式，而不是只在数据层面禁止篡改就完事。 |
| 中 | 明确不做批量改价，但价格是运营最高频变更的字段 | 大宗调价场景（比如车龄增长统一折价、市场行情整体下调）如果只能逐台改，运营操作成本很高，且短时间内产生大量单条价格记录，容易被误判为"价格波动异常"。这是 brief 已经拍板不做的范围，不要求推翻，但需要用户确认这个操作成本是可接受的。 |
| 中 | 明确不做导出，价格历史无法离线核对 | 财务/运营对账、复盘价格调整策略时通常需要导出价格变动明细。ADR-006 里 F-001 已经拍板"本期不做车辆清单导出，后续有实际运营需求再评估"，F-004 的价格记录导出应该沿用同一个结论，但需要在本 feature 里显式确认，不能默认沿用而不写清楚。 |
| 中 | 价格记录列表在后台侧没有筛选/搜索能力 | 单车价格改动次数多了之后（尤其是没有批量能力，改价更依赖逐次操作），后台如果要排查"这台车上个月改过几次价、什么时候从面谈变成了具体数字"，没有按时间范围筛选的能力会很难查。 |
| 低 | "面谈"与具体数值互相切换时的记录展示格式未定义 | 变动前值可能是"面谈"字符串，变动后值可能是数字，反之亦然。后台列表渲染这类混合类型记录时需要明确展示规则（如是否要千分位格式化数字、"面谈"如何视觉区分），否则容易被运营误读为脏数据。 |

## 对其他端的隐含要求

- **对 F-001（车辆信息管理）**：ADR-003 已定义 F-001 发布前反查 F-004 的"价格是否已填写"状态，F-004 需要提供一个稳定、低延迟的查询接口（单车或批量车辆 ID 查询当前价格状态），供 F-001 的 publish 端点同步调用；F-004 的价格状态字段语义（空/具体数值/面谈）要与 F-001 的校验逻辑严格对齐，不能出现 F-004 认为"已填写"而 F-001 判定"未填写"的不一致。
- **对 F-002（前台车辆展示）**：前台展示的价格记录列表是一个新的信息密度点，需要 F-002 明确：历史记录展示条数是否分页/限制、按时间倒序还是正序、面谈与数值混合的展示样式如何统一、是否需要区分"当前价格"卡片与"历史价格"列表两个独立组件。这些不是 F-004 能替前端决定的，但 F-004 的接口返回结构必须能支撑这些展示需求，接口设计前需要和前端对齐。
- **对 F-002 / 前台接口**：价格记录接口必须做字段裁剪，后台专属字段（操作人等）绝不能出现在 `/public/*` 接口的响应体里，这需要在契约层面（未来的 contracts/）明确区分 admin DTO 与 public DTO，不能用同一个序列化结构直接暴露给前台。
- **对 F-006（后台账号管理）**：F-004 的价格修改权限依赖 F-006 的角色体系，但 F-006 brief 当前是空白。F-004 无法在权限模型未定的情况下给出"谁能改价"的最终方案，这是一个跨 feature 的阻塞项，需要 F-006 先给出角色划分，或者本期先按"登录即可改价"的最低假设做，待 F-006 补充后再收紧。
- **对 F-005（回收站）**：车辆被软删除/恢复时，价格记录如何处理（是否跟随隐藏、恢复后价格记录是否完整保留）需要与 F-005 的删除语义对齐，避免车辆恢复后价格历史"看起来丢了一段"，触发 principles.md 的零容忍项。
- **对 F-001 的操作日志（ADR-006）**：ADR-006 已经为 F-001 定了"操作日志只落库不做查看页面"的基调，F-004 的价格记录事实上承担了同等甚至更高优先级的审计职责，是否要和 F-001 的操作日志共用同一套后台查询/排查方式（目前是"只能靠开发协助查数据库"），需要用户确认这个体验是否也适用于价格这种敏感数据，还是价格记录需要一个哪怕最简陋的后台查看列表。

## 我需要别人回答的问题

1. 价格记录是否需要包含"操作人"字段？如果需要，其识别依据是什么（F-006 账号体系目前是空的，是否要等 F-006 先确定账号模型）？
2. 价格修改权限是否需要角色区分（例如普通运营 vs 管理员），还是所有登录后台的账号权限一致，都能改任意车辆价格？
3. 如果价格录入错误，运营的标准纠错流程是什么：允许追加一条"更正记录"覆盖显示，还是允许在极短时间窗口内撤销最近一条记录，还是完全没有纠错手段、只能靠再改一次价格来盖过去？
4. 前台展示的价格历史记录是否有条数/时间范围限制？还是要展示车辆上架以来的全部价格变动？
5. 价格记录是否需要备注/原因字段（便于运营自己复盘调价逻辑），还是严格只存"前值、后值、时间"三元组？
6. 车辆被移入回收站（F-005）后，其价格记录是否保留、是否在恢复后完整可见？
7. 本期是否确定不做价格记录导出？如果后续财务需要对账，导出需求预计什么时候会提出？
8. "面谈"与具体数值互相切换算不算一次价格变动，是否都要生成价格记录（brief 字面表述是"价格变动"，倾向于都算，但需要用户明确确认）？
