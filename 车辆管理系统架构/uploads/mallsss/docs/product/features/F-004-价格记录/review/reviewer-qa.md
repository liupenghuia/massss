## 我理解的需求

管理员可以为车辆设置/修改价格，价格分两种形式：具体数值、或"面谈"。每次价格发生变动（无论从哪种形式到哪种形式）都要自动生成一条不可篡改的价格记录，包含变动前值、变动后值、变动时间。访客在前台能看到车辆当前价格和价格变动记录。F-001 的发布前置校验（ADR-003）需要能读取"该车价格是否已填写"这个布尔状态，"面谈"也视为已填写。车辆核心信息表（F-001）不包含价格字段，价格数据完全归 F-004 独立管理（ADR-007）。价格显示错误、价格历史记录丢失或错乱属于 principles.md 的零容忍项。

## 我的方案倾向

- 价格记录应设计为**只追加（append-only）**的存储模型：不提供任何"编辑/删除历史记录"的管理后台入口和 API，从接口层面而非约定层面保证"不可篡改"，这样"不可篡改"才是一条可自动化验证的验收标准（断言不存在对应的 update/delete 端点，或存在但对已生成记录返回 403/404）。
- 建议价格记录表独立于当前价格值：当前价格可以作为车辆的一个"最新状态"字段（在 F-004 自己的表里，不进 F-001），每次变动同时更新"当前价格"和追加一条历史记录，两者在同一事务内完成，避免出现当前价格与最新历史记录不一致的错乱。
- 建议价格修改接口比照 F-001 编辑接口的乐观锁模式（spec.md 中 F-001 已采用），防止并发改价导致历史记录错序或丢失——这属于零容忍项，测试用例应包含并发写入场景。
- "价格是否已填写"这个状态建议由 F-004 提供一个轻量查询接口（如 `GET /admin/vehicles/{id}/price-status`），返回 `{filled: boolean}`，供 F-001 发布校验反查，具体契约留给 API 评审定，但 QA 需要这个接口存在才能写 F-001↔F-004 的联调用例。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | "不可篡改"缺少可验证的技术约束 | 需求只说了历史记录不可篡改，但没说管理后台是否提供"删除/编辑某条价格记录"的入口。如果后台留了编辑历史记录的功能，这条零容忍项无法通过自动化测试断言，必须先明确"不可篡改"在接口层面具体禁止哪些操作。 |
| 高 | 首次设置价格是否算"变动"未定义 | 车辆创建时价格字段为空，管理员第一次填价格，"变动前值"应该是什么（null？不生成记录？）。这直接影响价格记录表结构（变动前值是否允许为空）和验收用例的预期结果，需求未说明。 |
| 高 | 并发改价缺少并发控制说明 | 两个管理员同时修改同一辆车价格，若无乐观锁/事务保护，可能导致后写覆盖先写但历史记录顺序错乱，直接命中"价格历史记录丢失或错乱"零容忍项，但需求和 brief 均未提及并发场景。 |
| 中 | "面谈"与具体数值互转是否算一次变动未定义 | 例如价格从"面谈"改为"88000"，或反过来，算不算触发一条价格记录？需要明确，否则测试用例的预期行为无法确定。 |
| 中 | 提交相同价格值的行为未定义 | 管理员把价格改成和当前值完全相同的数值，是应该阻止提交（前端/后端校验拦截），还是允许并生成一条"无变化"的记录？两种实现对历史记录的"干净程度"影响很大，需要明确。 |
| 中 | 价格记录是否包含操作人未定义 | F-001 的基本操作日志记录了"操作人/时间/车辆ID/状态变更"，但 F-004 brief 只提到"变动前值、变动后值、变动时间"，没有操作人。价格是零容忍项，出错时如果不知道是谁改的，排查和追责都做不到。 |
| 中 | 价格数值的格式/边界规则空白 | 是否允许小数、是否允许 0 或负数、是否有上限、单位（元/万元）是否固定，这些都影响输入校验用例，需求完全没提。 |
| 中 | 车辆进入回收站(F-005)/被删除后价格数据的处理未定义 | 价格能否继续修改、历史记录是否保留或级联删除，跨 feature 依赖不清楚，会影响"历史记录丢失"这条零容忍项的边界判定。 |
| 低 | 前台价格记录展示的范围未定义 | 是展示全部历史还是仅最近 N 条，是否分页，没有说明，无法据此写前台展示的验收用例。 |

## 对其他端的隐含要求

- **对 F-001（发布前置校验，ADR-003）**：F-004 需要暴露一个查询接口/字段，返回"该车价格是否已填写"的布尔状态（面谈也算已填写）。这个接口的契约（谁调用、入参出参、鉴权方式）目前未定义，F-001 的发布逻辑联调依赖它先行确定（ADR-003 中已明确指出这一读依赖）。
- **对 F-005（回收站）**：车辆被软删除/移入回收站或彻底删除后，价格当前值与历史记录如何处理（保留只读、禁止修改、还是随车辆级联删除）需要 F-004 先给出假设，并在 F-005 评审时对齐，否则回收站上线时可能出现"车辆已删除但价格记录还能被改"或反过来"车辆恢复后价格历史丢失"的场景，触碰零容忍项。
- **对 F-002（前台车辆展示）**：前台需要展示当前价格和价格变动记录，"面谈"状态下前台应显示的文案（如"面议""电话咨询"）需要统一措辞，这个文案由 F-004 定义还是 F-002 定义没有说明；价格变动记录的展示粒度（全量/近期/分页）也需要 F-002 配合确定 UI 承载方式。
- **对 F-006（后台账号管理）**：principles.md 已确认只有一种管理员角色、不设审批流程，意味着任何登录管理员可以直接改价并立即生效、无第二人复核。这对价格这种零容忍字段而言风险较高，是否需要"修改价格二次确认"这类 UI 层面的防呆设计，属于产品决策，但会直接影响 QA 对"误操作导致价格显示错误"这类场景的测试用例设计，需要产品明确是否需要该防呆环节。
- **对服务端通用规范**：参照 F-001 spec 中"编辑接口加乐观锁防覆盖写"的既有模式，F-004 的改价接口如果没有同等的并发保护机制，会与 F-001 已建立的技术规范不一致，也会给"价格历史记录丢失或错乱"这条零容忍项留下漏洞。

## 我需要别人回答的问题

1. 车辆首次设置价格（此前从未填写过）算不算一次"价格变动"？要不要生成一条价格记录？如果生成，"变动前值"如何表示（null/空字符串）？
2. "面谈"与具体数值之间互相切换，是否算一次价格变动、需要生成记录？
3. 管理员提交的新价格与当前价格完全相同时，系统应该拦截提交，还是允许并生成一条"无变化"的历史记录？
4. 价格记录是否需要记录操作人（管理员账号/用户名）？F-001 的操作日志有记录操作人，F-004 目前的字段列表（变动前值/变动后值/变动时间）里没有。
5. 具体数值价格的格式规则是什么：是否允许小数、是否允许 0 或负数、是否有上限、货币单位是否固定为人民币？
6. 管理后台是否提供任何"编辑/删除已生成的价格记录"的功能入口？如果完全不提供，"历史记录不可篡改"这条零容忍项才能落到具体的接口约束上进行自动化验证。
7. 价格修改接口是否需要类似 F-001 编辑接口的乐观锁机制，防止并发改价导致历史记录错序或覆盖丢失？
8. 车辆被移入回收站或被彻底删除（F-005）后，该车的当前价格和历史价格记录应如何处理：保留只读、禁止再修改，还是随车辆级联删除？
9. F-001 读取"价格是否已填写"这个状态的接口契约（端点、鉴权、返回格式）由谁主导定义、什么时候能定稿，以便 F-001 发布逻辑联调？
10. 前台展示的价格变动记录是展示全部历史还是仅展示最近若干条？是否需要分页？向访客展示完整降价历史是否存在业务上的顾虑（议价心理），产品是否已确认要全量展示？
