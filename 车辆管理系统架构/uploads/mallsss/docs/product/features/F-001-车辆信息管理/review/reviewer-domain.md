## 我理解的需求

管理员在管理后台维护一个核心实体——「车辆卡片」（车辆），其生命周期由一个状态机驱动：

- 新建车辆 → 可保存为 **草稿**，也可 **直接发布** 进入 **已上架**
- **已上架** → 可执行 **下架** → 变为 **已下架**
- **已下架** → 可执行 **重新上架** → 变回 **已上架**
- 管理员可以 **编辑** 已有车辆的信息（brief 未限定编辑仅适用于哪些状态）
- 全程无审核环节，管理员保存即生效

本功能明确排除：价格（F-004）、删除/回收站（F-005）、图片与评估报告（F-003）、前台展示逻辑（F-002）。这意味着「车辆卡片」在 F-001 范围内只承载状态与"核心字段"本身，价格、图片、报告是挂在同一车辆实体上、但由其他 feature 独立管理的关联数据。

## 我的方案倾向

- 将「车辆」建模为单一聚合根，字段集合为"车辆基础信息"（不含价格、不含图片/报告引用的具体内容，只需预留关联外键位）。
- 状态机保持最小化的三态：`草稿(DRAFT)` / `已上架(PUBLISHED)` / `已下架(DELISTED)`，不引入"待审核"等中间态，与"无需他人审核"的需求一致。
- 状态转移与内容编辑解耦：编辑操作只更新字段内容，不隐式触发状态变化；状态变化（发布/下架/重新上架）是独立的显式动作。即"保存草稿"“发布”“下架”“重新上架”是四个动作，"编辑"是贯穿所有状态都可执行的操作，二者正交。
- 建议为车辆引入一个业务侧唯一标识（如车架号/VIN 或内部编号），作为跨 feature（价格记录、图片、回收站）关联和运营查重的锚点，即使 brief 未提及，也应在契约设计前确认是否需要。
- 车辆卡片本身不感知价格、图片、报告是否齐备，发布动作是否需要校验这些外部数据，应作为跨 feature 依赖显式定义，而不是隐含在 F-001 内部。

## 反对/风险
| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | "核心字段"未列出具体清单 | brief 全文只说"车辆卡片核心字段"，没有任何字段名。这会导致 contracts/ 无法定义车辆实体的 schema，是后续所有开发的阻塞项，必须先补齐。 |
| 高 | 发布动作与价格(F-004)/图片(F-003)的依赖关系未定义 | principles.md 提到"每车最少 4 张"图片，属于业务现状描述还是发布前置校验规则不明；价格是否为发布必需字段也不明。若两端各自假设不同，会出现"能发布但前台无价格/无图"的展示错误，直接触碰 principles 中"内容准确 > 功能丰富"的质量底线。 |
| 中 | 编辑对状态的影响未定义 | 编辑已上架车辆后是否保持"已上架"、是否需要重新确认、是否允许编辑已下架车辆，brief 均未说明。若管理后台与前台对"编辑中/编辑后即时生效"理解不一致，可能出现前台短暂展示不完整信息。 |
| 中 | 车辆唯一性约束缺失 | 是否存在唯一标识（车架号等）及是否要求唯一性校验未提及。缺少此约束，长期运营中可能出现重复车辆卡片，影响回收站、价格记录等关联数据的准确关联。 |
| 低 | "已下架"能否退回"草稿"未定义 | 当前状态机只允许 已上架⇄已下架 往返，草稿只是单向起点。不算死状态（已下架仍可回到已上架），但若运营上有"下架后想大改再重新走草稿流程"的诉求，现状态机无法支持，需提前确认是否需要。 |

## 对其他端的隐含要求

- **对 F-002（前台车辆展示）**：前台只能读取状态为"已上架"的车辆，"草稿"与"已下架"车辆必须对前台完全不可见。principles.md 的零容忍项列出"已删除车辆仍在前端可见"，同一逻辑应类推适用于未上架/已下架车辆，但 brief 未显式写出，需要在 F-002 需求中明确并作为强约束落地（例如后台查询接口需按状态过滤，不能依赖前端自行判断——这也符合"前端是哑终端"的产品取向，过滤逻辑必须在后台完成）。

- **对 F-003（图片与评估报告）**：图片与报告需要以车辆 ID 关联到本 feature 的聚合根，因此 F-003 的接口设计依赖 F-001 先确定车辆的唯一标识字段。若"发布"要求最少 4 张图片才能上架，则发布动作需要跨 feature 校验 F-003 的数据，需要明确校验放在哪一端、以及车辆无图片时能否被直接发布——这个校验逻辑目前在两个 feature 之间没有归属，必须显式裁决。

- **对 F-004（价格记录）**：价格与车辆基础信息分离管理，但"新建/发布"车辆时是否要求价格已存在未定义。若允许车辆无价格发布，则 F-002 前台展示时需要处理"有车无价"的兜底逻辑（这本身有踩到"价格显示错误"零容忍红线的风险）；若不允许，则 F-001 的发布动作需要依赖 F-004 提供的价格存在性校验，两个 feature 需要约定调用时序与失败提示归属。

- **对 F-005（回收站）**：本 feature 明确不做删除，但"已下架"状态客观上是删除前必经的准备态。需要向 F-005 明确：删除操作允许作用于哪些状态的车辆（例如是否要求先下架才能删除、草稿车辆能否直接删除），否则 F-005 设计时可能对 F-001 状态机做出错误假设。

- **对权限体系（跨全局，可能涉及后续鉴权 feature）**：brief 只提到"管理员"这一单一角色，未定义是否存在多级后台角色（如只读/仅编辑/可发布下架）。principles.md 零容忍项包含"后台账号越权"，若后续引入角色分级，发布/下架这类状态转移动作的权限边界需要在本 feature 或权限 feature 中明确归属，否则默认"任意登录管理后台的账号都能做任何操作"这一假设可能与安全预期冲突。

## 我需要别人回答的问题

1. "车辆卡片核心字段"具体包含哪些字段？（例如：车架号/VIN、品牌、车型、年款、里程、颜色、车况描述等，请给出确定清单，用于定义 contracts/ 中的实体 schema）
2. 车辆是否需要一个业务唯一标识（如车架号），是否要求系统内唯一？重复录入时如何处理（拒绝/提示/允许）？
3. 编辑操作是否会改变车辆当前状态？例如编辑"已上架"车辆后是否仍保持"已上架"，还是需要管理员重新点击"发布"确认？"已下架"车辆是否允许编辑？
4. 发布（新建直接发布 / 草稿转发布 / 重新上架）时，是否要求车辆已关联价格记录（F-004）？是否要求已有最少数量的图片（呼应 principles 中"每车最少 4 张"的描述，这是硬性发布前置条件还是仅为业务现状说明）？
5. "已下架"状态是否允许退回"草稿"状态，还是状态机只支持 草稿→已上架⇄已下架 这一条固定路径？
6. 管理员角色是否存在权限分级（例如是否所有能登录管理后台的账号都能执行发布/下架操作）？这是否属于本 feature 范围，还是应归入独立的账号权限 feature？
