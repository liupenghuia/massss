## 我理解的需求

F-001 要在服务端提供车辆卡片核心字段的增删改与上下架能力，供管理后台使用：

- 新建车辆：保存为「草稿」或直接「已发布」，无需他人审核。
- 编辑已有车辆的信息（不含价格、图片、评估报告，这些归 F-003/F-004）。
- 状态流转：已发布 → 下架，已下架 → 重新上架。
- 不做删除/回收站（F-005）、不做价格记录（F-004）、不做图片与评估报告上传（F-003）、不做访客端展示逻辑（F-002）。

按 principles.md，本 feature 属于「服务端合一」架构下 `/admin/*` 路由的一部分，车辆记录需要作为稳定实体供 F-002（前台展示，只读 published 状态）、F-003（图片/评估报告挂载）、F-004（价格记录挂载）通过外键关联使用。车辆数量级「一百台以内」，属于小数据量场景，不构成索引/分片压力，但接口与状态机设计仍需为跨 feature 的字段扩展和状态可见性留出稳定契约。

## 我的方案倾向

- **实体与主键**：`vehicles` 表，`vehicleId` 作为稳定主键（自增或 UUID 均可，倾向自增 + 对外暴露即可，因为不涉及多租户或跨系统协作），作为 F-003/F-004 挂载图片、评估报告、价格记录的外键锚点。车辆核心字段本身不内嵌图片、价格等其他 feature 的数据。
- **状态机**：`status` 枚举为 `draft`（草稿）/ `published`（已发布）/ `unpublished`（已下架）三态，做成显式状态机而非布尔标记，状态转换通过独立端点实现：
  - `POST /admin/vehicles`（创建，状态由请求体或子路径决定是存草稿还是直接发布）
  - `PUT/PATCH /admin/vehicles/:id`（编辑核心字段，不改变 status）
  - `POST /admin/vehicles/:id/publish`（草稿或已下架 → 已发布）
  - `POST /admin/vehicles/:id/unpublish`（已发布 → 已下架）
  这样上下架操作可以做成**幂等**：对已处于目标状态的车辆重复调用 publish/unpublish 返回 200 且无副作用，而不是报错，避免管理员误触或网络重试导致状态抖动或产生多余的操作记录。
- **并发控制**：编辑接口使用乐观锁（`version` 字段或 `updatedAt` 比对），防止两个管理员同时编辑同一车辆时后写静默覆盖前写。冲突时返回 409，由前端提示"该车辆已被修改，请刷新后重试"。
- **创建幂等性**：新建车辆接口要求前端传 `Idempotency-Key`（或使用草稿的客户端临时 ID），防止表单提交时网络重试在服务端产生重复车辆记录。
- **前台可见性过滤**：`/public/*` 相关只读接口（供 F-002 使用）在服务端硬编码只查询 `status = published` 的记录，不接受调用方传参决定过滤条件，避免触发 principles.md 中「已删除/已下架车辆仍在前端可见」的零容忍红线。
- **不预留软删除字段**：F-005（回收站）尚未设计，本期不在 `vehicles` 表里预置 `is_deleted`/`deleted_at`，遵循 YAGNI，留给 F-005 时再做迁移。此为倾向，非定论，需与用户确认迁移成本是否可接受（见下）。
- **数据量级**：100 台以内，单表、单库即可，不需要分表、不需要额外索引优化，仅需为 `status`、更新时间等常用筛选字段建普通索引。

## 反对/风险
| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 车辆核心字段清单未定义 | brief 只说"车辆卡片核心字段"，未列出具体字段（品牌、型号、车架号/VIN、里程、上牌年份等）及必填/选填、类型、长度约束。这是 contracts 的基础，缺失则 API 设计无法定稿，且后续每次补字段都可能是一次不兼容变更（如把选填改必填）。 |
| 高 | 发布前置条件未定义 | 车辆无图片、无评估报告时能否"直接发布上架"？brief 明确图片/评估报告归 F-003、本 feature 不做上传，但若允许在完全没有图片的情况下发布，前台会展示空卡片，与 principles.md「内容准确 > 功能丰富，有疑问时砍功能不砍校验」的取向存在潜在冲突。 |
| 高 | 并发编辑无乐观锁会导致数据丢失 | brief 未提及多管理员协作场景。若两个管理员同时打开同一车辆编辑并保存，后提交者会静默覆盖前者的修改，且用户不会感知到丢失了什么。 |
| 中 | 状态机边界情况未定义 | 草稿态车辆能否直接"下架"（其实从未上架过）？已下架车辆编辑保存后状态是否保持不变，还是需要管理员重新确认发布？这些边界会影响状态机设计和前端按钮的可用性逻辑。 |
| 中 | 唯一性校验规则未定义 | 车架号/VIN 或车牌号是否要求全局唯一？如果录入重复车辆信息，服务端应报错还是允许（例如同一车多次进出库）？ |
| 中 | 草稿态数据泄露风险 | 草稿车辆是否可能通过直接猜测/遍历 ID 被前台或非授权接口访问到？需要在 `/admin/*` 接口上做鉴权，`/public/*` 接口上做状态过滤，两者都要落实，任一遗漏都会命中 principles.md 零容忍项。 |
| 低 | 缺少操作审计 | brief 要求"全程不需要他人审核"，但上下架、编辑等操作若无操作人和时间记录，后续排查"谁在什么时候把车下架了"会缺乏依据。这不阻塞上线，但建议至少记录 `updatedBy`/`updatedAt`。 |
| 低 | 软删除字段是否预留未定 | 本期不做删除，若完全不预留字段，F-005 上线时需要做一次 schema 迁移；若现在预留又违反 YAGNI。倾向不预留，但需用户确认是否接受后续迁移成本。 |

## 对其他端的隐含要求

- **对 F-002（前台车辆展示）**：前台只读接口必须只返回 `status = published` 的车辆，这个过滤逻辑必须在服务端固定实现，不能依赖前端传参或前端二次判断——这是 principles.md「前端是哑终端」的直接要求，也是「已删除/已下架车辆仍在前端可见」零容忍项的第一道防线。F-002 开发时不应假设自己需要做任何状态过滤，服务端已经做好。
- **对 F-003（图片与评估报告）**：F-003 需要一个稳定的 `vehicleId` 作为外键挂载图片和评估报告，本 feature 必须保证车辆主键一旦创建后不可变更（不能因为编辑车辆信息导致 ID 变化）。同时需要明确：车辆状态变更（下架/删除相关，虽删除归 F-005）时，F-003 挂载的图片是否需要联动处理（如下架车辆的图片是否仍需在管理后台可见以便重新上架时复核）——这个耦合点需要跨 feature 澄清。
- **对 F-004（价格记录）**：同样依赖稳定的 `vehicleId` 外键。当前 F-001 明确不做价格字段，但需要确认：车辆卡片本身是否包含任何价格占位字段（哪怕为空），还是价格完全由 F-004 独立管理、F-001 的车辆记录里不出现任何价格相关列。这个边界如果不清楚，两个 feature 的 contracts 会互相踩脚。
- **对 F-005（回收站）**：本期不做软删除设计，F-005 上线时大概率需要给 `vehicles` 表新增字段（如 `deletedAt`）并对现有的编辑/查询/状态流转接口做兼容改造（例如"已删除"状态与现有 `draft/published/unpublished` 三态如何共存）。F-005 设计者需要提前知道现在的状态字段设计，避免届时状态机冲突。
- **对管理后台前端**：草稿态与已发布态在编辑表单上的必填校验规则可能不同（草稿允许字段不全，发布需要字段完整），这个校验规则应该由服务端在 `publish` 端点里强制执行并返回明确的字段级错误，而不是由前端自行判断"这些字段填了就能发布"——同样是「前端哑终端」原则的体现，前端只负责展示服务端返回的校验失败信息。

## 我需要别人回答的问题

1. 车辆卡片核心字段的完整清单是什么？哪些必填、哪些选填？是否包含车架号/VIN、车牌号等具有唯一性要求的字段？
2. 车辆在完全没有图片/评估报告的情况下，是否允许直接发布（状态变为 published）？如果不允许，"至少需要几张图片"这个校验应该由 F-001 的发布接口检查（依赖 F-003 数据），还是产品上默认不会出现这种操作顺序？
3. 车辆卡片本身是否需要包含任何价格相关字段（哪怕是占位、由 F-004 后续填充），还是价格完全在 F-004 的独立表里，F-001 的车辆记录不涉及价格？
4. 已下架车辆是否允许编辑核心字段？编辑保存后状态是否保持"已下架"不变？
5. 车架号/VIN 或车牌号是否要求系统内全局唯一？重复录入时应报错拒绝还是允许并存？
6. 管理后台账号是否有角色/权限区分（例如只读账号、只能编辑不能发布的账号），还是所有登录管理后台的账号权限相同？这决定了 `/admin/*` 接口是否需要按角色做细粒度授权。
7. 是否需要记录车辆信息的操作日志（谁在何时创建/编辑/上下架），用于后续追溯？
