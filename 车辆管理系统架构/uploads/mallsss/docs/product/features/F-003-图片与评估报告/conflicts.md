## 冲突项

### C-1 图片/报告是否支持"原地替换"

- 各方主张：
  - api 主张 **不支持原地替换**——"如需换图，走『新增一张 + 删除旧的一张』，不复用同一个对象存储 key 覆盖内容，避免 CDN 边缘缓存返回旧内容造成的隐性错配风险"
  - admin 主张 **必须支持替换**——"图片必须支持删除和替换，评估报告文件也必须支持替换……运营传错图、传错报告是必然会发生的操作事故"
  - domain（Q5）、qa（Q1）只提问"是否支持删除/替换"，未选边；miniapp 未提及
- 分歧根因：api 从 CDN 边缘缓存返回旧内容的错配风险出发；admin 从运营纠错的必要性出发（并把"图片传错车"挂到 principles.md 零容忍项）。
- 选项 A：只支持"新增 + 删除"，不做原地替换 — 代价：评审中未给出对运营操作步数的评估；admin 主张的"评估报告替换"路径在此选项下如何实现，评审中未说明
- 选项 B：支持替换 — 代价：api 指出"需要额外设计 CDN 缓存刷新策略"；admin/domain 另指出被替换掉的旧文件是否留痕未定（关系到零容忍项"评估报告文件损坏或串号"，物理删除后无法恢复）

### C-2 已上架车辆图片被删至低于 4 张时如何处理

- 各方主张：
  - admin 主张 **由 F-003 主动拦截**——"如果车辆当前状态是『已上架』，删除操作导致图片数低于 4 张时，前端提示、服务端拒绝该次删除（返回明确错误，如『已上架车辆至少保留 4 张图片，请先下架或先补充图片』）"，依据是 principles.md「内容准确 > 功能丰富，有疑问时砍功能不砍校验」
  - api 列为 **高严重度未定义项**，Q3 给出"允许删除 / 联动自动下架 / 放任继续展示等下次发布才被拦下"三选，**未选边**
  - domain 列为 **高严重度未定义项**，Q1 给出"禁止删除导致跌破 / 自动转为已下架 / 允许跌破并如实展示"三选，**未选边**
  - qa、miniapp 未提及此场景
- 分歧根因：admin 直接依据 principles 给出主张；api 与 domain 把它定性为需用户裁决的业务规则，评审内不自决。
- 选项 A：服务端拒绝该次删除 — 代价：评审中未给出；admin 自述需要配套"先下架或先补充图片"的操作路径
- 选项 B：允许删除并联动自动下架 — 代价：qa 指出 ADR-004「编辑不改变车辆状态」与"图片增删改是否算编辑"尚未与 F-001 对齐，"否则会出现『改图片要不要重新发布』的行为歧义"
- 选项 C：允许跌破，等下次重新发布时才被 ADR-003 校验拦下 — 代价：api"前台展示中的已上架车辆图片数低于业务底线，且没人报错"；admin"前台会展示一辆图片不足的车"；domain"不在零容忍清单里明写、但明显违背『每车最少 4 张』这条业务底线的隐性死角"

### C-3 上传路径：客户端直传预签名 URL vs 服务端中转

- 各方主张：
  - api 主张 **客户端直传对象存储 + 预签名 URL，服务端只做元数据落库**——三步流程"①签发预签名 URL 与临时 key ②前端直传 ③前端携带 key 回调服务端确认接口"，"第③步是唯一的数据可见性开关"
  - domain（Q7）**未选边**，但在风险表中给出先后顺序的后果判断："若先写 OSS 后写 DB，DB 写失败会留下孤儿文件（可接受，非零容忍）；若先写 DB 后写 OSS，OSS 写失败会导致 DB 记录指向不存在的文件"
  - admin **未就技术路径表态**，主张交互层"必须支持批量选择/拖拽多文件一次性上传……上传时要有进度条和逐张成功/失败反馈（部分失败不能导致整批回滚，失败的单独提示重传）"
  - qa 未选边，另列低严重度"上传失败/超时/大文件重试策略未提"
- 分歧根因：api 从"图片/评估报告是长期主要成本项""PDF 可能体积不小"出发规避服务器带宽与内存压力。
- 选项 A：客户端直传 + 预签名 URL — 代价：api 自述"前端要多做一轮『申请上传凭证 → 直传对象存储 → 回调确认』的流程，比传统的表单上传复杂，需要在前端工作量评估里体现，尤其要处理直传失败后的重试与凭证过期"；admin 评审通篇未提及预签名、凭证过期
- 选项 B：服务端中转 — 代价：api 指出"会让应用服务器承担不必要的带宽和内存压力"
- 附：api 把"上传一致性窗口未设计"列为**高**严重度，"网络重试/客户端崩溃会导致孤儿文件（成本泄漏）或『数据库有记录但文件取不到』（前台 500/破图，触碰 principles『内容准确』红线）"——无论选 A 还是 B 都存在

### C-4 评估报告的基数：多份并存 vs 一车一份覆盖

- 各方主张：
  - admin 主张 **允许一辆车挂多份**——"不同机构、不同时间的评估报告都可能需要留存，逐份独立上传/删除/替换，而不是『一车一份、上传即覆盖』"
  - api（Q5）、domain（Q3）、qa（Q5）均**只提问未选边**；miniapp 未提及
- 分歧根因：admin 从运营留存诉求出发；其余三方把基数定性为影响实体设计（单一属性 vs 一对多子实体）的待裁决项。
- 选项 A：多份并存 — 代价：domain 指出"『直接展示』时前台如何排列多份报告"需定义（"按上传时间倒序，还是也需要像图片一样手动排序"）
- 选项 B：一车一份、上传即覆盖 — 代价：admin"被覆盖前的报告是否需要留痕……旧文件如果已被物理删除，就无法恢复"；api 追问"若覆盖，是否需要保留历史版本记录"

### C-5 评估报告"直接展示"如何兑现

- 各方主张：
  - api 主张 **服务端把 HTTP 头设对即可**——"『直接展示』要求服务端在文件的 Content-Type/Content-Disposition 上做对，保证浏览器内联预览而非强制下载，这一点需要写进契约给前台联调用"
  - miniapp 主张 **高严重度，需要兜底方案**——"微信内置浏览器（X5 内核）对 PDF 的原生预览支持不稳定，很多机型/版本会直接下载失败或显示空白，而不是『直接展示』……需要有兜底方案（如转图片、跳转外部浏览器提示等），否则会被当作 bug"
  - domain：前台需明确"是内嵌查看器展示，还是提供下载链接兜底"，且"这个展示方式的选型会反过来影响 F-003 存储报告文件时是否需要额外生成预览态资源（如 PDF 转图片首页做缩略图）"
  - admin：PDF 在移动端浏览器能否直接内嵌展示"会影响前台是否需要额外的 PDF 预览组件"
  - qa：中严重度，"不确定是『页面内嵌预览』还是『新开/下载』，两种验收路径完全不同"
- 分歧根因：api 把它当作服务端响应头问题；miniapp 指出是链路/运行环境问题——"这类拦截是链路层面的，前端代码无法规避"（miniapp 该句针对域名策略，PDF 一项同属其"绕不开微信生态对 H5 链接的一系列限制"的论点）。
- 选项 A：仅靠 Content-Type/Content-Disposition 保证内联预览 — 代价：miniapp 指出在微信内置浏览器中"『直接展示』可能无法兑现"
- 选项 B：增加兜底（后端转码成图片 / 提示用户用系统浏览器打开）— 代价：domain 指出 F-003 需额外生成预览态资源；miniapp 自述"这个决定应由 Web 端 reviewer 或 F-001/F-003 主评审拍板，我这里只提出风险，不替其决策"

### C-6 对象存储直链形态：稳定公开直链 vs 签名/有效期

- 各方主张：
  - api 关注 **URL 形态稳定性**——"前台是纯客户端渲染、无登录态……需要与前端约定清楚 URL 形态是否稳定（不能因为签名 URL 有效期过期导致前台刷新后图裂）"，同时 Q8 追问"是否需要访问控制……评估报告里是否可能包含不适合被搜索引擎或非目标访客直接访问到的敏感信息"
  - admin 关注 **底层资源可获取性**——"即便车辆在业务接口层『已下架不可见』，图片/报告文件本身的 URL 如果被外部保存下来，可能仍然可以被直接访问到……业务页面不可见，不等于底层资源不可获取。这个问题目前没有任何一份文档提到"
  - qa 主张 **高严重度，先裁决才能设计用例**——"页面不可见 ≠ 资源不可访问，需要先有裁决结论才能设计验收用例"，Q7 指出"这直接决定问题 2（下架联动）的答案能否落地"
  - domain 未就直链访问控制表态；miniapp 从微信域名安全策略角度另提（见 G-15）
- 分歧根因：api 以前台可用性（图裂）为出发点要求 URL 稳定；admin/qa 以 principles.md 零容忍项「已删除车辆仍在前端可见」的精神为出发点要求资源不可被直接访问。
- 选项 A：公开直链 — 代价：admin/qa 指出下架或删除后已流出的 CDN 直链仍可被外部直接访问
- 选项 B：签名 URL / 带有效期 — 代价：api 指出"签名 URL 有效期过期导致前台刷新后图裂"，URL 形态不稳定

### C-7 图片排序是否存在独立于车辆状态的"发布"态

- 各方主张：
  - admin 主张 **保存即生效，无独立发布动作**——"brief 里『排序后保存或发布』这句话我理解为笔误或表述不清，需要用户确认"，依据是 ADR-005「下架实时生效、不做缓存延迟」
  - domain 主张 **图片不引入独立生命周期状态**（可见性完全由车辆 published 决定），但同时把 brief 原句列为**高**严重度歧义，自述"这是本次评审最大的歧义点"
  - qa 列为 **中**严重度未定义项——"是否意味着存在一个独立于发布动作的『仅保存排序』接口？如果排序必须随编辑/发布动作一并提交，会和 F-001 的编辑接口耦合"
  - api 的方案只描述"拖拽结束后前端一次性提交完整的图片 ID 顺序数组"，**未涉及是否存在发布态**；miniapp 未提及
- 分歧根因：admin/domain 依据 ADR-004/ADR-005 推定"保存即生效"，但两人都指出 brief 原文字面暗示存在第二套状态，且都未认定自己有权判定原文是笔误（admin"需要用户确认"、domain"是否只是笔误"）。
- 选项 A：保存即生效，图片无独立状态 — 代价：domain 指出"『发布』字眼不应再出现在图片模块的文案里，避免运营误以为图片有独立于车辆的发布流程"
- 选项 B：图片排序/说明存在"已保存但未发布"中间态 — 代价：domain"会出现『车辆已上架，但图片顺序处于未发布状态』这类组合，前台该展示哪一份顺序需要明确规则，否则会出现死状态（保存了却永远不生效）"，且"管理后台 UI 需要明确区分『保存草稿顺序』与『发布生效顺序』两种按钮/状态提示，这是目前 brief 完全没有覆盖的交互要求"

### C-8 排序批量提交的并发覆盖是否要处理

- 各方主张：
  - api 列为 **中**严重度——"多个管理员/多标签页同时对同一车辆排序，后提交者会静默覆盖先提交者的结果，且当前方案（整单替换）没有天然的冲突检测……静默覆盖若丢失了刚保存的说明文案关联（如 1:N 模型下说明文案挂在排序记录上），后果不止是顺序问题"，同时引述 principles 把"图片加载顺序"列为可带上线的瑕疵
  - qa 提出 **接口幂等性需双方对齐**——"前端具体交互方式（保存按钮 vs 拖拽即时提交）会反过来约束后端接口的幂等性设计，需要双方对齐后才能定验收标准"
  - admin、domain、miniapp 均未提及并发编辑场景
- 分歧根因：无正面对立主张；api 从数据损失后果定级，admin（作为被要求配合的一端）通篇未涉及。
- 选项 A：做冲突检测（评审中未给出具体机制）— 代价：评审中未给出
- 选项 B：不做 — 代价：api 描述的静默覆盖风险保留，且在 1:N 说明文案模型下可能连带丢失文案关联

### C-9 图片/报告删除后对象存储文件的清理方式

- 各方主张：
  - api 主张 **软删除 + 异步清理**——"删除时先做 DB 软删除（前台立即不可见，满足强一致要求），对象存储文件的物理删除走异步任务/生命周期规则，并保留一张『待清理』记录表或依赖 DB 状态做定期对账，防止清理任务漏跑导致存储成本长期泄漏"
  - domain（Q5）**未选边**——"删除后该图片在对象存储中的文件是立即物理删除，还是仅解除数据库关联、文件延后清理"
  - admin 关注 **留痕**——被替换/删除前的旧文件"如果已被物理删除，就无法恢复"，关系到零容忍项"评估报告文件损坏或串号"
  - qa、miniapp 未提及
- 分歧根因：api 从成本泄漏与前台强一致出发；admin 从零容忍项的可恢复性出发；domain 未定性。
- 选项 A：软删除 + 异步物理清理 + 对账 — 代价：api 自述需要额外的"待清理"记录表或定期对账任务（该任务的实现与运维无人认领，见 G-8）
- 选项 B：立即物理删除 — 代价：admin 指出误操作后无法恢复
