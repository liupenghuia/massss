## 我理解的需求

F-003 围绕两类挂载在「车辆」上的资产展开：

- **车辆图片（VehicleImage）**：每辆车最少 4 张、无上限；可拖拽排序；可对单张图片添加说明文案；
  用 F-001 的技术主键（vehicleId，见 ADR-005）作为唯一关联锚点。
- **评估报告（EvaluationReport）**：第三方出具的文件（PDF/PNG/jpeg），前台直接展示，不做在线编辑、
  不做审核流程。

图片和评估报告都不落应用服务器本地磁盘，走对象存储 + CDN。发布前是否要求已有图片，已由 F-001
ADR-003 裁定（图片数量 ≥ 4 才能发布），不在本 feature 重复实现，本 feature 只需对外提供可供
F-001 查询的图片数量事实。车辆下架时图片是否联动处理，F-001 spec.md 已明确"留给 F-003 评审裁决"
（对应 F-001 conflicts.md 问题 24），是本 feature 需要正面回答的问题，不能再往后推。

## 我的方案倾向

- **实体**：VehicleImage（id、vehicleId、objectKey/url、order、caption、createdAt）与
  EvaluationReport（id、vehicleId、objectKey/url、fileType、createdAt）作为两个独立实体，都以
  vehicleId 为强制外键，不做业务侧唯一标识（与 ADR-005 一致，杜绝车架号等不稳定标识介入）。
- **一致性边界**：以「单辆车的图片集合」和「单辆车的评估报告集合」分别作为一致性边界。任何写操作
  （上传、排序、加说明、删除）都必须在同一个 vehicleId 范围内完成，禁止跨车辆的批量操作触达同一
  事务，避免 principles.md 零容忍项"图片与车辆错配"发生。
- **图片本身不引入独立的生命周期状态**（不做草稿态图片 / 已发布图片的区分）。前台可见性完全由
  F-001 的车辆状态（published）决定，图片/报告数据本身没有 status 字段——这是对 ADR-004「编辑与
  状态转换解耦」「前端是哑终端」原则在 F-003 上的延伸：图片增删/排序/改说明属于"编辑"范畴，写完
  即生效于底层数据，是否对访客可见完全取决于车辆当前是否 published，不需要图片自己再维护一套状态机。
- **排序**：用显式的 order 整数字段维护，整组顺序作为一次原子写入提交（而非逐条单独更新单个 order
  值），避免并发下产生重复/跳号的中间态。
- **发布前置校验的查询接口**：F-003 需要对 F-001 暴露"按 vehicleId 查图片数量"的查询能力（供
  ADR-003 的发布动作读取），这个查询应读取与前台展示同一份数据（不能读缓存层导致数量与实际展示
  不一致）。

## 反对/风险

| 严重度 | 问题 | 说明 |
|---|---|---|
| 高 | 已发布车辆图片数跌破 4 张后无兜底规则 | ADR-003 只在"发布/重新上架"动作发生时校验图片≥4张，但 brief 未提及图片是否允许删除、删除后是否可能让一辆**已上架**车辆的图片数跌破 4。若允许删除且无兜底（阻止删除/强制下架/仅警告），会出现"已上架车辆图片<4"这个不在 principles.md 零容忍清单里明写、但明显违背"每车最少 4 张"这条业务底线的隐性死角。 |
| 高 | 「排序后保存或发布」暗示图片可能存在独立于车辆状态机之外的第二套状态 | brief 原句"排序后保存或发布"若字面理解，意味着图片排序存在"已保存但未发布"的中间态，这与我方案倾向中"图片无独立状态、可见性完全跟随车辆状态"的假设直接冲突。如果图片确实需要自己的草稿/发布二态，则会出现"车辆已上架，但图片顺序处于未发布状态"这类组合，前台该展示哪一份顺序需要明确规则，否则会出现死状态（保存了却永远不生效）。 |
| 中 | 评估报告的基数（cardinality）未定义 | brief 只说"上传评估报告文件"，未说明一辆车能挂几份报告：是单份可覆盖替换，还是多份并存（如多家机构各出一份）？这直接决定实体设计（Vehicle 上的单一属性 vs 一对多子实体）以及"直接展示"时前台如何排列多份报告。 |
| 中 | 图片说明文案的基数未定义 | brief"给单张图片添加说明文案……条数无上限"中的"条数"用词，既可能指"文案字数无上限"，也可能指"一张图可以挂多条独立说明"。这两种理解对应完全不同的数据模型（字符串属性 vs 子集合），且后者在产品形态上比较反常（正常认知里一张图配一段说明），需要用户确认避免建错模型。 |
| 中 | 图片/文件上传与数据库记录之间的事务边界未定义 | 走对象存储 + CDN 意味着"文件写入 OSS"与"DB 记录写入"是两个独立系统的写操作。若先写 OSS 后写 DB，DB 写失败会留下孤儿文件（可接受，非零容忍）；若先写 DB 后写 OSS，OSS 写失败会导致 DB 记录指向不存在的文件——前台展示时出现"图片打不开"，触碰 principles.md 零容忍项"评估报告文件损坏或串号"的近似场景（图片同理，虽未直接列入零容忍清单但性质相同）。这个先后顺序需要明确。 |
| 低 | 图片删除动作本身未在 brief 中提及 | brief 只写了"上传、排序、说明"，通篇没提删除。既然"最少 4 张、无上限"隐含允许管理员纠错，删除大概率是隐含必须的能力，但未显式列出，容易在验收阶段产生"这算不算需求缺失"的分歧。 |

## 对其他端的隐含要求

- **对 F-001（服务端/车辆状态机）**：F-001 的发布动作（ADR-003）需要反查 F-003 的图片数量，这要求
  F-003 提供一个稳定、强一致（不经过 CDN 缓存层）的"按 vehicleId 查图片数量"接口或数据源，且该
  接口读到的数量必须与前台实际展示的图片集合完全一致——否则会出现"F-001 判断可以发布，但前台展示
  的图片其实不足 4 张"的错配，直接命中 principles.md「内容准确 > 功能丰富」的取向。
- **对 F-001（下架联动，问题 24）**：本 feature 需要明确回答——车辆下架后，图片/评估报告在
  **管理后台**是否仍可见、仍可编辑（例如为了下架期间修图、补报告，以便重新上架时复核）。若答案是
  "仍可编辑"，F-001 的状态机不需要任何改动；若答案是"下架后锁定编辑"，则需要 F-001 在其编辑接口
  层面感知车辆状态并联动拦截，这是对 F-001 已定稿的 ADR-004（"编辑与状态转换完全解耦"）的一次
  潜在冲突，必须在裁决前对齐 F-001 owner，不能由 F-003 单方面决定后默默要求 F-001 配合。
- **对管理后台前端**：若图片排序/说明确实存在独立于车辆状态的"保存"动作（见风险表第二条），管理
  后台 UI 需要明确区分"保存草稿顺序"与"发布生效顺序"两种按钮/状态提示，这是目前 brief 完全没有
  覆盖的交互要求；若最终裁定图片无独立状态（保存即生效），则管理后台只需要一个"保存"动作，"发布"
  字眼不应再出现在图片模块的文案里，避免运营误以为图片有独立于车辆的发布流程。
- **对前台（F-002 或对应展示端）**：评估报告要求"直接展示"，其中 PDF 类型在移动端浏览器内联预览
  存在兼容性差异（principles.md 明确"移动端优先"）；前台需要明确是内嵌查看器展示，还是提供下载
  链接兜底，这个展示方式的选型会反过来影响 F-003 存储报告文件时是否需要额外生成预览态资源（如
  PDF 转图片首页做缩略图）。
- **对对象存储/CDN 基础设施**：为落实"图片与车辆错配"零容忍项，存储路径（bucket/key 命名）必须
  以 vehicleId 强绑定分区（如 `vehicles/{vehicleId}/images/...`），不能用可能重复或可回收的标识
  做路径前缀；同时图片删除、排序变更后如何触发 CDN 缓存失效，需要有明确策略，否则会出现"后台已
  改，前台因 CDN 缓存仍展示旧图/旧顺序"的表现，性质上与 principles.md「已下架车辆仍在前端可见」这
  条零容忍项的风险模式一致（虽然对象不同，但都是"状态已变、展示未变"的同类风险）。
- **对 F-005（回收站，尚未开工）**：车辆被删除/进回收站时，其图片与评估报告的生命周期如何处理
  （级联删除对象存储文件、还是仅解除关联保留孤儿文件待人工清理），F-003 目前没有义务实现，但
  应当在本 feature 的"边界与限制"里显式留一句话给 F-005 提前打招呼，避免重蹈 F-001 conflicts.md
  里"三方都在向一个尚不存在的 F-005 提要求、无人认领对接"的覆辙。

## 我需要别人回答的问题

1. 已上架车辆的图片数量因删除操作跌破 4 张时，系统应如何处理——禁止删除导致跌破 4 张、自动将车辆
   转为已下架、还是允许跌破并仅在前台如实展示不足 4 张的图片？（见风险表第一条）
2. brief 中"排序后保存或发布"是否意味着图片排序/说明存在一套独立于车辆 published/unpublished 之外
   的"已保存但未发布"中间态？如果存在，这套状态与车辆状态机是什么关系（谁的可见性优先）？如果不
   存在，"发布"二字是否只是笔误，实际只有"保存"一个动作？（见风险表第二条，这是本次评审最大的
   歧义点）
3. 一辆车能挂几份评估报告——单份可覆盖替换，还是允许多份并存？如果允许多份，前台展示时如何排序/
   区分（例如按上传时间倒序，还是也需要像图片一样手动排序）？
4. 单张图片的说明文案，是"一张图一段文案（无长度上限）"，还是"一张图可挂多条独立文案（文案条数
   无上限）"？
5. 图片是否支持删除？如果支持，删除后该图片在对象存储中的文件是立即物理删除，还是仅解除数据库
   关联、文件延后清理？
6. 车辆下架后，图片和评估报告在管理后台是否仍可查看和编辑？这个答案会决定是否需要 F-001 在编辑
   接口层面感知车辆状态（对应 F-001 conflicts.md 问题 24，也是本 feature 明确要给出的裁决）。
7. 图片上传流程是"浏览器直传对象存储（预签名 URL）+ 事后向服务端登记记录"，还是"先经应用服务端
   中转再写对象存储"？这决定了文件落地与 DB 记录哪个先发生、失败时如何回滚/重试（见风险表第五条）。
8. 评估报告文件是否有大小上限？多种格式（PDF/PNG/jpeg）混合上传时，是否要求同一份报告只能是单一
   格式，还是允许一份报告由多个文件组成（如多页扫描件拆成多张图片）？
