# 车辆信息展示系统 — 全局概览

> 这份文件定义**这个系统里有什么、叫什么**。
> 所有 agent 在评审和开发前都会读它，用来对齐术语和边界。
> 取舍偏好在 `principles.md`，具体功能在各 feature 的 spec 里。
>
> ⚠️ = 从需求推断，请确认。❓ = 待你补充。

---

## 一句话

内部人员在管理后台录入车辆信息，访客无需登录即可在手机上浏览车辆详情、图片和评估报告。

---

## 角色

| 角色 | 需登录 | 能做什么 |
|---|---|---|
| **访客** | 否 | 浏览车辆列表与详情 |
| **管理员** | 是 | 录入、编辑、删除车辆到回收站、下架、重新上架；调整价格；管理回收站 |
| **超级管理员** | 是 | 管理员的全部权限 + 分配和停用账号 |

确认：只有两级后台权限，没有"只读账号"或"审核员"，不设审批/审核流程。
超级管理员可生成、分配、停用管理员账号。
管理员可以新建车辆信息（暂时保存不发布），上传车辆信息，删除车辆信息，重新上架车辆信息，
草稿保存后可自行直接发布，无需他人审核。

## 术语表

> 这一节最重要。所有文档、代码、接口命名统一用左列词汇。

| 术语 | 定义 | 不要叫成 |
|---|---|---|
| **前台** | 面向访客的展示端，无登录 | 前端、C 端、用户端 |
| **管理后台** | 内部人员操作的管理界面，需登录 | 后台、管理前端、admin |
| **服务端** | 同时给前台和管理后台提供接口的后端 | 后台系统、API |
| **车辆** | 系统的核心实体，一台在售的车 | 商品、产品、车源 |
| **车辆卡片** | 一台车的完整信息集合（数据概念，非 UI 组件） | 车辆信息、条目 |
| **图片说明** | 挂在**单张图片**上的文案，与车辆描述不同 | 图注、备注 |
| **车辆描述** | 挂在**整台车**上的详细说明 | 简介、详情 |
| **评估报告** | 第三方检测/评估的文件 | 检测报告、质检 |
| **价格记录** | 一次价格变动的留痕，含变动前后的值和时间 | 价格历史、改价日志 |
| **回收站** | 已删除车辆的暂存区，保留 1 个月后自动清除 | 垃圾桶、软删除 |

⚠️ "图片说明"和"车辆描述"必须严格区分——这是你需求里两个不同的东西，
混用会直接导致数据模型做错。

## 模块地图

```
┌─────────────┐        ┌─────────────┐
│    前台     │        │  管理后台   │
│  无登录     │        │   需登录    │
│  移动优先   │        │  桌面优先   │
└──────┬──────┘        └──────┬──────┘
       │ /public/*            │ /admin/*
       └──────────┬───────────┘
                  ▼
          ┌───────────────┐
          │    服务端     │  ← 单一服务，路由前缀区分
          └───────┬───────┘
                  ▼
        ┌─────────┴─────────┐
        ▼                   ▼
   ┌─────────┐        ┌──────────┐
   │  数据库  │        │ 对象存储 │
   └─────────┘        │ 图片/报告│
                      └──────────┘
```

### 各模块职责

**前台** — 哑终端。只负责渲染服务端返回的内容，不做业务判断。
新增展示字段优先走"服务端加字段"，不在前台加逻辑。

**管理后台** — 唯一的数据入口。所有车辆数据的产生和变更都经过它。

**服务端** — 与管理后台**同一个项目**，用路由前缀区分对外和对内接口。
`/public/*` 无需鉴权且只读，`/admin/*` 需鉴权。

**对象存储** — 图片和评估报告文件。图片数量无上限，是主要成本项。

## 系统边界

### 在系统内
- 车辆信息的录入、编辑、删除、恢复
- 图片与评估报告的上传和展示
- 价格变动留痕
- 后台账号管理

### 不在系统内
- 访客的任何身份信息（不登录、不收藏、不留痕）
- 交易、支付、下单、询价
- 车辆的采购、库存、物流
- 数据统计与经营分析
- 与外部系统（ERP、CRM）的对接

⚠️ 以上"不在系统内"从需求推断。**这一节写得越明确，
后续 agent 越不会给你加你没要的东西。** 有遗漏请补。

## 关键约束

| 约束 | 值 | 来源 |
|---|---|---|
| 单车图片数下限 | 4 张 | 需求明确 |
| 单车图片数上限 | 无 | 需求明确 |
| 单图说明条数 | 无上限 | 需求明确 |
| 回收站保留期 | 1 个月 | 需求明确 |
| 前台是否需登录 | 否 | 需求明确 |
| 车辆总量级 | 100（当前规模，非长期上限，预计后续增长，技术方案需按可增长设计） | 需求明确，见 ADR-007 |
| 单车图片典型数量 | 8 | 影响存储成本和列表性能 |
| 是否需要 SEO | 否 | **决定前台架构，优先确认** |

## 待确认清单

这些不用现在全答，评审时会逐条追问：

1. 评估报告是 PDF、PNG、jpeg 文件直接展示
2. 车辆有"上架/下架"状态
3. 价格记录给访客看
4. 图片顺序按上传顺序定，编辑上传者可以归拽进行排序后保存或发布
5. 回收站里的车能恢复，只有恢复后才能进待编辑状态，保存草稿或立即发布
6. 删除功能普通管理员也能删
