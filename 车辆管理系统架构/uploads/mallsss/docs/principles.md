> 这份文件是 agent 的**判断依据**，不是需求清单。
> 功能细节写在各 feature 的 brief.md 里，这里只写取舍。
>
> 标 ⚠️ 的是从你的需求里**推断**出来的，请逐条确认或改写。
> 标 ❓ 的是必须由你补充的，不填 agent 会自己假设。

## 产品取向

**前端是哑终端。** 后台传什么，前端展示什么。
展示逻辑、字段可见性、排序规则一律由后台数据决定，前端不做业务判断。
新增展示字段时，优先考虑"后台加字段"而非"前端加逻辑"。

**内容准确 > 功能丰富。** 车辆信息、价格、评估报告是核心资产，
展示错误的代价远高于功能少。有疑问时砍功能，不砍校验。

**移动端优先。** 前端所有设计以手机竖屏为第一目标，桌面端为兼容。
两者冲突时以手机端体验为准。

## 质量底线

**零容忍：**
- 价格显示错误、价格历史记录丢失或错乱
- 图片与车辆错配（A 车展示了 B 车的图）
- 评估报告文件损坏或串号
- 已删除车辆仍在前端可见
- 后台账号越权（低权限账号能改不该改的东西）

**可带上线：**
- 图片加载顺序、缩略图裁切比例等展示层瑕疵
- 后台表格列宽、排序等操作体验问题
- 回收站 UI 不够精致

## 技术偏好

**服务端合一。** 前台展示接口与管理后台接口在同一个服务里，
用路由前缀区分（如 `/public/*` 与 `/admin/*`），不拆微服务。

**前台无用户体系。** 前台不做登录、不做收藏、不埋用户身份。
需要用户态的功能一律推到下一期重新评估。

   **技术栈：** 
稳定可靠（具体帮我定下来就行）

确认（见 ADR-001）：前台与管理后台均采用 Web，不做微信小程序。移动端体验用响应式/自适应网页兼容手机浏览器，不引入小程序技术栈。

   **SEO 是否重要？** 
- 只是发链接给客户看 → 纯客户端渲染即可，简单得多

**图片是主要成本项。** 每车最少 4 张、数量无上限，
图片存储与流量会是长期支出大头。选型时优先考虑对象存储 + CDN，
不把图片塞进应用服务器本地磁盘。

  **车辆数量级：** 
一百台以内

## 明确不做

以下从你的需求推断，请确认：
- 不做前台用户注册/登录/收藏
- 不做交易、支付、下单
- 不做多租户（一套系统只服务一家）
- 不做数据看板/统计报表
- 不做站内消息、通知、询价表单
- 不做多语言、多币种

## 术语约定（重要）

你的描述里出现了三个词，实际指的是两个东西，先统一：

| 统一叫法 | 指什么 | 是否需登录 |
|---|---|---|
| **前台** | 面向访客的车辆展示页面 | 否 |
| **管理后台** | 内部人员管理车辆的界面 | 是 |
| **服务端** | 同时给前台和管理后台提供接口的后端 | — |

（你原文里的"管理后台"和"管理前端"看起来是同一个东西，
"后台系统"指的是服务端。后续统一用上表的叫法。）

## 评审与改需求的默认协议

> 这是**流程默认值**，不改变上面的产品取向。用来避免把已写明的规则再问一遍。
> 零容忍项、状态机、权限、价格对错，仍须用户明示，禁止用本节省略。

**提问纪律（评审 / RFC）：**
- `principles.md`、`overview.md`、已 Accepted 的 ADR 里写明的内容，**不要**再列入「我需要别人回答的问题」。
- 已确认不做微信小程序（ADR-001）时，不要再问「要不要做小程序」。
- 「可带上线」的展示瑕疵不要升级成待裁决。
- 每道待裁决问题一行；能合并的合并。

**尚未裁且不踩零容忍时，默认：**
- 选范围更小、本期能上线的一档
- 无人认领 → 写入「明确不做」，或推迟到该管的 feature，并写明不阻塞本 feature
- 非法操作：返回明确错误（与幂等成功区分：已在目标态的重复调用才幂等）

**改已定稿需求：**
- 文案、已有范围内加字段：小改 + 一条新 ADR，不开五方评审
- 状态机 / 权限 / 价格对错 / 跨端接口：`/rfc`，且**只派受影响的 1～2 个 reviewer**
- 跨端 + 状态机 + 钱或权限同时涉及：才允许 `/review` 全角色

**编码：**
- 只读该 feature 的 `spec.md`、其 frontmatter 列出的 ADR、`contracts/` 中相关 path
- 禁止通读 `review/`、`conflicts.md`、其他 feature 的评审全文
