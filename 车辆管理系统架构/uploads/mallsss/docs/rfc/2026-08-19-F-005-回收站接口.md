# F-005 回收站接口：删除/恢复/回收站列表/已清除车辆检索

## 动机

F-005 spec（v1.1，ADR-023/024/025 已裁决）需要一整套新接口支撑软删除生命周期：
删除进站、恢复、回收站列表（带搜索分页）、已清除车辆的只读检索。当前 `contracts/openapi.yaml`
无任何回收站相关路径，`vehicles` 表也未预留 `trashedAt`/`purged` 字段。本 RFC 是 F-005 实现前的
硬前置依赖之一（另一项是数据库表迁移，非契约范畴，不在本 RFC 内）。

## 提议

### 1. 新增写接口

```yaml
/admin/vehicles/{id}/trash:
  post:
    operationId: adminTrashVehicle
    summary: 删除到回收站
    description: |
      源状态 draft / unpublished / published 均可直接删除，无需先下架。
      已上架车辆删除时，服务端额外写一条「下架」操作日志（ADR-023）。

      检查顺序（先后如下，前面命中即短路，不做后面的检查）：
      1. 车辆不存在 → 404 VEHICLE_NOT_FOUND
      2. 已彻底清除（purged=true）→ 404 RECYCLE_BIN_ITEM_PURGED
      3. 已在回收站（trashedAt 已有值，未清除）→ 200 幂等成功，不刷新 trashedAt，
         不做版本比对（幂等短路优先于乐观锁校验，即使客户端带的 version 已过期也返回成功）
      4. 以上均不命中（车辆在管）→ 校验乐观锁（If-Match 或 body.version 二选一必填，
         不一致 409 VEHICLE_VERSION_CONFLICT），通过后执行删除

      操作人、时间写入操作日志（ADR-025）。
    security: [{ adminAuth: [] }]
    parameters:
      - $ref: '#/components/parameters/VehicleId'
      - $ref: '#/components/parameters/IfMatch'
    requestBody:
      required: false
      content:
        application/json:
          schema:
            type: object
            additionalProperties: false
            properties:
              version: { type: integer, format: int64, minimum: 1 }
    responses:
      "200": { description: 已在回收站中（含幂等重复调用）, headers: { ETag: { $ref: '#/components/headers/ETag' } }, content: { application/json: { schema: { $ref: '#/components/schemas/AdminVehicle' } } } }
      "400": { $ref: '#/components/responses/BadRequest' }
      "401": { $ref: '#/components/responses/Unauthorized' }
      "404": { description: 车辆不存在（VEHICLE_NOT_FOUND），或已被彻底清除（RECYCLE_BIN_ITEM_PURGED）, content: { application/json: { schema: { $ref: './errors.yaml#/components/schemas/ErrorResponse' } } } }
      "409": { $ref: '#/components/responses/Conflict' }
      "500": { $ref: '#/components/responses/InternalError' }

/admin/vehicles/{id}/restore:
  post:
    operationId: adminRestoreVehicle
    summary: 从回收站恢复
    description: |
      恢复一律落 draft（ADR-023），不保留删除前原状态。
      乐观锁：与 trash 对称，If-Match 或 body.version 二选一必填。

      检查顺序（先后如下，前面命中即短路）：
      1. 车辆不存在 → 404 VEHICLE_NOT_FOUND
      2. 已彻底清除（purged=true）→ 404 RECYCLE_BIN_ITEM_PURGED
      3. 从未进入回收站（trashedAt 一直为空，即正常在管车辆）→
         409 VEHICLE_NOT_IN_RECYCLE_BIN（不当幂等成功，避免掩盖前端误调用）
      4. 已在回收站且未清除（trashedAt 有值）→ 校验乐观锁（不一致 409
         VEHICLE_VERSION_CONFLICT），通过后恢复为 draft，trashedAt 置空
      5. 已恢复后短时间内重复调用同一 restore（trashedAt 已被自己刚置空）→
         200 幂等成功，不比对 version（与 trash 幂等短路对称）

      恢复优先于尚未跑完的到期清除任务（ADR-024）：只要记录未被清除任务标记 purged，
      恢复即成功；该竞态由服务端事务/行锁保证原子性，客户端无需感知中间态。
      操作人、时间写入操作日志（ADR-025）。
    security: [{ adminAuth: [] }]
    parameters:
      - $ref: '#/components/parameters/VehicleId'
      - $ref: '#/components/parameters/IfMatch'
    requestBody:
      required: false
      content:
        application/json:
          schema:
            type: object
            additionalProperties: false
            properties:
              version: { type: integer, format: int64, minimum: 1 }
    responses:
      "200": { description: 已恢复为草稿（含幂等重复调用）, headers: { ETag: { $ref: '#/components/headers/ETag' } }, content: { application/json: { schema: { $ref: '#/components/schemas/AdminVehicle' } } } }
      "400": { $ref: '#/components/responses/BadRequest' }
      "401": { $ref: '#/components/responses/Unauthorized' }
      "404": { description: 车辆不存在（VEHICLE_NOT_FOUND），或已被彻底清除（RECYCLE_BIN_ITEM_PURGED）, content: { application/json: { schema: { $ref: './errors.yaml#/components/schemas/ErrorResponse' } } } }
      "409": { description: 版本冲突（VEHICLE_VERSION_CONFLICT），或车辆本不在回收站中（VEHICLE_NOT_IN_RECYCLE_BIN）, content: { application/json: { schema: { $ref: './errors.yaml#/components/schemas/ErrorResponse' } } } }
      "500": { $ref: '#/components/responses/InternalError' }
```

### 2. 新增查询接口

```yaml
/admin/recycle-bin:
  get:
    operationId: adminListRecycleBin
    summary: 回收站列表
    description: |
      仅列出 trashedAt 不为空且 purged=false 的车辆。排序：trashedAt 倒序，
      并列时按 id 倒序（二级排序键，保证同一秒内批量删除多台车时分页结果稳定，不重复不遗漏）。
      支持关键字搜索（品牌+车型，规则与 GET /public/vehicles 的 keyword 一致：服务端 trim +
      不区分大小写模糊匹配；trim 后为空字符串等价于未传，返回全量）与分页。
      keyword 无匹配结果：total 0，items 空数组，不报错。
      page 超出筛选后总数范围：返回 items 空数组，不报错（与 GET /public/vehicles 一致）。
      每项额外返回 originalStatus（删除前状态）、trashedAt、purgeDueAt（到期日，服务端计算，
      = trashedAt 时间戳 **严格 + 720 小时**，不做自然月/日历对齐，Asia/Shanghai 展示时区）。
      多次「删除→恢复→再删除」循环后，purgeDueAt 基于最新一次 trashedAt 重新计算（ADR-023）。
    security: [{ adminAuth: [] }]
    parameters:
      - $ref: '#/components/parameters/Page'
      - $ref: '#/components/parameters/PageSize'
      - name: keyword
        in: query
        required: false
        schema: { type: string, minLength: 1, maxLength: 50 }
        description: 模糊匹配品牌+车型，规则同 GET /public/vehicles 的 keyword。
    responses:
      "200":
        description: |
          回收站列表。不返回整体 ETag header——每个 item 自带 version 字段
          （见 AdminRecycleBinItem），前端据此调用 restore（作为 body.version 或拼 If-Match）。
        content: { application/json: { schema: { $ref: '#/components/schemas/AdminRecycleBinList' } } }
      "400": { $ref: '#/components/responses/BadRequest' }
      "401": { $ref: '#/components/responses/Unauthorized' }
      "500": { $ref: '#/components/responses/InternalError' }

/admin/recycle-bin/{id}:
  get:
    operationId: adminGetRecycleBinItem
    summary: 回收站内车辆详情（只读）
    description: |
      仅 trashedAt 不为空（在站或已清除）可访问；不在回收站中（含从未删除、已恢复）→ 404
      VEHICLE_NOT_FOUND。
      返回车辆核心字段只读视图（不可编辑），purged 字段标明是否已彻底清除，version 字段
      供前端调用 restore 时拼 If-Match。
      **不含价格字段**——价格走既有 `GET /admin/vehicles/{id}/price-records`
      （已放宽为对回收站/已清除车辆同样可访问），避免两套价格查询口径不一致。
      图片/评估报告复用现有只读接口（GET /admin/vehicles/{id}/images、/reports），
      本 RFC 放宽这两个接口对已删除/已清除车辆的可访问性（见下方"影响面"）。
      **已彻底清除（purged=true）车辆**：images/reports 记录仍原样返回（服务端不做二次过滤），
      但对应对象存储文件大概率已被异步删除，直链可能已失效，**前端需自行处理图片/文件加载失败**，
      不代表服务端异常。
    security: [{ adminAuth: [] }]
    parameters:
      - $ref: '#/components/parameters/VehicleId'
    responses:
      "200":
        description: 回收站内车辆只读详情（headers 无 ETag，version 已在响应体里）
        content: { application/json: { schema: { $ref: '#/components/schemas/AdminRecycleBinItem' } } }
      "401": { $ref: '#/components/responses/Unauthorized' }
      "404": { $ref: '#/components/responses/VehicleNotFound' }
      "500": { $ref: '#/components/responses/InternalError' }
```

### 3. 新增 schema

```yaml
AdminRecycleBinItem:
  type: object
  additionalProperties: false
  description: |
    回收站内车辆的只读视图。不含 status——车辆在回收站期间 status 本身不变（ADR-023 正交建模），
    originalStatus 已完整表达"删除前是什么状态"，重复放一个 status 字段只会引起混淆，故省略。
    不含价格字段，价格走 GET /admin/vehicles/{id}/price-records。
  required: [id, originalStatus, trashedAt, purgeDueAt, purged, version, brand, model,
             registrationYear, mileageKm, color, conditionDesc, energyType, transferCount,
             displacementL, energyConsumption, batteryKwh, vinMasked, createdAt, updatedAt]
  properties:
    id:
      type: integer
      format: int64
      minimum: 1
      description: 系统生成的技术主键，跨 feature 关联锚点
    version:
      type: integer
      format: int64
      minimum: 1
      description: 乐观锁版本号，调用 restore 时作为 body.version 或拼 If-Match 使用
    originalStatus:
      type: string
      enum: [draft, published, unpublished]
      description: 删除前的状态（ADR-025 展示字段）
    trashedAt:
      type: string
      format: date-time
      description: 删除进站时间
    purgeDueAt:
      type: string
      format: date-time
      description: |
        到期彻底清除时间，服务端计算 = trashedAt 严格 + 720 小时（不做日历对齐），Asia/Shanghai
        展示时区。purged=true 时本字段仅表示历史到期时间，不代表任何未来动作，不用于倒计时展示。
    purged:
      type: boolean
      description: 是否已彻底清除。已清除时本资源仅剩只读展示用途，无法恢复。
    brand:
      type: string
      description: 品牌
    model:
      type: string
      description: 车型
    registrationYear:
      type: integer
      description: 上牌年份（公元纪年）
    mileageKm:
      type: integer
      minimum: 0
      description: 里程（千米）
    color:
      type: string
      description: 颜色
    conditionDesc:
      type: string
      description: 车况描述
    energyType:
      $ref: '#/components/schemas/EnergyType'
    transferCount:
      type: integer
      minimum: 0
      description: 过户次数（手数）
    displacementL:
      type: [number, "null"]
      exclusiveMinimum: 0
      description: 排量（升）。不适用时为 null。
    energyConsumption:
      type: [number, "null"]
      exclusiveMinimum: 0
      description: 电耗。不适用时为 null。
    batteryKwh:
      type: [number, "null"]
      exclusiveMinimum: 0
      description: 电池度数（kWh）。不适用时为 null。
    vinMasked:
      type: [string, "null"]
      description: 车架号掩码（末最多 6 位明文，其余 *），规则与 AdminVehicle 一致
    createdAt:
      type: string
      format: date-time
    updatedAt:
      type: string
      format: date-time

AdminRecycleBinList:
  type: object
  additionalProperties: false
  required: [items, page, pageSize, total]
  properties:
    items:
      type: array
      items: { $ref: '#/components/schemas/AdminRecycleBinItem' }
    page: { type: integer, minimum: 1 }
    pageSize: { type: integer, minimum: 1 }
    total:
      type: integer
      minimum: 0
      description: 筛选后（含 keyword）匹配总数
```

> 落地实现时须与 `AdminVehicle` schema 做一次字段级 diff，保证两者共有字段（brand/model/...）
> 不漂移；若 `AdminVehicle` 未来新增字段，需要人工判断是否同步进 `AdminRecycleBinItem`
> （reviewer-qa/api 共同提示的一致性风险）。

### 4. 新增错误码（并入 `errors.yaml`）

| code | HTTP | 场景 |
|---|---|---|
| `RECYCLE_BIN_ITEM_PURGED` | 404 | 对已彻底清除的车辆调用 trash 或 restore |
| `VEHICLE_NOT_IN_RECYCLE_BIN` | 409 | 对从未进入回收站（或已恢复）的正常在管车辆调用 restore |
| `VEHICLE_IN_RECYCLE_BIN` | 409 | 对回收站中车辆调用编辑/发布/下架/改价/改图/上传附件等写接口 |

以上三个 code 与既有 `VEHICLE_VERSION_CONFLICT`（409）在 `errors.yaml` 里都是独立的 code 值，
客户端按 `code` 字段区分，不依赖 HTTP 状态码本身区分场景（多个 409 场景共享状态码是本项目
既有约定，见 `VEHICLE_VERSION_CONFLICT`/`IDEMPOTENCY_KEY_CONFLICT` 已有先例）。

### 5. 现有接口的行为收窄（不改 schema，改 description）

- 所有在管写接口在车辆 `trashedAt` 不为空时**一律拒绝**，返回 `409 VEHICLE_IN_RECYCLE_BIN`，
  具体路径：`PATCH /admin/vehicles/{id}`、`.../publish`、`.../unpublish`、`.../price`、
  `.../images/presign`、`.../images`（POST 确认落库）、`.../images/order`、
  `.../images/{imageId}`（含 F-003 的图片删除/改序）、`.../reports/presign`、
  `.../reports`（POST 确认落库）、`.../reports/{reportId}`（F-003 报告删除）。
  检查顺序与 trash/restore 一致：先查是否在回收站（VEHICLE_IN_RECYCLE_BIN），
  再查版本冲突（VEHICLE_VERSION_CONFLICT），再查状态转换合法性（ILLEGAL_STATUS_TRANSITION）——
  回收站态是最外层的"资源不可写"约束，最先短路。
- 所有在管**列表**接口（`GET /admin/vehicles`）**默认排除** `trashedAt` 不为空的车辆。
- **既有 `GET /admin/vehicles/{id}`（在管详情主接口）新增两个只读字段** `trashedAt`
  （`[string, "null"]`，date-time，null 表示不在回收站）与 `purged`（`boolean`），
  供管理后台无需额外请求即可判断车辆当前是否可编辑。这是本 RFC 对 `AdminVehicle` schema
  的唯一改动，字段只增不改语义。
  该接口对 `trashedAt` 不为空的车辆**仍然可访问**（不改为 404），因为它是"在管车辆详情"，
  回收站的只读浏览统一走新增的 `/admin/recycle-bin/{id}`；管理后台前端应依据这两个新字段
  判断是否要跳转到只读视图，而不是依赖详情接口 404。
- `GET /admin/vehicles/{id}/images`、`.../reports`、`.../price-records` 三个**只读**接口
  **放宽**：只要车辆存在（含回收站中、含已彻底清除），均可访问，用于满足 ADR-025「回收站内
  完全只读可查看」与 ADR-024「已清除车辆管理端只读检索价格历史」。此为对既有契约行为的
  **反向放宽**（以前删除后必 404，现在仍可访问），需要更新对应的既有契约测试用例。
  已清除车辆的 images/reports 记录仍原样返回，但对象存储文件可能已被异步删除，直链可能失效，
  服务端不做过滤，前端需自行处理加载失败。

## 影响面

| 端 | 影响 |
|---|---|
| 服务端 | 新增 2 个写接口、2 个查询接口；vehicles 表新增 trashedAt/purged 字段（表迁移，非契约）；新增每日调度清除任务（非契约，恢复与清除任务之间的竞态由服务端事务/行锁保证，测试自动化所需的调度时钟控制钩子由服务端团队在测试环境另行提供，不在本 RFC 契约范围内）；既有写接口加一处 trashedAt 拦截并规定检查顺序；既有只读接口（images/reports/price-records）放宽可访问车辆范围；操作日志新增删除/恢复/清除三类动作，清除 job 操作人记为 system:scheduled-cleanup（ADR-025） |
| 管理后台 | 新增「删除到回收站」「恢复」按钮；新增回收站列表页（用 item.version 拼 If-Match 调用 restore，不依赖 HTTP header）；车辆详情页用 `AdminVehicle` 新增的 trashedAt/purged 字段判断可编辑性并跳转只读视图；已清除车辆的图片/报告展示需做加载失败兜底 |
| 前台 | 无契约影响；`GET /public/vehicles*` 已经只认 `published`，服务端过滤条件追加 `trashedAt IS NULL` 属实现细节，不改契约 |
| F-001 | `AdminVehicle` schema 新增 trashedAt/purged 两个只读字段（只增不改语义）；所有在管写接口的错误响应新增 409 VEHICLE_IN_RECYCLE_BIN 分支，且需按本 RFC 规定的检查顺序实现 |
| F-004 | 改价接口同样受 409 VEHICLE_IN_RECYCLE_BIN 约束；价格记录 schema 不变；已清除车辆价格历史查询统一走 `price-records`，不新增第二个入口 |

## 契约变更

- `contracts/openapi.yaml`：
  - 新增路径 `/admin/vehicles/{id}/trash`、`/admin/vehicles/{id}/restore`、
    `/admin/recycle-bin`、`/admin/recycle-bin/{id}`
  - 新增 schema `AdminRecycleBinItem`（含 version/originalStatus/trashedAt/purgeDueAt/purged，
    不含 status、不含价格）、`AdminRecycleBinList`
  - `AdminVehicle` schema 新增两个只读字段：`trashedAt`（`[string,"null"]`）、`purged`（boolean）
  - 既有写接口（PATCH/publish/unpublish/price/images 系列/reports 系列，见上方第 5 节列出的
    完整路径清单）的 description 补充 `409 VEHICLE_IN_RECYCLE_BIN` 场景说明与检查顺序，
    responses 增加对应 409 分支
  - 既有 `GET /admin/vehicles/{id}/images`、`.../reports`、`.../price-records` 的 description
    放宽为"车辆存在即可访问，含回收站/已清除"，并注明已清除车辆的直链可能失效
- `contracts/errors.yaml`：新增 `RECYCLE_BIN_ITEM_PURGED`（404）、
  `VEHICLE_NOT_IN_RECYCLE_BIN`（409）、`VEHICLE_IN_RECYCLE_BIN`（409）

## 不做的替代方案

- **把回收站状态并入 `status` 枚举第四值**：ADR-023 已否决，改用正交字段 `trashedAt`，
  理由是避免 F-001 全部状态机与在管接口大改。
- **用 `DELETE /admin/vehicles/{id}` 表达软删除**：容易被误解为物理删除且不符合 REST 语义下
  DELETE 通常不可逆的直觉，改用显式的 `POST .../trash` 动词端点，与 publish/unpublish 风格一致。
- **回收站列表复用 `GET /admin/vehicles` 加 `?trashed=true` 参数**：会让"在管列表默认排除回收站"
  与"回收站列表只看回收站"这两条互斥规则挤在同一个接口里，容易被前端漏传参数导致误显示；
  改为独立路径 `/admin/recycle-bin`，语义更清晰、契约更易维护。
- **已清除车辆检索复用 `GET /admin/vehicles/{id}`**：该接口现有 description 明确是"管理端车辆详情"
  给在管场景用，混入已清除车辆会让调用方无法区分"这车还能编辑吗"；改为独立的
  `GET /admin/recycle-bin/{id}`，天然表达只读语义。

## 评审意见

### reviewer-domain
1. **`status` 与 `originalStatus` 语义重叠需澄清**：已上架车辆删除时"额外写下架日志"，是否伴随 `status` 真的翻转为 `unpublished`？若不变，`originalStatus` 是否冗余？若翻转，与"三态正交、状态机不变"的建模初衷冲突。需业务方明确。
2. **`restore` 缺少与 `trash` 对称的乐观锁 requestBody**：`trash` 有 body.version 选项，`restore` 只有 IfMatch，不对称。
3. **"IfMatch 或 body.version 二选一必填"未在 schema 层强制**，只停留在 description 文字里。
4. **幂等重复删除/恢复时乐观锁校验的处理未定义**：客户端带旧 version 重试，服务端是否仍校验版本？
5. **已彻底清除车辆调用 `trash` 与 `restore` 的错误码不对称**：restore 有专用 `RECYCLE_BIN_ITEM_PURGED`，trash 只返回笼统 404。
6. **既有 `GET /admin/vehicles/{id}` 对回收站中/已清除车辆的可访问性未定义**：与新 `/admin/recycle-bin/{id}` 存在两个入口重叠风险，建议既有详情接口对 trashedAt 不为空一律 404，只读查看统一收口到新接口。
7. **F-003 附件上传接口未被显式点名列入 409 拦截范围**，RFC 只写"图片与报告的写接口"，建议列出具体路径。
8. **操作日志要求未体现在"影响面"**：ADR-025 要求删除/恢复/清除均写审计日志，需在服务端影响一行补上。
9. **`purgeDueAt` 在 `purged=true` 时的语义**需补充说明，避免前端误用于倒计时展示。

（其余核对项——三态均可删除、恢复落草稿、恢复优先于清除、回收站只读可查、已清除车辆只读检索、公开侧 404 语义——均与 ADR-023/024/025 一致，无偏差）
### reviewer-qa
- **幂等语义可断言性**：`trash`/`restore` 幂等重复调用时 `version`/`updatedAt`/ETag 是否原样返回（不产生写入）未明确声明。
- **幂等重复调用带过期 version/If-Match 时**：应 200 忽略还是 409 版本冲突，两种解释都合理但测试用例完全不同，需明确（与 reviewer-domain 问题 4 重合）。
- **restore 端点不对称**：无 requestBody/body.version，只能用 If-Match，与 trash 不一致（与 domain 问题 2 重合）。
- **restore 的 404 应按错误码拆成两条可断言分支**：不存在 → VEHICLE_NOT_FOUND；已清除 → RECYCLE_BIN_ITEM_PURGED，而非合并成一段自然语言描述。
- **"从未进入回收站的车辆调用 restore" 是全新发现的边界缺口**：当前 description 字面意思会被误判为 200 幂等成功，这明显不对，必须明确该场景返回什么错误码。
- **VEHICLE_IN_RECYCLE_BIN(409) 与乐观锁冲突 409 需要在 errors.yaml 里确认 code 字段互斥**，契约里应显式列出该 409 response 的两种可能 error code。
- **回收站列表缺二级排序键**：仅"按 trashedAt 倒序"，并列时（同一秒删除多台车）分页结果不稳定，建议明确二级排序为 id。
- **keyword trim 后为空、无匹配结果、分页越界**三种情况的响应需显式声明（空 items 而非 404/400）。
- **purgeDueAt 计算需声明"严格 +720 小时，不做日历对齐"**，避免服务端误用"自然月+1"在跨月天数不同的月份产生偏差；多次循环后需基于最新 trashedAt 重算（与 spec 一致，建议契约里交叉引用）。
- **"恢复优先于清除任务"竞态在契约层面无可观测信号**：建议注明"由服务端事务保证原子性，客户端无需感知中间态"；验收 #22 需要控制清除任务执行时机的测试钩子，但调度任务非契约范畴，属测试基础设施缺口，需服务端另行提供。
- **AdminRecycleBinItem 缺 version 字段，两个 GET 响应缺 ETag header**：前端在回收站列表/详情页拿不到乐观锁凭证，无法在点"恢复"前提供 If-Match，需要在 schema 里补 version 或在 GET 响应加 ETag。
- **images/reports/price-records 放宽后，对象存储直链在已清除车辆的失效状态如何处理**（继续原样返回可能 404 的 URL，还是过滤）未定义。
- **AdminRecycleBinItem 的 status 与 originalStatus 语义是否重复**（与 domain 问题 1 重合，两份评审独立发现同一问题，建议优先处理）。

**需裁决问题（QA 提出，与 domain 部分重合）：**
1. restore 对"从未进入回收站的车辆"应返回什么错误码？
2. restore 是否补充 body.version 支持（与 trash 对称）？
3. 幂等重复调用带过期 version/If-Match：200 忽略还是 409？
4. AdminRecycleBinItem 是否补 version 字段 / GET 响应是否加 ETag？
5. status 与 originalStatus 语义是否重复？
6. 恢复优先于清除任务的测试调度控制钩子由谁提供？
### reviewer-api
- **restore 乐观锁语义未定义**（高，与 domain/qa 重合）：只有 IfMatch 无 body.version，且不一致时返回哪个错误码未定义。
- **trash 幂等短路与版本校验的先后顺序未定义**（高）：过期 version 遇到"已在回收站"幂等短路，两种检查顺序语义不同，需显式写出检查顺序（建议：先查存在与 purged，再查 trashedAt 幂等短路，最后对"确实要执行变更"的路径做版本比对；幂等短路时不比对 version）。
- **trash-on-purged 与 restore-on-purged 错误码不对称**（高，与 domain/qa 重合）：trash 用通用 404，restore 用专用 RECYCLE_BIN_ITEM_PURGED。
- **AdminRecycleBinItem 用注释省略号代替真实字段定义**（高）：不是合法 OpenAPI，required 数组里的字段在 properties 里无对应类型声明，合入 openapi.yaml 会导致 schema 不完整/校验失败。必须逐个展开或改用 allOf 组合公共 schema。
- **images/reports/price-records 放宽是静默行为变更**（中）：同一 404 错误码语义从"删除后必现 404"变成"仍可访问"，属于反向隐性变更，建议在 description 注明并提醒补充测试用例。
- **已清除车辆的 images/reports 放宽后可能返回死链**（中）：对象存储文件已异步删除，但记录仍返回，需明确是否标注"文件不保证可访问"。
- **trash 与每日清除任务之间的并发未在契约层给出保证**（中）：需确认 trash 与 purge 任务共享同一把行锁/乐观锁字段。
- **AdminRecycleBinItem 未包含价格字段**（低）：需确认回收站详情页是否展示价格，若不展示应在 description 说明价格走 price-records 接口。

**对其他端的隐含要求：**
- 管理后台需要用 `AdminVehicle`（在管详情主接口）或额外调用判断车辆可编辑性——建议在 `AdminVehicle` 里加 `trashedAt`/`purged` 字段。
- F-001 所有写接口需要确认多个错误码同时命中时的检查顺序（建议：回收站态最先短路 → 版本冲突 → 状态转换合法性）。
- F-004 已清除车辆的价格历史查询入口需要统一（只保留一个，避免两套查询口径不一致）。

**需裁决问题（API 提出，与 domain/qa 重合的已合并）：**
1. restore 乐观锁是否必填 version？不一致时错误码？
2. trash 幂等短路是否要在版本校验之前？
3. trash-on-purged 是否也用 RECYCLE_BIN_ITEM_PURGED？
4. AdminVehicle 是否加 trashedAt/purged 字段供管理后台判断可编辑性？
5. 已清除车辆的 images/reports 是否需要标注"文件不保证可用"？
6. AdminRecycleBinItem 是否需要价格字段？

### 裁决结果（用户授权按推荐方案自行决断）

| 问题 | 裁决 |
|---|---|
| restore 是否支持 body.version，不一致时错误码 | 支持，对称 trash；不一致 409 VEHICLE_VERSION_CONFLICT |
| trash/restore 幂等短路 vs 版本校验顺序 | 幂等短路优先，不比对 version（检查顺序已写入第 1 节接口定义） |
| trash-on-purged 错误码是否对称 restore | 对称，也用 404 RECYCLE_BIN_ITEM_PURGED |
| 从未进回收站车辆调用 restore | 新增 409 VEHICLE_NOT_IN_RECYCLE_BIN，不当幂等 |
| AdminRecycleBinItem 是否加 version / GET 是否加 ETag | 加 version 字段（不加 ETag header，前端用响应体里的 version） |
| status 与 originalStatus 是否重复 | 重复，AdminRecycleBinItem 删除 status，只保留 originalStatus |
| AdminVehicle 是否加 trashedAt/purged | 加，供管理后台判断可编辑性 |
| 已清除车辆 images/reports 死链 | 服务端不过滤，description 标注"前端需自行处理加载失败" |
| AdminRecycleBinItem 是否需要价格字段 | 不需要，价格统一走 price-records 接口 |
| 回收站列表二级排序键 | id 倒序 |
| keyword trim 为空/无匹配/分页越界 | 等同未传 / 空 items 不报错 / 空 items 不报错 |
| purgeDueAt 计算方式 | 严格 +720 小时，不做日历对齐 |
| F-003 附件接口是否显式列入 409 拦截 | 已在第 5 节列出完整路径 |
| 恢复优先于清除任务的测试钩子 | 非契约范畴，服务端测试环境另行提供，本 RFC 不覆盖 |

以上均已落实到本 RFC 正文（第 1/2/3/4/5 节），无需再回评审小节确认。
